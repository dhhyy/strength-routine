# 9/8 · 주요 문서별 개발 완성도 검토

검토일: 2026-09-08, Asia/Seoul. 코드 기준: `5eaaed8` (`main`). 요청: **주요 문서를 하나씩 읽고 실제로 얼마나 잘 개발되었는지 검토한다.** 기존 기능 코드와 명세를 수정하지 않고 구현·시험·검증 기록을 대조했다. 이 보고서와 독립 검토 노트, 재현용 시험 및 실행 로그만 추가한다.

## 1. 판단

**프로그램 선택 → 개인화 → 실제 운동 기록 → 파일 저장·재로딩의 핵심 흐름은 구현돼 있다. 백업, 일정 변경, 관리자 정밀 편집까지 연결된 로컬 앱이다. 다만 오류가 없는 완성품으로 판정할 단계는 아니다.** 이번 검토에서 기존 349개 시험이 모두 통과한 상태에서도 재시도·연속 버전 저장 경로의 기능 오류 2건을 재현했다. 여러 문서의 ‘현재/최신’ 설명도 이후 구현과 충돌한다.

백업·수행일·마감·일정·이전 복사에서 확정할 데이터 손실 결함은 발견하지 못했다. 저장 전후를 구별하고 실패·취소·오래된 검토 결과를 방어하는 구현은 구체적이다. 그러나 실제 OS 파일 공급자, 강제 종료 후 아이콘 재실행, 접근성, 배포 서명과 결제 운영은 별도 검증 대상이다. 자동 시험 수로 출시 완료나 완성도 백분율을 산출하지 않는다.

## 2. 확인한 오류의 재현과 수정 기준

### RV01 — 저장 실패 뒤 기본 버튼 재시도가 자동 휴식 의도를 지운다

계약: [휴식·가이드 명세](2026-09-08-rest-guides.md) 14행과 129행은 최초 완료 저장 실패의 재시도에도 영구 완료가 확정될 때 자동 휴식을 한 번 시작한다고 설명한다.

원인: [workout_screen.dart](../lib/workout_screen.dart) 1142–1146행은 `_commit`을 호출할 때마다 `_autoRestPending`을 다시 계산한다. `TrainingController.update`는 저장 실패 때도 메모리의 완료 상태를 유지한다. 두 번째 기본 저장에서는 이를 기존 완료 수정으로 보므로 대기 플래그가 false가 된다. 전용 `저장 다시 시도`는 `_retry`를 통하므로 이 문제가 없다.

재현 순서:

1. 사용자 기본 휴식을 90초, 완료 후 자동 시작을 켠다.
2. 아직 완료하지 않은 세트에 중량·반복을 입력한다.
3. 임시 시험 파일의 최종 쓰기 경로를 디렉터리로 막고 `세트 완료`를 누른다.
4. 저장 실패와 타이머 미시작을 확인한 뒤 파일 경로를 복구한다.
5. 여전히 활성인 기본 `수정한 기록 저장` 버튼을 누른다.
6. 새 저장소로 읽으면 세트가 완료됐지만 타이머는 null이다. 기대는 최초 영구 완료 이후 90초 타이머 시작이다.

초기 두 번과 helper를 줄인 최종 위젯 재현에서 같은 기대 assertion이 실패했다. 정상 전용 재시도 시험이 통과하는 것과 다른 경로다. `저장하고 다음 세트`도 같은 `_commit`을 호출하지만 이 버튼 자체의 추가 재현은 수행하지 않았다. 기록 손상은 확인되지 않았고 수동 휴식 시작은 가능하다.

수정 완료 기준: 최초 완료 저장 의도를 성공 또는 명시 취소까지 보존하고, 기본 저장·다음 세트·전용 재시도 각각에서 한 번만 시작해야 한다. 이미 영구 저장된 완료 수정, 제외·초안, 0초 처방과 타이머 교체 취소의 기존 계약은 유지해야 한다. 화면 플래그를 무조건 true로 유지하는 수정은 제외·취소의 의미까지 확인한 뒤 판단한다.

증거: [운동 검토 노트](../research/2026-09-08/review/workout-review.md), [재현 코드](../research/2026-09-08/review/review_workout_probe_test.dart.txt). 실행 로그와 재실행 방법은 해당 노트를 따른다.

### RV02 — 연속 저장 뒤 과거 사용 버전이 검토 검사에서 빠진다

계약: [관리자 확장 명세](2026-09-08-local-admin.md)는 사용했던 ID·버전을 재사용하지 않고 불변 이력을 보존한다.

원인: [detailed_routine_screen.dart](../lib/admin/detailed_routine_screen.dart) 210–213행은 현재 `_catalog`와 화면 진입 때 받은 `widget.versionHistory`를 검사한다. 저장 성공 후 227–230행에서 `_catalog`는 최신 프로그램으로 교체하지만 과거 버전 목록을 갱신하지 않는다. 같은 화면에 계속 머무르면 방금 대체된 버전이 사전 검사에서 빠질 수 있다.

재현 순서:

1. 버전 이력이 비어 있는 구 작업/초기 카탈로그의 프로그램 v1을 정밀 편집 화면으로 열고 v2로 검토·저장한다.
2. 화면을 나가지 않은 채 버전을 다시 v1로 바꾼다.
3. `변경 검토`를 누르면 충돌 안내 대신 검토 화면으로 이동한다.
4. 저장하면 [AdminWorkspace.withProgram](../lib/admin/admin_program_store.dart)의 사용 버전 검사가 거부한다.
5. UI는 `카탈로그 저장 재시도`라는 일반 안내만 표시하며 같은 버튼을 다시 눌러도 해결되지 않는다.

데이터 방어는 작동한다. v2와 이전 이력은 보존됐고 잘못된 버전 덮어쓰기는 발생하지 않았다. 재현 시험은 현재 오동작을 assert하여 통과하도록 작성했으므로 **제품 동작이 올바르다는 통과 결과가 아니다.**

수정 완료 기준: 편집 화면의 사용 버전 집합을 저장 후 갱신하거나 항상 최신 workspace로 조회한다. 영구적인 검증 실패와 일시적인 파일 쓰기 실패를 구분해 버전 수정으로 돌아가게 한다. 같은 화면에서 v1→v2→v3 저장 뒤 v1/v2 재사용을 검토 전에 거부하고, 실제 쓰기 실패는 후보·재시도를 유지해야 한다.

증거: [관리자 검토 노트](../research/2026-09-08/review/admin-review.md), [재현 코드](../research/2026-09-08/review/review_admin_probe_test.dart.txt), [관찰 시험 로그](../research/2026-09-08/review/admin-probe-tests.txt).

날짜가 같은 9/8 문서에 여러 개발 단계가 누적돼 날짜만으로 우선순위를 판단하기 어렵다. 예전 결과를 이력으로 보존하는 것은 맞지만, 현재형 안내까지 남겨 두면 읽는 위치에 따라 다른 결론이 나온다.

권장 수정: 현재 상태 진입점을 하나로 고정하고 각 문서 상단에 **기준 커밋·상태(현재 계약/과거 검증/후속 제안)·대체 문서**를 둔다. 역사 본문은 지우지 않고 당시 상태로 묶는다. 새 기능 검증 수·스키마·다음 작업을 여러 문서에 반복 복사하기보다 정본으로 연결한다. 이번 검토에서는 이전 문서를 수정하지 않았다.

### RV04 — 토큰 규칙의 부분 미준수

[디자인 시스템](03-design-system.md) 14–16행은 색·간격·폰트를 토큰에서만 가져오도록 정한다. 그러나 [widgets.dart](../lib/widgets.dart) 16행의 `GlassPanel` 기본 padding은 `EdgeInsets.all(16)`이고 236행의 `HeroCard`도 직접20을 사용한다. [tokens.dart](../lib/tokens.dart)의 `AppSpace.x4/x5`와 현재 값은 같지만 참조가 연결되지 않았다. 특히 GlassPanel은 현재 화면에서도 공통으로 사용된다.

현재 렌더 결함으로 확대하지 않는다. 개선은 해당 공용 여백을 기존 토큰으로 연결하는 정도가 적절하며 전체 UI 재설계의 근거는 아니다. 이번 정규식 검색은 정적 색상 리터럴 및 일부 여백 형태의 표본 검사로, 모든 스타일 하드코딩이나 접근성 준수를 완전 검증한 것은 아니다.

## 3. 문서별 판정

판정 기준은 **실제 진입 연결, 정상 결과, 취소·실패·재시도, 저장·이행, 의미 있는 시험, 문서 최신성**이다. 아래에서 ‘계약 충족’은 확인한 명세 범위의 코드와 시험이 맞는다는 뜻이며 모든 기기 검증이나 모든 잠재 결함 제거를 뜻하지 않는다.

### 01. [00-overview.md](00-overview.md) — 프로젝트 진입점

**판정: 현황 정보는 있으나 읽기 우선순위를 정리해야 한다.** 상단 LC01~06과349개 결과는 코드 상태와 맞는다. 반면 ‘최신 관리자’, ‘최신 전체 회귀’, ‘다음 할 일’이 이전 단계로 연결된다. 기능 누락보다는 RV03의 인수인계 문제다. 다음 작업자가 이 파일만 읽고 이미 완료한 백업을 다시 개발하지 않도록 하나의 현재 요약과 역사 목차로 나누는 것이 우선이다.

### 02. [01-requirements.md](01-requirements.md) — 제품 요구사항

**판정: 핵심 사용자 결정은 구현됐지만 현재 계약 절은 갱신이 필요하다.** 완성 프로그램 선택, 운동·세트 구성 보존, 중량·시작일·요일 개인화와 운영자1명이라는 방향은 코드와 맞는다. 마지막 LC완성 절과 앞부분 현재 계약의 스키마·미구현 목록이 충돌한다. 8/27 직접 생성·자동 볼륨·다중 트레이너 등 명시된 과거 제안은 현재 미구현 결함으로 세지 않았다.

### 03. [06-engine-spec.md](06-engine-spec.md) — 루틴 엔진

**판정: 현재 선택형 프로그램 엔진은 연결됐고 자동 훈련 엔진은 미구현으로 구별돼 있다.** `createActivePlan`은 원작 스냅샷, 명시 기준 중량, 일정과 목표를 보존한다. D5는 사용자 검토 후 미래 목표만 조정한다. 규칙 레지스트리·자동 e1RM·자동 디로딩을 구현했다고 해석하면 안 된다. 현재 확장 절이 주간 생성/이전120개 검증으로만 연결돼 정밀 편집·고급 처방·LC04와 최신 스키마 링크를 보강할 필요가 있다.

### 04. [2026-09-08-programs.md](2026-09-08-programs.md) — 기본 프로그램5개

### 검증 신뢰성 관찰 — 관리자 파일 I/O 대기

관리자31개 묶음 중 이력 복구 시험이 저장 버튼 이후 `pumpAndSettle` 시간초과로 실패했다. 같은 시험 단독은 통과했고 전체349개도 통과했다. [local_admin_extension_screen_test.dart](../test/local_admin_extension_screen_test.dart) 61–68행의 helper가 최대10×5ms 실시간 대기 후 fake async의 settle로 전환하는 방식이 실제 파일 I/O 지연에 취약할 가능성이 있다. **원인은 추정이며, 지연 주입으로 확정하지 않았다.** 카탈로그 값 불일치나 영구 복구 실패가 확인된 것은 아니다. 다음 시험 안정화에서는 고정 지연을 늘리는 데 그치지 말고 관찰 가능한 저장 완료를 기다리는 방식을 검토한다.

### 랜딩 재실행의 환경 실패

첫 Chromium 시작은 macOS 샌드박스의 MachPort 권한으로 검사0개 상태에서 실패했다. 제한 밖 실행은 시작됐지만 기존4175 서버의 카탈로그 요청이 `socket hang up`으로 끝나 역시 검사0개였다. 기존 서버/사용자 브라우저를 변경하지 않고 별도 임시 정적 서버를 앱 루트에 열어 마지막59개를 모두 통과했다. 두 선행 실패는 랜딩 assertion 실패로 계산하지 않는다. 이 환경 복구는 Simulator 실행이나 외부 배포가 아니다.
