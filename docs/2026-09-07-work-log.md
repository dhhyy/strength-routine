### 첫 마일스톤 · 사용자 확정

루틴 생성 → 운동 기록 → 앱 재실행 후 복원.

이를 확인할 완료 조건:
- 입력으로 만든 루틴을 오늘 화면에서 확인할 수 있다.
- 세트별 실제 중량·반복·RIR을 기록할 수 있다.
- 앱을 종료하고 다시 열어도 생성한 계획과 수행 기록이 남는다.

자동 조절의 상세 정책은 별도 인터뷰 대상으로 유지한다.

### 기록 부족 처리 · 사용자 확정

첫 생성은 최근 기록이 입력된 메인 리프트부터 지원한다. 기록이 없는 리프트의 시작 중량을 임의로 생성하지 않는다.

구현 판단: 선택한 우선순위에 기록 없는 리프트가 있으면 검증 오류를 반환한다. 화면에서는 해당 기록을 입력하거나 선택을 바꾸도록 연결하며, 사용자의 선택을 조용히 제거하지 않는다.

I05 반영 후 주의: 사용자가 리프트를 직접 선택한다는 이전 입력 흐름은 재검토한다. **프로그램에 필요한 리프트 기록이 없는 경우의 처리**를 구체화해야 하며, 프로그램에서 운동을 임의로 삭제하지 않는다.

### 트레이너 프로그램 선택 · 사용자 확정

- 트레이너가 기간·요일·운동·세트가 구성된 **완성된 프로그램을 등록**한다.
- 사용자는 여러 프로그램 중 원하는 것을 고를 수 있어야 한다.
- 공통 4주 블록을 모든 루틴에 강제하지 않는다. 기존 4주 구성은 과거 제안이며, 전체 제품의 고정 규칙으로 구현하지 않는다.
- 첫 마일스톤의 ‘루틴 생성’은 **선택한 프로그램을 사용자의 활성 루틴으로 시작하는 흐름**으로 구체화한다.
- 개인화 범위(I06): **트레이너의 운동·세트 구성을 유지**하며, **중량·시작일·운동요일**을 맞춘다. 앱이 운동을 교체하거나 세트 수를 재배분하는 생성은 첫 흐름에 넣지 않는다.
- 트레이너 등록 도구는 **사용자가 별도로 나중에 개발**한다. 현재 작업 범위에는 등록 화면·트레이너 로그인·관리 서버를 넣지 않는다.
- 사용자 앱에서 선택할 프로그램 데이터의 준비 방식은 I08로 확인한다. 개발 판단으로 데이터 공급 경계를 분리해 추후 등록 도구와 연결 가능하게 한다.

## 초기 단계에서 정한 후속 인터뷰 순서

아래는 최초 인터뷰 직후의 순서다. 후속 작업에서 I08 조사 방식 답변을 받았고 후보 조사를 완료했다. 현재 재개 질문은 아래 ‘최신 다음 재개 지점’을 따른다.

한 번에 1~2개 질문으로 진행하며, 앞선 답변에 따라 순서를 조정한다.

1. 초기 프로그램 내용의 준비 방식(I08).
2. 프로그램 처방 형식: 고정 중량/%/RIR 등, 필수 기준 기록과 부족한 기록 처리.
3. 트레이너의 프로그램 구성과 엔진 제안이 충돌할 때의 처리. 기존 D3~D6 적용 범위를 재검토한다.
4. 시작한 루틴의 버전 보존, 기록 기반 제안·적용·되돌리기.

숫자는 검토할 제안과 확정값을 구분한다. 수치의 근거 조사나 코칭 정책을 확정할 때는 출처도 함께 기록한다.

위 구현은 사용자 요구를 연결하기 위한 기술 판단이다. 특히 `manual` / `fixedKg` / `percentOfBaseline`이라는 지원 타입이 특정 훈련 방식의 사용자 승인이나 실제 콘텐츠의 수록 승인을 의미하지 않는다. 비율 처방의 baseline은 사용자가 직접 명시하며, 최근 중량·반복을 자동 e1RM/TM으로 바꾸지 않는다. 중량은 선택한 간격에 맞춰 처리하고 일정·결과를 보존한다.

구현 계약의 한계:

- 각 주의 세션 수가 같고 세션 순서가 연속된 유한 프로그램만 지원한다. 주차별 횟수가 다른 프로그램·AMRAP·단계 진급·무한 반복 주기는 아직 지원하지 않는다.
- 프로그램 중 운동·세트 구성은 앱이 재배분하지 않는다. `manual` 처방에는 목표 중량이 없고 수행 시 실제 중량을 입력한다.
- `PlanReviewScreen`에서 날짜별 운동·세트·개인화 목표 kg를 확인한 뒤 ‘이 일정으로 시작’에서 최종 저장한다. 확인 전에는 활성 루틴을 바꾸지 않는다.
- 미래 일정 변경의 도메인 메서드는 있으나 일정 변경 UI는 없다.
- 검색·습관은 기존 목업이며 자동 조절·e1RM 추세·트레이너 등록·계정·서버 동기화·구독은 미구현이다.

## 개선 기능 상세 문서화와 기능 분석

- 사용자 요청: **“그리고 문서들을 남기고, 그 기능들을 분석해”**.
- [9/7 기능 분석 정본](2026-09-07-feature-specification.md)과 프로그램·시작·검색, 운동 입력·요약·정정, 상태·날짜·일정·복원의 상세 문서 **4개**를 추가했다. 기존 연구의 IM01~15를 유지하고 각 기능의 현재 코드 차이, 정상 흐름, 논리 데이터, 빈/로딩/실패/취소/이탈, 선행 작업과 영향 파일, 수용 기준, 미결정 정책을 분석했다.
- 기능 간 공통 계약: 목표·지난값·초안·실제를 구별하고, 기존 계획/세션/세트 ID를 유지한다. 지난 값 복사나 기록 정정은 새 수행 완료가 아니며 타이머를 새로 시작하지 않는다. 예정일과 실제 수행일은 별개이고 옛 수행일 미상은 그대로 보존한다.
- 상태 분석: 필수 세트를 모두 제외해도 참이 되는 현재 `isSessionComplete`와 명시 마감·실제 수행 수를 분리했다. 필수 세트가 없는 세션의 마감 제안, 과거 마감 미상 기록의 정정 전이도 추가했다. 제안한 새 마감 기능은 아직 구현하지 않았다.
- 저장 분석: 설정 초안 취소가 이미 저장된 최근 리프트 기록을 삭제하지 않게 하고, 백업 복원은 쓰기 큐·늦은 콜백을 정리한 뒤 전체 후보를 검증·교체하는 별도 경계로 정의했다. 강제 종료 후 복원 범위는 마지막 영구 저장 성공분까지이며 실패한 최신 쓰기 복원을 보장하지 않는다.
- 개발 순서는 실제 콘텐츠/상태/네이티브 검증 → 식별·날짜와 기록 편의 → 일정·요약·백업으로 연결했다. IM14 최소 콘텐츠 확장의 조건부 선행과, IM06을 기다리지 않고 진행할 수 있는 다음 세트 이동·집계 문구 작업을 구분했다.
- 개요·경쟁 앱 종합 분석·Claude 인수인계에 읽기 경로를 연결했다. 확정된 사용자 요구, 현재 구현, 새 설계 제안, 미결정 제품 정책을 구별했다.
- 검증: 관련 8개 문서의 로컬 링크와 공백 형식, IM01~15의 상세 절이 각각 한 번씩 존재함을 확인했다. 문서 간 마감/정정/타이머/날짜/초안 계약을 교차 검토했고 `git diff --check`를 통과했다. 앱 코드·콘텐츠·사용자 저장 스키마를 변경하지 않았으므로 Flutter 테스트·시뮬레이터 검증은 다시 실행하지 않았다.

### F01 · 저장 성공 후 다음 세트와 닫기 재시도

- 기존 세트 완료를 유지하면서 ‘저장하고 다음 세트’를 추가했다. 원래 순서의 다음 미기록 세트로 이동하고 기존 다음 세트 초안을 복원한다. 완료/제외된 세트는 건너뛴다.
