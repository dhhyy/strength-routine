# 9/8 · 관리자 루틴 생성 기능

## 확정 요청과 구현 방식

사용자가 직접 생성 기능을 **관리자만** 사용하도록 요청했다. 트레이너는 운영자 1명이므로 회원별 트레이너 가입·심사·마켓플레이스는 만들지 않는다. 일반 사용자는 등록된 프로그램을 선택하고 중량·날짜·요일을 맞춘다.

서버 인증이 없는 현재 구조에서는 **별도 내부 빌드**를 기본으로 적용했다. 사용자에게 별도 빌드/서버 로그인 선택을 질문했으며 답변 전 추천안을 가정한 것이다. `lib/main.dart` 소비자 진입점의 import graph에는 관리자 코드가 없다. `lib/main_admin.dart`로 실행하는 도구를 운영자의 신뢰할 수 있는 Mac에서만 사용한다.

기본 macOS 제품명·번들 ID는 동일하므로 별도 설치 앱을 생성하는 방식은 아니다. 내부 빌드 뒤 사용자 배포물을 만들 때 반드시 `-t lib/main.dart`로 다시 빌드한다. 같은 출력 경로의 관리자 실행파일을 잘못 배포하지 않게 구분해 보관한다.

이것은 서버 관리자 계정 인증이 아니다. 내부 실행파일을 가진 사람은 사용할 수 있으므로 공개 배포하면 안 된다. 앱 속 비밀 탭·공유 PIN·로컬 관리자 스위치를 권한 확인처럼 사용하지 않는다. 원격 관리자 접근이 필요해지면 서버 인증·권한 검사·감사 로그가 선행돼야 한다.

## 실제 동작

1. 프로그램 ID·이름·버전·설명·기간을 입력한다.
2. 주간 세션을 추가하고 세션마다 운동을 입력한다.
3. 각 운동의 안정적인 ID·이름·메인 리프트 여부·세트·반복·RIR·중량 방식을 정한다.
4. 생성 요청 시 모든 필드를 검증하고 동일 주간 구성을 지정한 기간만큼 반복한다.
5. 생성된 모든 주차·세션·운동의 구성을 확인한다.
6. 확인 버튼을 눌러 관리자 로컬 카탈로그에 저장한다.
7. 카탈로그를 JSON 파일로 내보내고 사용자 앱 번들에 반영한다.

입력 중인 원문은 별도의 관리자 파일에 저장한다. 앱을 다시 열면 `3.` 같은 미완성 입력도 돌아오지만, 생성 시에는 올바른 정수가 필요하다. 파일을 읽지 못하면 빈 초안으로 덮어쓰지 않고 재시도를 표시한다. 저장 실패 시 입력/카탈로그는 화면에 남고 재시도할 수 있다.

## 생성 계약과 한계

| 입력 | 계약 |
|---|---|
| 프로그램·운동 ID | 영문 소문자/숫자/밑줄/하이픈, 1~80자; 같은 운동은 세션·주차에 걸쳐 같은 ID·이름·mainLift 유지 |
| 메타데이터 | 이름 1~80자, 버전 1~30자, 설명 1~2000자 |
| 기간·빈도 | 1~52주, 매주 같은 1~7개 세션; 사용자가 시작할 때 실제 요일 선택 |
| 운동·세트 | 세션당 1~20종목, 종목당 1~10세트, 세트당 1~100회; 같은 종목 내 모든 세트에 입력한 처방 적용 |
| RIR | 미지정 또는 0~10의 유한한 수 |
| 중량 | 운동 시 직접 입력 / 양수 고정 kg / 명시한 메인 리프트 기준 작업중량의 양수 비율 |
| 동일 프로그램 ID | 새 버전을 입력해야 관리자 카탈로그 교체 가능; 미리보기에서 교체를 알림 |

숫자 범위는 데이터/편집기 제한이며 권장 운동량이 아니다. 생성기는 목표에 맞는 세트나 강도를 추정하지 않는다. 전체 기간의 주간 패턴이 동일한 첫 버전이며, 주차마다 다른 구성·AMRAP·무한 주기·진급 엔진·자동 중량 증가를 만들지 않는다. 그런 프로그램은 정식 `TrainingProgram` JSON에서 개별 주차를 작성하고 검증해 수록해야 한다. 사용자 카탈로그의 서로 다른 5개 프로그램을 하나의 공통 루틴으로 바꾸지 않는다.

메인 리프트 지정은 사용자 시작 시 최근 기록을 요구하게 한다. 기준 비율은 1RM 자동 추정이 아니며 관리자는 프로그램 설명에 기준 중량의 뜻을 명시해야 한다.

## 저장과 사용자 반영

- 관리자 작업: 앱 지원 디렉터리의 `strength-admin/workspace.json`.
- 내보내기: 그 디렉터리 아래 `admin-export/programs.json`.
- 내보내는 형식: 소비자 번들과 같은 `schemaVersion: 1`, `programs` 목록.
- 첫 관리자 실행에서는 현재 번들 5개를 초기 카탈로그로 읽는다.
- 기존 관리자 작업 파일이 있으면 그 작업을 우선 복원한다.
- 내보내기는 온라인 게시가 아니며 사용자 기기의 계획을 직접 바꾸지 않는다.
- 소비자 카탈로그는 프로그램 전체 스냅샷을 시작할 때 저장하므로 번들 교체가 기존 계획을 다시 계산하지 않는다.

**운영자의 Mac 터미널, 앱 루트:**

```sh
flutter run -d macos -t lib/main_admin.dart
```

macOS 데스크톱 앱으로 실행하는 명령이며 iOS 시뮬레이터 명령이 아니다. 이번 작업에서는 실행하지 않고 위젯 렌더로 검증한다. 생성 후 내보내기 대화상자의 실제 경로에서 파일을 확인하고 `assets/programs.json`에 반영한다. 기존 파일을 무조건 복사하기 전 프로그램 수·ID·버전과 diff를 확인한다.

```sh
flutter test test/bundled_programs_test.dart --reporter expanded
flutter analyze
```

현재 번들 테스트는 승인된 첫 5개를 검증하므로 새 프로그램을 추가하면 테스트의 개수·기대 목록도 의도적으로 갱신한다. 이후 일반 진입점 `lib/main.dart`로 사용자 앱을 빌드한다. 관리자 진입점을 앱스토어 제출이나 사용자 설치 안내에 넣지 않는다.

## 확인 방법

- 빈 ID·기간 `3.`·소수 반복·동일 세션 중복 운동 ID로 생성하면 오류가 표시돼야 한다.
- 올바른 3주·주 2회 구성은 6세션으로 생성돼야 한다.
- 미리보기에서 뒤로 가면 원문이 유지되고 저장 버튼 전에는 카탈로그에 추가되지 않아야 한다.
- 저장 후 프로그램 수가 증가하고 같은 ID/같은 버전 재생성은 차단돼야 한다.
- 재실행 시 초안과 관리자 목록이 복원돼야 한다.
- 내보낸 JSON을 `TrainingProgram.fromJson`으로 읽고 사용자 계획을 생성할 수 있어야 한다.
- 일반 앱에서 관리자 메뉴가 없어야 하며 소비자 import graph 검증도 통과해야 한다.

자동 테스트: `test/admin_routine_test.dart`, `test/admin_screen_test.dart`. 실행 결과·렌더와 남은 한계는 [이번 기능 검증](2026-09-08-feature-verification.md)을 따른다. Flutter의 별도 실행 진입점/플랫폼 배포 구분은 [공식 배포 문서](https://docs.flutter.dev/deployment)와 함께 확인한다.
