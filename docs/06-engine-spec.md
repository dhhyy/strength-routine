## 2026-09-07 · 현재 코드가 수행하는 계산

현재 실행 경로는 **트레이너 프로그램을 보존한 채 시작 설정을 적용하는 순수 함수 `createActivePlan`**이다. 아래의 과거 자동 볼륨/디로딩 규칙은 현재 엔진이 실행하는 기능이 아니다. 코드는 [training_program.dart](../lib/domain/training_program.dart), 화면 연결과 검증 상태는 [9/7 인수인계](2026-09-07-claude-handoff.md)를 참조한다.

| 계약 | 구현 |
|---|---|
| 입력 프로그램 | ID·버전·작성자·기간·주차·세션 순서·운동·세트·반복·선택 RIR·필수 여부·중량 처방 |
| 지원 구조 | 유한 주차, 각 주 동일 세션 수, 주별 연속된 세션 순서. AMRAP·진급 단계·무한 반복 주기는 미지원 |
| 시작 입력 | 시작 날짜, 주당 세션 수에 맞는 중복 없는 요일, kg 간격, 필요한 메인 리프트 기준 중량. UI에서 필수 최근 기록도 입력/보관 |
| `manual` | 계산된 목표 중량은 null. 운동 시 사용자가 실제 중량을 기록 |
| `fixedKg` | 프로그램에 명시된 kg를 사용하고 선택한 중량 간격에 맞춰 반올림 |
| `percentOfBaseline` | 프로그램에 명시된 비율 × 사용자가 명시한 해당 리프트 기준 kg. 이후 중량 간격에 맞춰 반올림 |
| 일정 배치 | 시작일 이후 선택한 요일에 원작 세션 순서를 유지하며 날짜 배정 |
| 저장 결과 | 프로그램 전체 버전 스냅샷 + 기준값/출처 + 확정 날짜 + 계산된 세트 목표 kg. 복원 시 현재 날짜·새 원작 데이터로 재계산하지 않음 |
| 실제 기록 | 계획 세트 ID를 참조하는 완료/제외·실제 kg/lb·반복·선택 RIR·메모. 계획과 초안/수행 기록 분리 |
| 저장소 | 별도 JSON 스키마, 읽기/쓰기 직렬화, 임시 파일 write/flush 후 rename, 실패 시 입력 및 손상 원본 보존 |

이 처방 타입은 **기술 지원 범위**다. 특정 프로그램의 시작 비율·증량 폭·e1RM 공식을 승인한 기록이 아니다. 최근 반복 기록을 기준 최대치로 자동 추정하지 않으며 **baseline과 e1RM/TM을 동의어로 사용하지 않는다.** UI는 비율 처방에 필요한 프로그램 기준 중량을 별도로 입력받는다. D7은 여전히 미확정이다.

`PlanReviewScreen`에서 날짜별 운동·세트·개인화 목표 중량을 확인하고 최종 시작 버튼에서 저장한다. 미래 일정 변경의 도메인 메서드는 오늘/과거 날짜를 보존하지만 사용자 일정 편집 UI는 아직 없다. 정적 분석 및 전체 39개 테스트는 통과했다. iPhone QA 빌드·실행 후 Mac 잠금으로 렌더·조작 검증은 대기 중이다. 상세 결과는 작업 기록을 따른다.

I08 답변 **“공개 프로그램을 조사해 후보를 제안해줘”**에 따라 [공식 공개 후보 3개](../research/2026-09-07/program-candidates.md)를 조사했다. 원작은 서로 처방·주기·정체 처리 방식이 다르며 현재 지원 계약으로 손실 없이 표현되는지 채택 전에 검토해야 한다. 카탈로그는 아직 비어 있고, 원작 선정·앱 수록·배포는 미확정이다. QA 전용 합성 데이터로 동작을 검증한다.

### 2026-09-07 · 생성 입력 정책 추가

- 사용자 인터뷰 확정: 첫 생성은 **최근 기록이 입력된 메인 리프트부터** 지원한다.
- 기록이 없는 리프트의 시작 중량을 임의로 생성하지 않는다. 선택한 리프트에 기록이 빠진 경우 입력 검증에서 알리고, 기록 입력 또는 선택 변경으로 해결한다.
- 이 결정은 입력 자격에 관한 것으로, D7의 e1RM 공식·갱신 조건을 확정한 것은 아니다.
- 첫 마일스톤은 생성→기록→재실행 복원이며, 상세 결정과 검증은 [9/7 작업 문서](2026-09-07-work-log.md)에 남긴다.
- 추가 확정: 트레이너가 기간·요일·운동·세트를 포함한 **완성된 프로그램을 등록하고 사용자가 선택**한다. 엔진은 공통 4주 구성으로 모든 프로그램을 다시 만들지 않는다.
- 개인화 범위 확정: **운동·세트 구성은 유지하고 중량·시작일·운동요일을 맞춘다.** 아래 D3~D6의 프로그램 구성 변경 규칙은 첫 생성에 그대로 적용하지 않는다. 훈련 후 조절 기능은 별도 후속 결정 대상으로 유지한다.

## 기존 엔진 설계 기록을 읽는 분께

아래 §1~§8은 9/6까지의 엔진 설계·결정 이력이다. **현재 구현은 위 9/7 계약이 우선**한다. 아직 실행되지 않는 자동 조절 규칙의 목적·제안 수치를 구현 완료로 읽지 않는다.
- **§1~§4**: 원칙과 확정된 뼈대 (바뀔 일이 거의 없음)
- **§5**: 설계 중인 규칙 4개 (수치 미확정, 현재 실행 경로 미연결)
- **§6 결정 기록**: 각 선택에 대해 **고른 것 / 버린 대안 / 이유**를 남깁니다. 나중에 생각이 바뀌면 여기서 갱신합니다.

수치가 `제안`으로 표시된 것은 아직 확정 전이며, **임의로 만든 숫자를 사실처럼 쓰지 않습니다.**

## 1. 엔진이 하는 일 (한 문단)

사용자의 목표·우선순위·훈련 요일과 그동안의 **완료 기록(중량·반복·RIR)**을 입력받아, **오늘 무엇을 몇 세트·몇 kg·목표 RIR 몇으로 할지**를 계산해 내놓는다. 계산은 사람이 검토할 수 있는 **규칙과 공식**으로만 이루어지며(생성형 AI 아님), 같은 입력이면 항상 같은 결과가 나온다. 생성은 끝이 아니라 시작점으로, 기록이 쌓이면 엔진이 중량·볼륨을 **자동으로 조절**하고 그 이유를 한 줄로 설명한다.

## 2. 불변 원칙 (산문)

1. **결정론.** 같은 입력 → 같은 출력. 엔진은 UI와 분리된 **순수 함수**다. 모든 생성은 입력·엔진 버전·결과를 스냅샷으로 저장해 **재현**할 수 있다.
2. **규칙·계산식 기반.** 확률적 생성이 아니라, 사람이 읽고 검증할 수 있는 규칙의 집합이다.
3. **안전·회복이 발전을 이긴다.** 규칙끼리 충돌하면 항상 회복·부상 방지 쪽을 택한다 (§4).
4. **계속 늘어나도 안 무너진다.** 각 로직은 **독립된 규칙(Rule)**이다. 디테일 추가 = 규칙 하나 추가일 뿐, 기존 규칙은 건드리지 않는다 (§7). — 이는 UI의 "디자인 토큰" 원칙과 같은 처방이다: 단일 진실 공급원 + 격리된 조립 단위.
5. **항상 이유를 말한다.** 모든 자동 조절에는 사람이 이해할 한 줄 이유가 붙고, 추천은 **되돌릴 수 있다.**
6. **엔진은 제안하고, 사용자가 결정한다.** 자동 적용 항목과 사용자 승인 항목을 구분한다. 수동 편집을 막지 않되, 원칙에 어긋나면 **경고**한다.

## 3. 핵심 어휘 (확정)

| 용어 | 확정된 뜻 | 결정 |
|---|---|---|
| **볼륨(Volume)** | 부위별 **주간 hard set 수** (대략 RIR 0~3의 힘든 세트만 카운트) | **D1** |
| **정교함 수준** | **Lv1** — RIR + 주간 hard-set 볼륨 + 블록(축적→디로드) | **D2** |
| **강도(Intensity)** | working max 대비 % (목표 RIR로 역산 가능) | D5·D7 연동 |
| **Working Max (e1RM)** | 완료 기록으로 갱신되는 '살아있는' 최대 추정. 실제 1RM 판정이 아닌 **추세** | **D7 (논의 중)** |
| **국면(Phase)** | `축적(accumulation) → 강도/피킹(intensity) → 디로딩(deload)` | 명칭 확정 |
| **부위(Muscle group)** | 볼륨 상한을 매기는 단위 | **D6 (논의 중)** |
| **리프트 역할(Role)** | `MAIN_VOLUME`(메인 볼륨) / `TECH_MAINTAIN`(기술·유지) / `ACCESSORY`(보조) | 확정 |

## 4. 충돌 해소 — 우선순위 사다리 (D8 확정)

규칙이 서로 다른 방향을 가리키면 **위가 아래를 항상 이긴다.**

> **부상 방지 > 회복(피로 신호) > 볼륨 목표 > 강도 발전**

예: 로직3이 "무겁다, 낮춰라"(회복)라고 하고 블록 계획은 "증량"(강도 발전)이라면 → **낮춘다.**

## 5. 설계 중인 규칙 4개 · 현재 미구현

각 규칙 형식: **신호 → 조건 → 액션 → 이유(예시)**. 수치의 확정 상태는 §6 결정 기록 참조.

### 규칙 1 — 축적 상한 → 자동 디로딩 / 미니 피킹  *(D3)*
- **의도**: 무한 축적을 막고, 일정 주차 뒤엔 피로를 풀거나(디로딩) 국면을 전환(미니 피킹: 볼륨↓·강도↑)한다.
- **신호**: `accumulationWeeks` (현재 블록 내 연속 축적 주차)
- **조건**: `accumulationWeeks >= MAX_ACCUM` (제안 **3**)
- **액션**: 다음 주 `phase = DELOAD | MINI_PEAK` — 선택 기준은 목표에 따름 (제안: 근비대→디로딩 / 스트렝스·파워빌딩 & 잔여 블록 충분→미니 피킹)
- **이유 예**: "3주 연속 볼륨을 쌓았어요. 쌓인 피로를 풀기 위해 이번 주는 디로딩입니다."

### 규칙 2 — 스쿼트·데드 같은 날: 볼륨은 하나만  *(D4)*
- **의도**: 같은 날 배치는 허용하되 둘 다 고볼륨은 금지(척추기립근·후면사슬·신경계 = 공유 자원).
- **신호**: 한 세션에 스쿼트·데드가 둘 다 `MAIN_VOLUME`인가
- **조건**: 공존 AND 둘 다 메인 볼륨
- **액션**: 우선순위(1~3순위) 낮은 쪽을 `TECH_MAINTAIN`(저볼륨·소수 고강도)으로 강등. 벤치+OHP에도 동일 적용.
- **이유 예**: "오늘은 스쿼트가 메인이라 데드리프트는 가볍게 기술 유지로 둘게요."
- **엣지**: 사용자가 수동으로 둘 다 볼륨을 넣으면 → **경고 후 허용**(편집은 막지 않음).

### 규칙 3 — RIR 누적 과부하 → 하향 추천 + 이유  *(D5)*
- **의도**: 실제 RIR이 목표보다 지속적으로 낮으면(계획보다 무겁게) 감량을 **제안**한다.
- **신호**: 최근 `N` 세션의 대상 리프트 `목표RIR − 실제RIR`
- **조건**: `실제RIR ≤ 목표RIR − k` 가 `m`회 연속 (제안 `N=3, k=1, m=3`)
- **액션**: 감량 대상은 §6 D5에서 확정 (working max 재보정 / 목표 중량 / 볼륨 중 택)
- **이유 예**: "최근 3세션 RIR가 목표보다 낮았어요. 질 좋은 볼륨을 위해 기준 중량을 조금 낮출게요." (+되돌리기)
- **엣지**: 하루 컨디션 저하와 **추세**를 구분. 의료적 표현은 피한다.

### 규칙 4 — 주간 부위 볼륨 상한  *(D6)*
- **의도**: 부위별 주간 볼륨에 상한을 두고, 초과 시 낮은 우선순위 보조부터 줄이거나 대체한다.
- **신호**: 부위별 주간 세트 = Σ(메인 리프트의 부위 기여 + 보조 세트), 단위는 **hard set**(D1)
- **데이터 필요**: `부위 분류 체계` + `운동→부위 기여 매핑` + `부위별 상한 테이블` (D6)
- **조건**: `부위 주간세트 > 상한`
- **액션**: 낮은 우선순위 보조부터 세트↓ 또는 대체 제안
- **이유 예**: "이번 주 등 볼륨이 회복 범위를 넘어서, 바벨 로우 2세트를 줄였어요."
- **엣지**: 사용자가 추가한 보조는 완료 조건에서 제외, 경고만.

## 6. 결정 기록 (Decision Records)

> 형식: **선택 / 버린 대안 / 이유 / 상태.** 생각이 바뀌면 여기서 갱신한다.

### D1 · 볼륨의 정의 — ✅ 확정
- **선택**: **hard set** (대략 RIR 0~3의 힘든 세트만 카운트)
- **버린 대안**: (a) 총 세트 — 워밍업까지 세어 과대계산 (b) effective set — 가장 정교하나 계산·데이터 요구 큼
- **이유**: 현대 근비대 문헌의 표준이며, 이미 수집하는 RIR로 바로 판정 가능. effective set은 Lv2 확장 슬롯으로 보류.

### D2 · 참고엔진 정교함 채택 수준 — ✅ 확정
- **선택**: **Lv1** (RIR + 주간 hard-set 볼륨 + 블록). 단, **규칙 레지스트리**로 지어 Lv2를 규칙 추가만으로 확장 가능하게 한다.
- **버린 대안**: Lv2(recruitment router 개념·effective set 근사)는 지금이 아니라 확장, Lv3(이중 비용 모델)은 HRV·수면 입력이 필요해 MVP 범위 밖.
- **이유**: MVP를 단순·검증 가능하게 유지하면서, 정교화 경로를 아키텍처로 열어둠.

### D8 · 규칙 충돌 해소 — ✅ 확정
- **선택**: 우선순위 사다리 **부상 방지 > 회복 > 볼륨 목표 > 강도 발전**
- **버린 대안**: 규칙별 임의 우선순위(예측 불가), 발전 우선(과훈련 위험)

## 7. 아키텍처 — 규칙 레지스트리 (요약)

```
각 로직 = 독립 규칙(Rule) {
  id, version, priority,          // 재현성 · 충돌 우선순위
  signals(state) -> {}            // 입력 신호 수집
  guard(signals) -> bool          // 발동 조건
  action(ctx) -> Change           // 제안/변경 (자동 or 승인)
  reason(ctx) -> string           // 한 줄 이유 (필수)
}
엔진(state) = 신호 수집 → 규칙 평가(priority·충돌 해소)
            → 제안 → (자동적용 | 사용자 승인) → 스냅샷 저장
```

- **디테일 추가 = 규칙 하나 추가.** 기존 규칙은 격리되어 영향받지 않는다.
- Dart **순수 함수 패키지**로 두어 UI와 완전 분리, 테스트 용이.
