# 9/8 · 실제 확인·실기기 재실행 테스트 절차

> 상태: 실행 가능한 테스트 절차·합성 데이터 준비. 실제 iPhone/Android에서의 완료·강제 종료·복원은 **이번 작업에서 실행하지 않음**. 시뮬레이터 자동 실행 보류를 유지한다.

## 개발자의 자동 검사

현재 호스트는 macOS다. **[macOS 터미널 · 앱 루트]**에서 실행한다.

```sh
cd /Users/yudongheon/Documents/vibe-design/apps/strength_routine
flutter analyze
flutter test --concurrency=2 --reporter expanded
git diff --check
```

테스트 묶음별 원인 확인:

```sh
flutter test test/bundled_programs_test.dart --reporter expanded
flutter test test/admin_routine_test.dart test/admin_screen_test.dart --reporter expanded
flutter test test/training_insights_test.dart test/training_insights_screen_test.dart --reporter expanded
flutter test test/local_settings_store_test.dart test/settings_screen_test.dart test/settings_integration_test.dart --reporter expanded
flutter test test/device_qa_state_test.dart test/storage_schema_upgrade_test.dart test/load_adjustment_workout_test.dart --reporter expanded
```

파일명은 저장소의 최신 테스트 파일을 기준으로 한다. 단위 테스트 통과는 실제 OS가 프로세스를 종료한 뒤 화면이 복원된다는 증거가 아니다.

## 실기기 연결 준비

iPhone은 Mac의 Xcode에서 Apple 계정·서명 팀을 설정하고, 연결된 iPhone을 신뢰하며 개발자 모드를 활성화한다. 실제 기기를 선택한다. Apple 공식 절차: [실제 기기에서 앱 실행](https://developer.apple.com/documentation/Xcode/running-your-app-on-simulated-or-physical-devices), [릴리스 빌드 검사](https://developer.apple.com/documentation/xcode/testing-a-release-build).

**[macOS 터미널 · 실제 iPhone/Android를 USB 연결]**

```sh
flutter devices
```

출력에서 실제 연결 기기의 ID를 복사한다. 시뮬레이터 ID를 쓰지 않는다.

```sh
STRENGTH_DEVICE_ID='여기에 실제 기기 ID 입력'
flutter run --release -d "$STRENGTH_DEVICE_ID" -t tool/device_qa.dart
```

위 값은 예시 자리이며 실제 ID로 바꾼다. 코드 서명·SDK가 준비되지 않으면 먼저 그 오류를 해결한다. Android의 현재 release 설정은 debug 서명 구성이므로 스토어 배포 전 별도 릴리스 서명이 필요하다.

**[Windows PowerShell · 실제 Android]**에서도 Android SDK·USB 디버깅이 준비됐다면:

```powershell
flutter devices
$STRENGTH_DEVICE_ID = '여기에 실제 Android ID 입력'
flutter run --release -d $STRENGTH_DEVICE_ID -t tool/device_qa.dart
```

Windows에서 iPhone 앱을 직접 빌드하는 절차가 아니다. iPhone 빌드·서명은 Mac/Xcode에서 수행한다.

## QA 데이터가 일반 기록을 건드리지 않도록

`tool/device_qa.dart`는 **처음 파일이 없을 때만** 전용 데이터를 만든다. 과거 3회 완료 기록·오늘 세션·향후 2회가 있는 합성 프로그램이다. 수치는 UI 검증값이며 실제 운동을 권하는 처방이 아니다.

- 운동: `device-qa-v1-training.json`
- 습관: `device-qa-v1-habits.json`
- 설정: `device-qa-v1-training.json.settings.json`
- 일반 실행: `training-state.json`, `habits-state.json`, `app-settings.json`
- 관리자: `strength-admin/workspace.json`

재실행하면 저장된 날짜를 그대로 쓴다. **A·B는 최초 QA 데이터 생성 당일 완료한다.** 날짜가 바뀌어도 기록 탭에서 원래 세션을 조회할 수 있지만, 7일이 지나면 다음 미기록 세션이 비교 창에 포함되고 미래 세션 수도 줄어 B의 전제가 깨진다. 새 시험 자료가 필요하면 이전 복원 시험 결과를 먼저 남긴 뒤 운영자가 QA 파일만 백업/제거하고 별도 회차로 시작한다. **앱 전체 삭제나 일반 저장 파일 삭제를 복원 테스트 단계로 사용하지 않는다.** 손상 파일은 자동 초기화하지 않는다.

## 실제 조작 시나리오

따라 할 순서는 **D1~4 → A(중간에 C 초안 복원) → B(중간에 C 적용·되돌림 복원) → D5~7 → E**다. D5의 제안 숨김 확인은 B2에서, 이력 보존 확인은 B5 이후에 끼워 넣는다.

### A. 초안과 운동 완료

먼저 아래 D1~4의 단위 확인을 수행한다. 빈 세트를 사용하는 시험이므로 A 완료 이후에 수행하지 않는다. D4 종료 시 기본 단위를 kg로 돌려놓는다.

1. QA 앱의 오늘 화면에서 `저장·복원 검증 4`를 열고 1세트 단위가 kg인지 확인한다.
2. 1세트 중량에 `60.`을 입력하고 닫는다.
3. 다시 열어 마지막 소수점까지 같은 원문인지 확인한다.
   이 시점에 아래 C를 한 번 실행해 **작성 중 초안**의 OS 종료·복원을 먼저 확인한다. 복원된 1세트를 다시 열고 이어서 진행한다.
4. `60 kg`, 반복 `5`, RIR `1`을 입력하고 **`저장하고 다음 세트`**를 누른다.
5. 저장 성공 후 2세트로 이동하는지 확인한다.
6. 2세트를 제외해 실제 수행 1/제외 1인지 확인한다.
7. 제외한 2세트를 다시 편집해 `60 kg`, `5회`, RIR `1`로 완료한다.
8. 실제 수행 2/제외 0이고 모든 필수 세트 기록 안내가 표시되는지 확인한다.

RIR 제안까지 한 번에 확인하려면 마지막 상태는 두 세트 모두 완료/RIR 1이어야 한다. 제외나 RIR 누락 상태에서 제안이 보류되는 것은 정상이다.

### B. D5 감량 적용과 되돌리기

1. 기록 탭 → `기록 추세·중량 조절`로 이동한다.
2. 동일 QA 운동의 최근 3개 비교 가능 기록과 제안 이유를 확인한다.
3. `변경 내용 확인`을 눌러 향후 2세션의 각 세트가 `60 → 57.5 kg`인지 확인한다.
4. 취소하면 적용 이력이 생기지 않아야 한다.
5. 다시 확인하고 적용한다.
6. 오늘/과거 값은 60kg로 남고 미래 계획 상세에는 조정 목표 57.5kg가 표시돼야 한다.
7. 아래 C의 강제 종료·복원을 다시 수행하고 완료 기록과 적용 이력이 남는지 확인한다. 이 시점에는 작성 중 초안이 없는 것이 정상이다.
8. `조정 되돌리기`의 전/후 값을 확인하고 실행한다.
9. 향후 목표가 60kg로 돌아오고 되돌린 이력이 남아야 한다.
10. 다시 같은 근거로 중복 감량을 제안하지 않아야 한다.

오늘/과거가 됐거나 실제 기록/초안이 생긴 대상은 전체 되돌리기를 제한한다. 제한 이유가 보이면 값을 임의로 바꾸지 않는지 확인한다. 이는 일반적인 치료·부상 판정이 아닌 초기 제품 규칙이다.

### C. 실제 OS 종료·앱 재실행

이 절차는 A3의 초안 상태, B7의 조정 적용 상태, B9의 되돌린 상태에서 각각 실행한다. 단계별로 존재하는 상태만 대조하고 없는 초안이나 이력을 만들지 않는다.

1. 입력 시트를 닫은 운동 상세에서 `기기에 저장됨`을 확인한다. 기록 추세 화면에서 확인할 때의 문구는 `기기에 저장했어요`이며, 저장 중/실패 상태에서 성공으로 판정하지 않는다.
2. 프로그램 이름, 예정일, 현재 존재하는 세트별 실제 값/단위/RIR·작성 중 원문·적용/되돌림 상태, 기본 단위 설정을 캡처한다.
3. 앱을 백그라운드로 보낸다.
4. iPhone은 앱 전환기에서 해당 앱을 종료하고, Android는 앱 정보에서 강제 종료한다.
5. **삭제·재설치·데이터 지우기를 하지 않는다.**
6. 기기의 앱 아이콘을 눌러 다시 연다. 개발 도구의 hot reload/hot restart로 대신하지 않는다.
7. 종료 직전에 있던 계획·날짜·기록·초안·조정 이력·설정이 그대로인지 전 화면과 대조한다.
8. 네트워크를 끈 상태에서도 2~7을 반복해 로컬 저장 흐름을 확인한다.
9. A3에서 왔다면 A4부터 복원된 초안을 완료한다. 완료 후 이 절차를 한 번 더 실행해 초안이 완료 기록으로 바뀐 상태가 남는지 확인한다. B에서 왔다면 해당 B 단계로 돌아간다.

### D. 설정·도움말·구독 안내

**D1~4는 A 전에**, D5~7은 B 진행 중 또는 이후에 확인한다.

1. 기본값 kg 상태에서 오늘 1세트 중량에 `60.`만 입력하고 닫아 kg 초안을 만든다. 프로필 → 앱 설정에서 기본 단위를 lb로 저장한다.
2. 오늘의 **아직 열지 않은 2세트**를 열어 lb로 시작하는지 확인하고 값을 입력하지 않은 채 닫는다.
3. 1세트 초안은 `60.`/kg를 유지해야 한다. 과거 QA 완료 세션의 실제 값도 `60 kg` 그대로인지 확인한다. 숫자를 자동 환산하지 않아야 한다.
4. 프로필 → 프로그램 선택 → `바벨 기본 동작 · 주 3일` → `이 프로그램으로 시작` → 최근 기록 입력에서 새 입력의 lb 기본값을 확인한다. 저장·최종 `이 일정으로 시작`을 누르지 않고 취소/뒤로 돌아와 QA 계획을 유지한다. 앱 설정 기본 단위를 kg로 다시 저장한 후 A를 시작한다.
5. B2에서 감량 제안 표시를 끄고 기록 추세에 다시 진입하면 새 제안이 숨겨져야 한다. 다시 켜고 B를 진행한다. B5 이후에도 껐다 다시 진입해 기존 적용 이력/되돌리기는 남는지 확인한다.
6. 도움말 질문을 펼쳐 내용을 확인한다.
7. 구독 화면은 준비 상태를 표시하고 실제 구매 성공이나 유료 권한을 생성하지 않아야 한다.

결제 테스트는 상품·스토어 계정·검증 서버 연결 이후에만 별도 진행한다. [1인 구독 운영안](2026-09-08-subscription-operations.md)의 Sandbox/TestFlight/Play 라이선스 테스트 조건을 따른다.

### E. 일반 앱과 관리자

QA 이후 일반 사용자 흐름을 확인하려면 같은 기기에 `lib/main.dart`로 실행하고 프로그램 5개 목록부터 시작한다. QA 저장 파일을 읽지 않아야 한다. 관리자 생성 메뉴가 없어야 한다.

```sh
flutter run --release -d "$STRENGTH_DEVICE_ID" -t lib/main.dart
```

관리자 Mac 도구의 생성·내보내기는 [관리자 루틴 생성 문서](2026-09-08-admin-routine-builder.md)의 절차를 따른다. 내부 관리자 실행파일을 사용자에게 배포하지 않는다.
