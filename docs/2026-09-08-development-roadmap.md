# 2026-09-08 · 후속 기능 상세 개발 로드맵

**현재 상태 갱신:** [로컬 여섯 기능 완료 범위](2026-09-08-local-completion.md)가 아래 계획보다 최신이다. R01 운동백업/복원(전체앱백업 제외), R02 미래일정/놓친운동, R03이전실제값복사, R04사용자휴식/자동시작(OS알림 제외), R05반복범위·종류·일괄수정·보관·버전복구, R06운동24종목/용어9개를 구현했다. 아래 ‘최초 제안’·‘미결정’은 계획 수립 당시이며 실제 채택 정책은 위명세를 읽는다. R07~R10원격/계정/결제/문의와 실제기기확인은 별도다.


작성일: 2026-09-08, Asia/Seoul. 사용자 요청은 **남은 작업을 매우 상세하게 문서화하고 기능 구현을 시작하는 것**이다. 첫 단위인 실제 수행일·운동 마감·요약은 구현했으며 [명세](2026-09-08-session-lifecycle.md)와 [당시 검증·렌더·커밋 보고서](2026-09-08-session-lifecycle-verification.md)에 결과를 남겼다. 이후 “관리자가 세밀하게 편집할 수 있어야 한다”는 요청으로 **R05의 기존 프로그램 편집·복제·독립 주차·개별 세트 편집을 우선 구현했다**. R05의 통합 검증·정확한 완료 범위는 [정밀 편집 명세](2026-09-08-admin-precise-editor.md)를 따르며, 전체 테스트 189개 통과·정적 분석 문제 없음을 확인했다. 나머지 단위는 개발 계획이고 외부 서비스·운영 선택을 완료한 것으로 해석하지 않는다.

**최신 후속 작업:** 직전 미구현이라고 안내한 휴식·템포·슈퍼세트·AMRAP의 구현을 반영했다. 필드·관리자 편집·사용자 순서/기록·조건부 저장 형식과 최종 자동 검증은 [고급 처방 명세](2026-09-08-advanced-prescriptions.md)를 따른다. 189개는 그 이전 정밀 편집 단위의 결과로 보존한다. 이번 휴식은 처방이 있는 저장된 완료 세트에서 명시 시작하는 앱 내 타이머이며 **R04의 자동 시작/OS 알림이나 R01~R10 전체 완료가 아니다.**

## 3. 모든 단위에 적용할 개발 계약

1. **원본과 실제를 분리한다.** 시작 당시 프로그램·계획/세션/세트 ID·원래 목표를 보존한다. 새 카탈로그, 복사, 날짜 변경, 구독 권한이 실제값이나 원본 처방을 조용히 바꾸지 않는다.
2. **저장 성공과 화면 값은 다를 수 있다.** `TrainingController.update`는 메모리를 먼저 변경하고 실패 때 유지한다. 마지막 성공 저장 이후의 입력은 OS 종료 뒤 복원을 보장하지 않는다. 백업 교체·정정 확정처럼 이전 확정값을 지켜야 하는 동작은 일반 `update` 호출만으로 원자성을 확보했다고 설명하지 않는다.
3. **큐는 인스턴스별이다.** 운동·습관·설정·관리자·휴식 타이머는 각각 파일과 큐가 있다. 한 큐의 직렬화는 여러 인스턴스/프로세스 또는 여러 파일의 일괄 트랜잭션이 아니다. 공유 controller/store를 사용하고, 복원은 writer 진입 차단·큐 소진·세대 경계를 별도로 설계한다.
4. **날짜는 용도대로 보존한다.** 예정 달력 날짜, 확인한 수행 달력 날짜, 입력·수정 UTC 시각을 섞지 않는다. 실제 날짜 미상 데이터를 이행일/예정일/파일 수정일로 채우지 않는다. 첫 구현의 최종 이행 계약을 다음 기능의 출발점으로 삼는다.
5. **새 스키마는 묶어서 관리한다.** 고급 처방 사용 여부에 따라 **카탈로그 1/2·관리자 2/3·운동 3/4 쓰기**로 구분하며 이전 카탈로그 v1, 관리자 v1/v2, 운동 v1/v2/v3 읽기를 유지한다. 고급 필드를 구 envelope에 넣은 파일은 거절한다. 타이머 `.rest-timer.json`의 버전도 별개다. 이 실제 계약보다 뒤의 버전은 예약하지 않으며 미지원 미래 버전은 원본 보존·명시 오류가 기본이다.
6. **기능 상태는 분리한다.** 빈 데이터, 불러오는 중, 검증 실패, 기기 저장 실패, 원격 전송 실패, 취소, 오프라인을 0·완료·접수 성공으로 대체하지 않는다. 재시도에는 동일 동작 ID를 쓰고 중복 제출과 늦은 응답을 검증한다.
7. **사용자 권한과 운영자 권한을 분리한다.** 일반 앱의 공유 PIN·숨은 탭·로컬 bool을 관리자 권한으로 쓰지 않는다. 현재 내부 빌드는 배포 통제라는 구현 가정이며 서버 인증이 아니다. 운영자가 1명이어도 원격 쓰기는 인증·서버 권한 검사를 통과해야 한다.
8. **로컬 기록 접근을 보존한다.** 카탈로그 장애, 로그인 해제, 구독 만료·철회, 문의 실패가 기기의 기존 계획·실제·초안 열람을 막거나 삭제해서는 안 된다. 신규 유료 콘텐츠 접근과 이미 보유한 사용자 기록은 별도 정책이다.
9. **검증 결과는 층위를 나눈다.** 순수 로직 → 실제 임시 파일 왕복/실패 → 실제 화면 경로 위젯 테스트 → 작은 화면·큰 글자 headless 렌더를 수행한다. OS 파일 선택/공유·알림·스토어·실기기 프로세스 복원은 별도 실기 검증이다. 사용자 재요청 전 Simulator는 사용하지 않는다.
10. **커밋은 사용 가능한 기능 단위다.** 기능의 코드·의미 있는 테스트·정확한 문서·필요한 이행을 함께 검토한다. 아래 커밋 제목은 예정안이며 생성된 커밋이나 실행 결과가 아니다. 같은 도메인/저장 파일을 여러 단위가 동시에 무단 수정하지 않는다.

## R01 · 사용자 기록 백업·파일 복원

**목적·현재 코드.** 앱 삭제·기기 변경에 대비해 사용자가 명시적으로 기록을 옮길 수 있게 한다. [운동 저장소](../lib/data/local_training_store.dart)는 지원 파일을 다시 읽고 임시 파일 flush→rename으로 저장한다. [컨트롤러](../lib/app/training_controller.dart)는 자동 저장·재시도를 제공하지만 외부 파일 선택/공유, 복원 후보, writer 잠금은 없다. 관리자 JSON 내보내기는 소비자 기록 백업이 아니다.

**최초 범위 제안.** 먼저 화면 이름을 **운동 기록 백업**으로 제한해 `TrainingAppState` 전체를 왕복한다. 활성/보관 계획과 프로그램 스냅샷, 최근 리프트 입력, 실제·초안·메모, 완료 안내 이력, D5 이력 및 첫 구현에서 확정한 수행일·마감 데이터를 포함한다. 구조 일부를 복사해 백업이라고 부르지 않는다. 습관·앱 설정·관리자 작업·웹 체험·계정/결제 비밀은 이 첫 파일에 포함하지 않음을 내보내기와 복원 검토에 표시한다.

**비범위.** 자동 클라우드 동기화, 다른 앱 CSV 가져오기, ID 추정 병합은 제외한다. 분석 CSV는 별도 후속 내보내기이며 복원 파일로 광고하지 않는다. 전체 앱 백업 확장은 아래 다중 파일 조건을 해결한 뒤 별도 범위로 채택한다.

**정상 흐름 제안.**

1. 프로필→운동 기록 백업에서 포함/제외 범위와 마지막 저장 상태를 본다. 미저장 변경이 있으면 먼저 현재 저장 재시도를 해결하는 방안을 초기값으로 권고한다.
2. 일관된 revision의 복원 파일을 생성하고 파일 저장/공유 UI로 전달한다. OS가 실제 목적지 저장을 확인해 주지 않으면 ‘파일 생성/공유 열기’까지만 성공으로 표시한다.
3. 복원은 선택한 파일을 읽기 전용 후보로 검사한다. 계획·실제·초안·수행일 미상 수와 파일 범위, 현재 기록을 교체한다는 영향을 미리 본다.
4. 전체 교체 확인→기준 revision 재검사→새 쓰기 차단·기존 큐 소진→복구용 이전 스냅샷 확보→후보 기록·검증→파일 교체→새 상태 공개 순서로 적용한다. 자동 병합은 하지 않는다.
5. 완료 후 기록 화면과 새 저장소로 다시 읽은 상태가 일치한다. 복원 파일의 타이머가 나중에 추가돼도 소리/알림을 즉시 재생하지 않는다.

**데이터·이행 제안.** 백업 포맷 종류·버전, 내보낸 시각, 앱 데이터 버전, 포함 범위, payload, 무결성 확인값을 둔다. 무결성 확인값은 전송 손상 검사용이며 작성자 인증이나 암호화를 대신하지 않는다. 파일 크기/중첩/항목 수 제한, 중복 ID·고아 참조·단위·날짜·새 필드 검증을 적용한다. 이행은 원본 복사본에서 수행하고 구버전 fixture의 ID·목표·원문 초안·미상 날짜를 보존한다. 새 버전 필드를 모르는 앱의 축소 저장을 거부한다.

**취소·오프라인·실패·동시 쓰기.** 파일 선택/미리보기 취소는 메모리·현재 파일·가져온 원본에 변화가 없다. 로컬 파일은 오프라인 처리 가능하나 OS 클라우드 문서 공급자가 파일을 내려받지 못하면 선택 파일 오류로 표시한다. 디스크 부족/권한/rename 실패는 이전 상태와 후보를 유지한다. 복원 중 화면 자동 저장·설정과 무관한 운동 writer·지연 콜백이 후보를 덮지 않도록 세대 ID를 사용한다. 교체 직전/직후 종료를 주입해 이전본 또는 완전한 복원본만 읽히게 한다.

**전체 앱 백업 확장 조건.** 습관·설정까지 포함하면 `LocalHabitStore`, `LocalSettingsStore`, `LocalTrainingStore`의 독립 큐를 조정해야 한다. 세 파일에 차례로 rename하는 방식은 중간 종료 시 서로 다른 세대가 섞인다. 후보 세대 디렉터리+검증 후 단일 활성 세대 포인터 교체 또는 동등한 복구 저널을 검토하고 RootGate가 한 세대를 함께 읽도록 바꾼다. 그 전에는 ‘앱 전체 복원’이라고 표시하지 않는다.

**검증 기준.** ① 모든 포함 필드가 있는 구/신 버전 fixture→빈 대상 복원→새 controller에서 값·ID 동일. ② 손상/미래 버전/고아 참조/가져오기 취소→현재 파일 바이트와 메모리 불변. ③ 자동 저장을 지연시킨 상태에서 복원→오래된 큐가 복원본을 덮지 않음. ④ 교체 경계 실패·중복 적용→한 세대만 공개, 입력 손실 없음. ⑤ 공유 취소와 실제 목적지 저장 미확인은 ‘백업 보관 완료’로 오표시하지 않음.

**선행·결정 필요.** 첫 구현의 최종 스키마·미상 날짜 계약; 초기 포함 범위(운동만/전체 앱), 교체만 제공할지, 암호화/비밀번호 분실 정책, 복구본 유지 기간, OS별 파일 선택/공유 방식이 필요하다. 저장 오류 상황의 별도 비상 내보내기는 보류 중 메모리라는 표식과 완전한 검증을 갖추기 전 넣지 않는다. 파일 어댑터 의존성은 이 범위 확정 후 최소한으로 선택한다.

**예정 커밋·완료 판정.** `feat(backup): export versioned workout backup` → `feat(restore): review and atomically replace workout state`. 전체 앱 범위를 택하면 `feat(backup): coordinate multi-store generations`를 별도 단위로 둔다. 파일 생성만으로 완료 처리하지 않고 실제 새 저장소 복원·실패/경합 검증·UI 검토가 통과해야 로컬 기능 완료다. OS 공유/문서 선택 미검증은 출시 확인표에 남긴다. 근거: [IM12](feature-analysis/2026-09-07-data-reliability.md), [Strong CSV의 복원 제한](https://help.strongapp.io/article/235-export-workout-data), [FitNotes의 백업/CSV 구별](https://www.fitnotesapp.com/settings/).

## R02 · 놓친 운동 접근과 미래 일정 변경

**목적·현재 코드.** 운동을 못 한 날 이후에도 계획과 입력을 잃지 않게 한다. [ActiveTrainingPlan.rescheduleFuture](../lib/domain/training_program.dart)는 변경 전/후 날짜가 모두 `asOf`보다 미래인 이동만 허용한다. 전체 일정은 선택 요일·시작일 이상·세션 순서의 엄격 증가를 만족해야 한다. 현재 달력에서 지난 기록/초안을 열 수 있으나 날짜 이동 UI는 없다. `withActivePlan`은 새 계획 시작·보관용이므로 같은 ID의 일정 개정에 그대로 쓰지 않는다.

**범위·비범위 제안.** 놓친 운동은 원래 예정일 그대로 열고 첫 구현의 실제 수행일 입력을 사용한다. 최초 일정 편집은 활성 계획의 미래 세션만, 현재 선택 요일과 순서 제약 안에서 제공한다. 오늘/과거 이동, 세션 삭제·새 세트 생성, 같은 날 다중 세션, 주당 횟수 변경, 뒤 세션 자동 밀기, 보관 계획 이동은 별도 정책 전까지 제외한다.

**정상 흐름 제안.** 기록/오늘→대상 세션→예정일과 실제 기록 유무 확인→새 날짜 선택→이전/이후 날짜와 영향을 받는 세션 목록 검토→충돌 없을 때 적용→달력·다음 운동·D5 대상 표시 갱신. 조정 범위를 넓혀야 하는 경우에는 자동 재배치하지 않고 허용 범위를 설명한다. 취소는 선택한 날짜 후보만 버린다.

**데이터·이행 제안.** 같은 계획·세션·세트 ID를 유지하는 전용 개정 명령과 `baseRevision`, 이전/새 날짜, 변경 동작 ID·시각을 둔다. 최초 일정과 유효 일정을 구분하는 구조를 검토한다. 이전 파일은 저장된 날짜를 이행 기준 스냅샷으로 둘 수 있지만, 과거에 일정이 바뀐 적이 없다고 단정하거나 원래 생성일을 복원했다고 주장하지 않는다. 목표·실제·초안·D5 근거 스냅샷은 재생성하지 않는다.

**취소·오프라인·실패·동시 쓰기.** 오프라인에서 검토/적용 가능하다. 저장 실패 시 현재 적용본과 후보를 구분하고 입력을 유지한다. 후보 생성 뒤 실제/초안/마감/다른 일정 개정이 생기면 revision을 다시 검사해 영향 비교부터 갱신한다. 동일 동작 재시도는 이력 한 건이다. 삭제·새 계획 시작으로 경합을 회피하지 않는다. 화면 이탈 시 미적용 후보의 임시 보존 여부를 정하고, 최소한 취소 없이 적용되지는 않게 한다.

**D5 영향 확인.** 기존 D5는 미래 대상·근거 회차·적용일/되돌린 이력을 검사한다. 유효 일정 이동으로 대상이 오늘이 되거나 근거 순서/창이 바뀌어도 과거 조정 근거는 다시 쓰지 않는다. 첫 수행일 구현이 추세/D5에 미친 최종 계약을 확인하고, 오래된 제안 차단·새 제안 계산·undo 가능 여부를 함께 검증한다.

**검증 기준.** ① 허용 날짜 변경 후 새 controller에서 같은 ID·실제·초안·원목표/D5 이력 유지. ② 중복 날짜/순서 역전/비선택 요일/오늘 또는 과거 요청→원상 유지와 구체 오류. ③ 미리보기 뒤 기록/마감 발생→자동 덮어쓰기 없음. ④ 일정 변경·자정 경계 후 D5 적용/undo가 유효한 전체 대상에만 동작. ⑤ 놓친 세션을 오늘 기록해도 예정일은 바뀌지 않음.

**선행·결정 필요.** 첫 구현, 같은 계획 개정 API, 원일정 이력 범위가 선행이다. 단일 이동/뒤 전체 이동, 초안 있는 미래 세션 이동 허용, 요일 예외, 일정 undo, 마감된 세션 이동을 결정해야 한다. 초기 권고는 제약 안의 단일 이동이며 구성 변경으로 확대하지 않는다.

**예정 커밋·완료 판정.** `feat(schedule): preserve schedule revisions` → `feat(schedule): review and apply future date changes`. 달력 UI만 움직이는 단계는 미완료다. 재실행·경합·D5/초안 보호·작은 화면의 충돌 목록까지 확인해야 완료다. 근거: [IM09](feature-analysis/2026-09-07-data-reliability.md), [TrainHeroic 날짜 이동 안내](https://support.trainheroic.com/hc/en-us/articles/18156964554765-As-an-athlete-can-I-reschedule-my-training-sessions), [Trainerize 상대 일정과 실제 달력 구별](https://help.trainerize.com/hc/en-us/articles/115004404763-What-is-a-Phased-Program-and-How-to-Build-One). 경쟁 앱의 권한·자동 이동을 그대로 채택하지 않는다.

## R03 · 지난 실제 기록을 새 초안으로 가져오기

**목적·현재 코드.** 같은 값을 기억해서 다시 쓰는 부담을 줄인다. [SetEditor](../lib/workout_screen.dart)는 초안→기존 실제값→기본 단위 순서로 입력을 복원하고, 저장 성공 후 다음 미기록 세트 이동이 이미 있다. 지난 실제값 복사·증감은 없다. [현재 추세 식별](../lib/domain/training_insights.dart)은 같은 계획의 운동 ID·이름·mainLift 조합에 한정되고 글로벌 운동/장비/변형 ID는 없다.

**범위·비범위 제안.** 최초에는 같은 계획·동일 운동 의미·대응 가능한 세트의 실제 완료 기록을 출처와 함께 제공한다. 프로그램 간 자동 합치기, 이름 검색만으로 같은 운동 간주, 최근 리프트 기준값을 실제 세트처럼 복사하기, 목표 변경, 자동 완료, 과거 RIR/메모를 이번 실적으로 복사하기는 제외한다. 공통 종목 사전은 R06과 계약을 공유한다.

**정상 흐름 제안.** 세트 편집→목표/이번 초안/지난 실적 구분→수행일과 단위·중량·반복 확인→‘지난 중량·반복 사용’→현재 입력이 있으면 덮을 필드 확인→원중량·원단위·반복만 초안 적용→이번 수행 후 기존 완료/다음 세트 동작. 지난 RIR·메모는 읽기 전용 참고다. 이번 RIR·메모는 그대로 유지한다.

**데이터·이행 제안.** 출처 계획/세션/세트 ID·기록 revision·수행일 출처, 비교한 장비/변형/부하 의미, 가져온 필드, 사용자 수정 여부를 보존한다. 현재 초안은 원문 문자열 map이므로 새 메타데이터를 임의 문자열 키로 흩뿌리기보다 검증된 복사 출처 구조를 검토한다. 기존 초안은 출처 미상·기존 사용자 입력으로 읽어 보호한다. 실제 날짜 미상은 자동 ‘최근’ 정렬에서 제외하거나 날짜 미상 목록에서 사용자가 직접 고르게 하는 정책을 결정한다.

**숫자·단위 계약.** 0kg와 RIR 0은 유효하며 빈칸과 다르다. 단위만 바꾸는 기존 동작은 숫자를 보존한다. 환산을 제공하려면 별도 명시 동작과 원값 보존이 필요하다. 숫자 증감은 선택 후속이며 단위가 붙은 장비 간격이 확정되어야 한다. `incrementKg`를 lb 간격으로 그대로 사용하지 않고 `87.` 같은 미완성 초안을 임의 정규화하지 않는다.

**취소·오프라인·실패·동시 쓰기.** 로컬 이력은 오프라인으로 제공한다. 조회 지연/실패는 수동 입력을 막지 않는다. 늦은 결과로 입력을 채우지 않는다. 복사 취소는 초안 원문 유지; 저장 실패는 시트/대상 세트/값을 유지하고 다음 이동을 막는다. 같은 출처 반복 복사는 변화 없는 동작이어야 하며, 복사 뒤 사용자가 수정했으면 다시 확인한다. 이 보호는 저장 후 재열기에도 유지한다. 출처 정정은 이미 사용자가 복사한 대상 초안·실제값을 소급 변경하지 않는다.

**검증 기준.** ① 지난 80lb×5, RIR/메모 존재→중량·단위·반복만 복사하고 이번 RIR0/메모 유지, 실제 완료 수 변화 없음. ② 기존 초안→복사 취소/저장 실패/재열기→원문·보호 상태 유지. ③ 이름 동일·장비 다름/수행일 미상/세트 수 변경→자동 최근값 오선정 없음. ④ 늦은 조회·같은 출처 재복사·수정 후 재복사→사용자 입력 조용히 덮지 않음. ⑤ 완료 저장 성공에만 기존 다음 세트로 한 번 이동.

**선행·결정 필요.** 첫 구현의 수행일, 종목 동일성 확인 주체, 같은 날 복수 기록 순서, 세트 대응이 없을 때 선택 방식, 날짜 미상 수동 후보 허용, 환산/증감 간격을 결정한다. 자동 후보의 안전한 범위를 확보하지 못하면 수동 입력은 유지하고 가짜 지난값을 만들지 않는다.

**예정 커밋·완료 판정.** `feat(history): select compatible prior set records` → `feat(workout): copy prior values with draft protection`. 단순 텍스트 비교만이 아니라 출처·초안 보호·저장/다음 세트 회귀를 통과해야 완료다. 근거: [IM07](feature-analysis/2026-09-07-workout.md), [Hevy 이전값과 루틴값 구별](https://help.hevyapp.com/hc/en-us/articles/34105442929943-Previous-Workout-Values-Vs-Routine-Values-How-to-Adjust-in-Settings), [FitNotes 기록 비교](https://www.fitnotesapp.com/progress_tracking/).

## R04 · 명시 휴식 타이머 구현과 남은 자동 시작·OS 알림

**상태·범위.** [고급 처방 명세](2026-09-08-advanced-prescriptions.md)에 따라 `ProgramSet.restSeconds`를 추가하고, 휴식이 1초 이상 지정된 실제 완료 기록에서 사용자가 명시 시작하는 앱 내 타이머를 구현했다. 일시정지·재개·종료·한 개 타이머 교체 확인·파일 복원을 제공한다. 최종 자동 검증은 해당 명세에서 확인한다. 이 로드맵이 처음 제안했던 신규 완료 자동 시작·사용자 휴식 설정·OS 알림 전체를 완료한 것은 아니다.

**정상 흐름.** 세트 처방 확인 → 실제값 저장 성공 → 해당 세트의 휴식 시작 → 기존 실행/일시정지 타이머가 있으면 교체 확인 → 저장 성공 뒤 남은 시간 표시 → 일시정지/재개 또는 종료 순서다. 완료 기록을 저장했다고 자동 시작하지 않으며 다음 운동도 사용자가 직접 시작한다. 미지정과 명시적 0초는 구분하고 둘 다 타이머를 시작하지 않는다. 기본 시간이나 사용자 임의 시간을 추가하지 않는다.

**데이터·시계 계약.** 운동 파일 경로에 `.rest-timer.json`을 붙인 별도 파일에 한 타이머를 저장한다. 계획/세션/세트, 처방 시간, UTC 종료 시각 또는 일시정지 남은 밀리초, 출처 `sourceStamp`를 보관한다. 같은 종료 시각으로 복원하며 만료 후에는 0초를 표시하고 새 전체 시간을 시작하지 않는다. 시간대가 달라도 같은 UTC 종료 시각을 유지한다. 단조 시계 드리프트 탐지·시스템 시계 조작의 완전한 검출은 이번 구현이 아니다.

**출처와 마감/재개.** `sourceStamp`는 시작 당시 실제 기록 JSON과 세션의 마감/재개 사건 수를 포함한다. 현재 활성 계획의 같은 세트·같은 실제 기록·같은 처방인지 검증하며, 새 초안·실제 기록 수정·제외·마감·보관·계획 교체로 무효가 되면 타이머를 적용하지 않는다. 마감 후 다시 열어도 사건 수가 달라지므로 예전 타이머가 되살아나지 않는다. 별도 파일의 무효 타이머를 숨기고 재개 차단하는 방식이며 마감 사건과 타이머 파일 삭제를 한 트랜잭션으로 처리한 것은 아니다.

**취소·실패·경합.** 교체 확인 취소는 기존 타이머를 유지한다. 후보 저장 성공 뒤에만 타이머를 바꾸며 실패 재시도는 같은 후보를 사용한다. 타이머 저장 실패는 이미 저장한 실제 기록을 되돌리거나 다음 운동 기록을 막지 않는다. 실제 기록 저장 실패 상태에서는 그 미저장 완료로 휴식을 시작하지 않는다. 한 controller/store의 저장 큐와 busy 상태를 사용하며 여러 프로세스의 타이머 공동 편집은 지원하지 않는다.

**현재 검증 기준.** 양수 처방/완료/초안/마감/활성 계획 조건, 명시 시작과 중복 방지, 일시정지/재개, 교체 확인 취소, 저장 실패 후보 재시도, 만료 직전 일시정지, 새로운 controller에서 복원, 실제 기록/마감재개 사건/새 계획 변경 후 무효화를 확인한다. 긴 운동 목록의 하단에서 시작해도 타이머/실패 상태를 볼 수 있는지 렌더와 위젯 흐름으로 확인한다. 실제 OS 종료/잠금화면은 별도 실기 시험이다.

**후속으로 남는 결정과 구현.** 사용자 기본값·임의 시간·자동 시작을 도입할지, 신규 완료 동작 ID와 반복 저장의 구분, 기록/마감/타이머의 파일 간 원자성, 조절 간격, 단조 시계와 드리프트, 소리/진동·OS 권한·알림 예약/취소를 따로 정한다. 자동 시작을 도입한다면 초안/정정/제외/재개를 새 완료로 취급하지 않아야 하며, 백업 복원만으로 소리나 알림을 예약하지 않아야 한다.

**완료 판정.** 실제 기능 커밋과 자동 결과는 고급 처방 명세에 기록한다. 후속 `feat(rest): reconcile platform rest notifications`는 후보 제목이며 생성된 커밋이 아니다. 잠금화면/백그라운드 알림은 플랫폼 어댑터 회귀와 허용된 실제 기기 시험 전에는 완료로 표시하지 않는다. 기존 조사 근거: [IM08](feature-analysis/2026-09-07-workout.md), [Strong 휴식](https://help.strongapp.io/article/231-rest-timer), [FitNotes 시작 조건](https://www.fitnotesapp.com/workout_tools/).

## R05 · 운영자 주차별 프로그램 편집 — 로컬 정밀 편집 구현

**상태와 변경 이유.** 로드맵 최초 작성 때는 [RoutineBlueprint](../lib/admin/routine_builder.dart)의 한 주 반복 생성만 가능했다. 이후 [정밀 초안 모델](../lib/admin/detailed_routine.dart)과 [정밀 편집 화면](../lib/admin/detailed_routine_screen.dart)을 추가하고, [관리자 화면](../lib/admin/admin_screen.dart)에서 기존 카탈로그 편집·복제·새 작성·초안 이어서 흐름을 연결했다. 해당 단위 당시 통합 시험을 포함한 전체 189개가 통과했으며 근거와 커밋은 [당시 검증 기록](2026-09-08-admin-precise-editor.md#13-구현검증커밋-기록)에 남겼다. 새 고급 처방 검증과는 구분한다. 주차별 차이를 만들 수 없다는 이전 제한은 이제 기본 반복 생성기에만 적용한다.

**구현 범위.** 주차·세션을 선택하여 운동·세트를 추가·삭제·재정렬하고, 세트별 반복·RIR·필수/선택·수동/고정/비율 중량·기준 리프트를 편집한다. 후속으로 세트별 휴식·템포·AMRAP과 연속 운동의 슈퍼세트 그룹을 추가했고 사용자 표시/교차 이동/기록에 연결했다. 한 주를 깊은 복사해 추가하거나 다른 주차에 확인 후 덮어쓸 수 있다. 현재 편집 세션은 최대 50단계 실행 취소·재실행과 연속 텍스트 입력 묶음을 제공한다. 기존 프로그램의 ID·작성자·각 세트 처방과 원본 직렬화 순서를 보존한다. `mainLift`와 세트별 `load.lift`를 분리한다.

**실제 진입·정상 흐름.** 기존 항목의 `정밀 편집`으로 원본을 열거나 `복제해서 만들기`로 구성은 유지하고 프로그램 ID를 빈 값·버전을 `1`로 시작한다. 복제본은 새 ID를 입력해야 한다. `새 정밀 프로그램`과 `정밀 초안 이어서`도 제공한다. 기본 입력은 `주차·세트별로 편집`에서 검증을 통과한 경우에만 독립 주차로 펼친다. 편집 → `변경 검토` → 전체 구성·기존 ID 교체 여부 확인 → `검토한 프로그램 저장` → JSON 내보내기 → 사용자 번들 반영 순서다. 같은 ID·같은 버전의 확정 저장은 막는다.

**데이터·이행 계약.** [AdminWorkspace](../lib/admin/admin_program_store.dart)는 **관리자 v1/v2/v3 읽기, 고급 처방/고급 초안 입력이 있으면 v3·없으면 v2 쓰기**이며, 기존 `draft`와 nullable `detailedDraft`를 함께 보관한다. 이전 계획의 “기존 Blueprint를 펼쳐 이행” 표현은 **유효한 입력을 명시적으로 정밀 편집으로 여는 작업**에만 적용한다. v1 파일을 읽는 것만으로 `3.` 같은 미완성 기본 원문을 생성하거나 바꾸지 않는다. 정밀 초안의 원문·구조가 최종 유효 프로그램과 다를 수 있음을 허용하고 검토에서 오류를 처리한다. 소비자 카탈로그는 고급 처방 사용 시 2·미사용 시 1, 사용자 운동은 진행/보관 계획에 고급 처방이 있으면 v4·없으면 v3를 쓴다. 구 envelope에 고급 필드를 섞은 파일은 거절한다. 기본 5개 카탈로그나 이미 선택한 사용자 계획을 자동 개정하지 않는다.

**복사·취소·저장 경계.** 다른 구성을 열어 기존 정밀 초안을 바꿀 때 명시 확인하고 새 작업 파일 저장에 성공한 뒤 교체한다. 주차 덮어쓰기는 대상의 같은 순번 세션 ID를 유지하며 원본보다 세션이 부족하면 새 ID를 만들고 많으면 원본 개수로 교체한다. 원본 주차는 그대로다. 취소는 원문을 보존한다. 검토한 프로그램도 파일 성공 전 카탈로그 메모리를 교체하지 않는다. `_committing` 동안 기본 입력과 다른 변경을 막아 늦은 저장이 이전 카탈로그를 다시 덮지 않게 한다. 저장 실패는 원문·이전 확정 목록·검토 후보를 유지하고 재시도한다. 이는 단일 내부 앱 인스턴스의 보호이며 다중 창·프로세스 공동 편집을 구현한 것은 아니다.

**검증 기준.** 상세 명세 ME01~ME23에서 무손실 왕복, 한 세트 수정의 독립성, 주차 복사·덮어쓰기·ID, 입력 경계, undo/redo, v1 원문 보존, 저장 실패/재시도·동시 쓰기, 내보내기·새 계획 생성, 기존 사용자 계획/D5 보호, 좁은/넓은 화면·큰 글자·키보드 렌더와 일반 앱 접근 경계를 추적한다. 이전 기능의 테스트 통과 수를 정밀 편집의 결과로 재사용하지 않는다. 실제 내부 Mac 앱 종료·재실행과 사용자 기기 검증은 별도이며 시뮬레이터는 실행하지 않는다.

**남은 세밀한 제어.** 휴식·템포·슈퍼세트·AMRAP은 별도 고급 처방 단위로 연결했지만, 최종 프로그램은 여전히 매주 같은 1~7개 세션을 요구하며 초안의 일시적인 개수 차이는 검토에서 막는다. 반복 범위·워밍업 유형·드롭세트·대량 수치 조정·자동 진급·자동 디로딩은 후속이다. AMRAP의 실제 통계는 유지하되 D5 근거와 미래 감량 대상에서는 제외하며 AMRAP 성과 기반 진급 정책을 새로 추정하지 않는다. 전체 프로그램 복제는 구현했지만 카탈로그 삭제와 과거 게시 버전 복구는 남아 있다. 초기 5개 프로그램의 실제 내용 개정은 운영자의 콘텐츠 판단을 거쳐 별도 버전으로 저장한다.

**운영 경계와 후속 단위.** 내부 빌드는 운영자 보유물이며 공유 PIN·숨은 탭을 권한으로 추가하지 않는다. 관리자 서버 로그인·게시·예약·게시 취소·사용자 자동 반영은 R07의 인증·배포 계약이 필요하다. 이 기능을 원격 운영 완료로 판정하지 않는다. 이번 실제 커밋은 최종 검증 기록으로 확인하며 로드맵 초안의 후보 커밋명을 생성된 이력으로 취급하지 않는다. 근거: [정밀 편집 명세](2026-09-08-admin-precise-editor.md), [관리자 진입·기본 생성](2026-09-08-admin-routine-builder.md), [IM14](feature-analysis/2026-09-07-programs.md). 기존 [Liftoscript 사례](https://www.liftosaur.com/doc/liftoscript)는 다른 표현 방식의 조사 근거이며 범용 스크립트 엔진을 이번에 도입했다는 뜻이 아니다.

## R06 · 공통 운동 사전과 수행 가이드

**목적·현재 코드.** 사용자가 기록 맥락에서 운동 방법과 장비 의미를 확인한다. [검색 화면](../lib/search_screen.dart)은 번들/활성/보관 프로그램의 실제 운동 발생 항목을 검색하고 해당 세트 구성을 보여준다. 고정 가짜 검색 화면을 다시 개발하는 작업이 아니다. `ProgramExercise`에 공통 사전 ID·가이드·장비/변형 구조는 없다.

**범위·비범위 제안.** 현재 수록 운동부터 검토한 짧은 텍스트·장비/변형·부하 의미·별칭과 선택 영상 링크를 제공한다. 공통 설명과 프로그램 전용 지시를 분리한다. 인터넷 운동 설명 자동 수집·저작물 복제, 진단·개별 처방, 자동 운동 교체, 코치 채팅은 제외한다. 영상 없이도 기록과 텍스트 설명은 작동한다.

**정상 흐름 제안.** 이름/별칭/장비로 검색→구분된 종목 선택→검토된 설명과 출처 확인. 운동 기록에서는 해당 종목의 설명을 열고 닫아 같은 초안·대상 세트·스크롤 위치로 돌아온다. 외부 영상은 외부 이동임을 표시하고 사용자가 누른 경우에만 연다.

**데이터·이행 제안.** 공통 종목 ID, 표시명·별칭·장비/변형·부하 의미, 안내 제공 상태를 둔다. 가이드에는 버전·작성/검토 주체·검토일·출처·매체 사용 근거가 필요하다. 기존 프로그램 경로 ID는 유지하고 새 참조를 추가한다. 이름이 같다는 이유만으로 기존 계획을 자동 매핑하지 않는다. 미매핑은 유효 상태이며 이름·원래 구성 열람을 유지한다. 과거 프로그램 스냅샷의 지시와 최신 공통 가이드 버전을 각각 표시할 방식을 정한다.

**취소·오프라인·실패·동시 쓰기.** 로컬 텍스트는 오프라인 열람한다. 사전 없음/검색 0건/가이드 미제공/매체 실패를 구별한다. 설명 열기 전 초안 저장이 실패해도 입력을 버리지 않고 화면에 머물며 재시도/닫기를 제공한다. 가이드 조회가 늦게 돌아와 다른 종목 설명을 끼워 넣지 않도록 대상·버전을 확인한다. 외부 링크 복귀는 세트 완료나 타이머 재시작으로 취급하지 않는다. 사전 갱신은 검증된 한 버전으로 교체한다.

**검증 기준.** ① 같은 이름 계열·다른 장비 검색→다른 종목으로 표시, 기록 합치기 없음. ② 미완성 초안/단위/RIR0 입력→가이드 열기·닫기→원문 동일. ③ 외부 매체 실패/오프라인/미매핑→기록 계속 가능. ④ 구 사전 버전/프로그램 스냅샷→새 사전→원래 처방 불변. ⑤ 문구·작은 화면·큰 글자·읽기 순서와 링크 명칭 확인.

**선행·결정 필요.** R03과 공유할 식별 정의, 초기 수록 범위, 설명 작성·검토 책임, 영상 권리/호스팅 방식, 공통 안내 업데이트 정책이 필요하다. 공통 사전의 추가가 자동으로 프로그램 간 비교를 허용하지 않으며 그 범위는 별도 검증한다.

**예정 커밋·완료 판정.** `feat(exercises): add reviewed exercise definitions` → `feat(guides): open contextual guides without losing drafts`. 사전 모델만으로 완료하지 않는다. 최소 확정된 운동 범위에서 검색·기록 양쪽 진입, 누락/실패, 출처·권리 기록, 초안 보존까지 확인한다. 근거: [IM11](feature-analysis/2026-09-07-programs.md), [플랜핏 가이드 구조](https://planfit.ai/ko/exercise), [Caliber 운동 앱 안내](https://caliberstrong.com/workout-app/). 기존 조사 참고이며 이번에 해당 페이지를 다시 열거나 매체를 가져오지 않았다.

## R07 · 선택적 원격 카탈로그와 운영자 게시

**목적·현재 코드.** 필요할 때 앱 재빌드 없이 운영자가 콘텐츠를 배포한다. [loadBundledPrograms](../lib/app/training_controller.dart)는 `assets/programs.json`을 검증하며 ProgramLoader를 주입할 수 있다. 관리자는 로컬 카탈로그를 파일로 내보낸다. 실제 원격 URL·쓰기 서버·관리자 로그인·캐시 갱신은 없다.

**범위·비범위 제안.** 먼저 읽기 전용 원격 카탈로그+마지막 정상 캐시+번들 fallback을 구현하고, 게시 도구는 인증된 1인 운영자 경로로 분리한다. 사용자 운동 업로드·계정 강제·다중 트레이너 마켓플레이스·원격 임의 코드 실행은 제외한다. 원격 필요성이 없으면 기존 번들 배포를 계속 사용한다.

**정상 흐름 제안.** 운영자 작성→전체 데이터 검증→변경 목록/버전 검토→원격 후보 저장→게시 포인터 확정. 사용자는 캐시로 목록을 열고 갱신 결과를 확인한다. 새로 시작하는 프로그램만 선택 버전을 스냅샷으로 저장하며 기존 활성/보관 계획은 바꾸지 않는다. 서비스에서 내려간 프로그램도 보유한 계획·기록에서는 계속 열린다.

**데이터·이행 제안.** 카탈로그 revision, 스키마/지원 능력, 프로그램 ID+버전, 콘텐츠 해시·게시 시각·이전 revision·게시 동작 ID를 검토한다. 같은 ID/버전에 다른 본문이 나타나면 조용히 교체하지 않고 검증 오류로 취급한다. 캐시는 검증 완료 후 교체하고, ETag 같은 전송 최적화가 콘텐츠 검증을 대신하지 않게 한다. 소비자 기록 파일과 캐시를 분리하며 인증 토큰·관리자 비밀을 JSON에 넣지 않는다.

**취소·오프라인·실패·동시 쓰기.** 게시 확인 취소는 공개본 불변이다. 오프라인/서버 장애는 마지막 정상 캐시·번들에 대한 출처/갱신 상태를 표시한다. 손상·미지원 타입은 현재 캐시를 보존한다. 동시 게시에는 예상 revision 비교를 사용하고 최신 게시본을 덮지 않는다. 중복 게시 재시도는 한 revision이다. 사용자 갱신 응답 순서 역전은 이전 버전 재활성화를 막는다. 운영자 게시 권한과 공개 읽기 권한을 서버에서 분리한다.

**검증 기준.** ① 캐시/원격 최신/오프라인/미지원 버전→유효 목록만 표시. ② 동일 ID+버전 본문 충돌→거부. ③ 새 버전 게시·철회→기존 계획/기록 원본 불변. ④ 인증 없는 게시·공유 PIN 시도→서버 거부. ⑤ 동시/중복 게시·늦은 읽기 응답→버전 역행 없음. 게시 실패에서 성공 공지가 나가지 않아야 한다.

**선행·결정 필요.** 원격 운영 채택, 호스팅·도메인·운영 계정, 관리자 인증/복구 방식, 승인·롤백 절차, 프로그램 철회 안내·캐시 정책을 정해야 한다. 읽기 공개 여부와 유료 콘텐츠 다운로드 권한은 R09와 함께 결정한다. 무료 공개 카탈로그 단계에 불필요한 소비자 계정을 선행 강제하지 않는다.

**예정 커밋·완료 판정.** `feat(catalog): load validated remote revisions with local fallback` → `feat(admin): publish catalog with server authorization`. 첫 단위는 로컬 시험 서버/어댑터 회귀로 확인하고, 공개 운영 완료는 실제 설정·권한·게시/롤백 시험 후 별도로 판정한다. 현재 로드맵 작성은 서버 도입·외부 게시 승인이 아니다. 근거: [관리자 배포 경계](2026-09-08-admin-routine-builder.md), [프로그램 버전/스냅샷 분석](feature-analysis/2026-09-07-programs.md).

## R08 · 선택적 계정과 여러 기기 동기화

**목적·현재 코드.** 사용자가 원할 때 계정을 연결하고 다른 기기에서 기록을 계속한다. 현재 계정 모델·인증·동기화 서비스는 없고 파일은 기기 로컬이다. 파일 백업은 사용자 주도 이동이며 자동 동기화와 다른 기능이다. ProgramLoader 주입이나 구독 안내를 계정 기능으로 해석하지 않는다.

**범위·비범위 제안.** 계정 연결과 기록 동기화는 두 단계로 분리한다. 구독 거래 연결만 필요하면 운동 업로드를 자동 포함하지 않는다. 동기화를 채택할 때만 명시 동의 후 승인된 데이터 범위를 업로드한다. 소셜 피드·친구·트레이너별 회원 관리·원격 원문 수집은 제외한다.

**정상 흐름 제안.** 게스트 로컬 사용→계정 연결 이유/전송 범위 확인→인증→로컬과 계정 데이터 비교→선택한 복사/병합 정책 검토→첫 동기화→기기별 최신/대기/충돌 표시. 로그아웃 후에도 보유 로컬 기록을 열고, 다른 계정 연결 전에 현재 로컬 데이터의 소유/계정 범위를 분명하게 확인한다.

**데이터·이행 제안.** 안정적 사용자 ID, 데이터 집합 ID, 기기 식별, 항목 ID·revision, 서버 승인 버전, 중복 방지 operationId, 변경 큐, 삭제 tombstone이 필요하다. 기기 시각만으로 충돌 승자를 고르지 않는다. 기존 게스트 기록은 계정 미연결 상태로 이행하고 로그인 직후 자동으로 다른 계정 데이터에 붙이지 않는다. 토큰은 플랫폼 보안 저장소 등 별도 저장 대상이며 운동 백업에 넣지 않는다. 원본 프로그램 스냅샷/실제/초안/마감/D5 관계를 한 동기화 단위로 검증한다.

**취소·오프라인·실패·동시 쓰기.** 로그인/연결 취소는 로컬 데이터 불변이다. 인증 서버 장애가 로컬 입력을 막지 않는다. 오프라인 변경은 로컬 영구 저장 후 대기 상태로 남기고 서버 전송 성공과 구분한다. 동일 세트의 두 기기 수정은 무조건 최근 시각 덮어쓰기가 아니라 충돌 비교로 해결한다. 삭제 대 정정, 일정 대 수행, D5 적용 대 실제 입력, 마감 대 초안 경합을 정의한다. 재시도는 같은 동작 ID이며 계정 전환 뒤 늦은 응답을 새 계정에 반영하지 않는다.

**검증 기준.** ① 게스트→계정 연결 취소/실패→기록 동일. ② 오프라인 실제/초안 저장→재연결→서버 한 번 반영. ③ 두 기기 같은 세트·삭제/정정·일정/D5 충돌→숨은 데이터 손실 없음. ④ 로그아웃·다른 계정·토큰 만료→다른 사용자의 자료 노출/합치기 없음, 로컬 접근 유지. ⑤ 백업에 인증 비밀이 포함되지 않고 동기화 삭제/복원 이력이 일관됨.

**선행·결정 필요.** 계정 도입의 실제 목적, 로그인 수단·복구/탈퇴, 업로드 범위·보유 기간, 기기 간 충돌/병합, 로그아웃 후 기기 보관·명시 삭제, 운영 접근 권한을 정한다. R01 백업은 선행 보호 수단으로 권고한다. 계정 삭제와 스토어 구독 해지/거래 보존은 같은 동작으로 만들지 않는다. 해당 법률·스토어 정책은 실제 도입 시 다시 확인한다.

**예정 커밋·완료 판정.** `feat(account): link optional identity without moving local data` → `feat(sync): reconcile offline workout operations`. 로그인 성공만으로 동기화 완료를 선언하지 않는다. 두 독립 저장소/기기 역할의 충돌·복원·오프라인 시험과 운영 보안 검토가 통과해야 해당 범위를 완료로 적는다. 이번에는 인증 공급자/API/계정에 접근하지 않는다. 근거: [IM12의 백업 경계](feature-analysis/2026-09-07-data-reliability.md), [구독 권한과 기록 업로드 구별](2026-09-08-subscription-operations.md).

## R09 · 실제 구독과 콘텐츠 권한

**목적·현재 코드.** 1인이 지속 제공할 수 있는 프로그램/설명의 가치를 실제 상품과 연결한다. [SubscriptionScreen](../lib/subscription_screen.dart)은 현재 구매 불가·기록 열람 유지 안내만 제공한다. `AppSettings`에 가짜 premium 플래그가 없고 결제 SDK·상품·검증 서버·복원 동작은 없다. [기존 운영안](2026-09-08-subscription-operations.md)이 상세 기준이다.

**범위·비범위 제안.** 확정한 혜택에 대해 스토어 상품 조회, 사용자 구매, 서버 검증 권한, 기존 구매 재조회, 구독 관리 진입, 갱신/해지/유예/만료/철회를 구현한다. 월간/연간·가격·무료 체험·업데이트 개수는 아직 미정이다. 개인별 무제한 상담, 다중 트레이너 정산, 로컬 버튼으로 유료 전환, 별도 근거 없는 지역 외부 결제 예외는 제외한다.

**정상 흐름 제안.** 혜택/갱신 조건/스토어의 지역화 가격 확인→구매→대기/사용자 취소/검증 중 구분→검증된 권한만 활성→관리/기존 구매 확인 제공. 만료·철회는 신규 유료 콘텐츠 접근에 반영하되 기기에 남은 계획·실제·초안 열람은 계속한다. 권한 서버 도입이 기록 업로드 동의가 되지 않는다.

**데이터·이행 제안.** 스토어·환경·상품·거래 식별자, 검증한 사용자 연결, 상태·만료·검증 시각, 중복 처리한 이벤트 ID를 서버 권한 근거로 관리한다. 서명 거래/구매 토큰은 검증 경로에서만 다루고 로그·운동 백업에 노출하지 않는다. 기존 설치는 구매 미확인/구매 없음으로 시작하며 기존 기록을 잠그지 않는다. 동일 스토어 구매 재조회와 iOS↔Android 권한 공유를 구분한다. 후자는 계정 연결 정책을 먼저 확정한다.

**취소·오프라인·실패·동시 쓰기.** 구매 취소는 성공/오류 청구로 오표시하지 않는다. 상품 조회 실패는 구매를 막고 재시도한다. 결제 대기/서버 확인 실패는 신규 권한을 임의 발급하지 않는다. 오프라인 유료 사용 범위는 마지막 검증 권한과 명시 정책에 따르고 무기한 연장하지 않는다. 중복/순서 역전 알림은 스토어 최신 상태 재조회로 조정한다. 환불 요청과 승인·철회는 분리한다. 만료/권한 서버 장애 중에도 로컬 기록 열람과 백업은 구독 결제에 종속시키지 않는다.

**검증 기준.** ① 상품 실패/대기/취소→가짜 가격·구독 성공 없음. ② 정상 구매→종료→기존 구매 재조회→한 권한·중복 청구 없음. ③ 갱신 해제/유예/보류/만료/철회→플랫폼 상태와 접근 일치. ④ 지연/중복/다른 환경·다른 계정 거래→잘못된 권한 없음. ⑤ 만료·서버 장애→기존 기록·초안·계획 열람/백업 유지. 스토어 Sandbox/license tester 시험 결과를 로컬 mock 테스트와 따로 기록한다.

**선행·결정 필요.** 최초 콘텐츠·제공 주기·무료/유료 경계, 이미 시작한 유료 프로그램의 만료 후 편집 범위, 월/년 상품·가격, 지원 국가·스토어 계정/계약·앱 ID, 권한 연결/복구, 이용/개인정보 안내·문의 채널이 필요하다. 현재 스토어 상품/계정 접근 정보는 제공되지 않아 실제 결제 완료를 약속할 수 없다. 계정이 반드시 필요한지 거래 연결 대안을 검토하되 사용자 데이터 동기화를 묶어 강요하지 않는다.

**예정 커밋·완료 판정.** `feat(billing): display store products and pending purchase states` → `feat(entitlements): verify and reconcile subscription access` → `feat(billing): restore purchases and expose management`. 실제 상품·비과금 시험 환경에서 수명주기·실패 행렬을 통과하기 전에는 ‘구독 구현 완료/판매 가능’으로 표시하지 않는다. 결제 테스트와 공개 판매는 별도 단계이며 이번 작업은 돈을 받거나 상품을 생성하지 않는다. 기존 공식 근거: [Apple 구독](https://developer.apple.com/app-store/subscriptions/), [StoreKit 2](https://developer.apple.com/storekit/), [Google 구매 보안](https://developer.android.com/google/play/billing/security), [Google 구독 수명주기](https://developer.android.com/google/play/billing/lifecycle/subscriptions). 최신 정책 재확인은 연결 시 수행한다.

## R10 · 로컬 FAQ에서 실제 문의 접수로 확장

**목적·현재 코드.** 사용자가 해결하지 못한 제품 문제를 접수하고 운영 상태를 확인하게 한다. [SupportScreen](../lib/support_screen.dart)은 앱에 포함된 FAQ 6개를 펼쳐 읽는 화면이며 질문을 저장·전송하거나 운영자가 답하지 않는다. 현재 ‘보내기’나 접수 성공 화면이 없는 것은 사실에 맞는 상태다.

**범위·비범위 제안.** 1인 운영 가능한 비동기 문의부터 검토한다. 유형·내용·답변 받을 채널, 사용자가 동의한 최소 진단 정보, 접수 상태를 제공한다. 실시간 채팅·무제한 개인 코칭·자동 의료 상담·사용자 기록 전체 첨부·커뮤니티는 제외한다. 외부 이메일 작성기로 연결하는 최소 방식과 앱 내 접수 서버 방식 중 하나를 명확히 정한다.

**정상 흐름 제안.** FAQ 검색/열람→해결 안 된 유형 선택→초안 작성→전송할 항목 확인→사용자가 전송→서버 수신 확인이 있는 경우만 접수번호/상태 표시→운영자의 답변 가능 시간 안내→답변/해결 상태 확인. 이메일 앱을 열기만 한 경우에는 ‘메일 작성 화면 열기’로 표시하고 접수 완료를 주장하지 않는다.

**데이터·이행 제안.** 로컬 초안 ID, 유형·본문·선택 연락처, 동의한 첨부 목록, 작성 revision, 전송 operationId, 서버 접수 ID·상태·답변 시각을 구분한다. 기본 FAQ는 오프라인 자산으로 유지한다. 기존 운동/설정 스키마에 문의 본문을 끼워 넣지 말고 별도 저장 범위를 검토한다. 문의/첨부의 보관·삭제 정책과 백업 포함 여부를 명시한다. 비밀번호·구매 토큰·전체 운동 원문은 자동 첨부하지 않는다.

**취소·오프라인·실패·동시 쓰기.** 작성 취소는 전송하지 않고 초안 보존/폐기 선택을 제공한다. 오프라인은 로컬 초안으로 유지하며 서버 접수 전 완료로 표시하지 않는다. 명시 전송 후 재시도 큐를 둘지 결정하고, 자동 재전송 조건을 사용자에게 알린다. 응답 유실은 동일 operationId로 중복 접수를 막는다. 전송된 본문과 그 뒤 수정한 새 초안을 구분하고 늦은 응답이 새 입력을 지우지 않게 한다. 문의 실패가 운동 기록 화면을 막지 않는다.

**검증 기준.** ① 초안→화면 이탈/재실행/취소→정한 보존 정책과 일치, 미전송 유지. ② 오프라인/서버 5xx/응답 유실→초안 유지·중복 접수 없음. ③ 외부 이메일 열기→접수 성공 오표시 없음. ④ 사용자가 선택하지 않은 기록·토큰·연락처가 payload에 없음. ⑤ 답변 상태 갱신/다른 계정/삭제 요청 경계에서 다른 문의 노출 없음. FAQ는 접수 채널 장애에도 열린다.

**선행·결정 필요.** 운영 채널·지원 주소, 문의 유형, 답변 가능 시간·처리 범위, 담당자 1명의 휴무/장애 공지, 연락처 필요 여부, 개인정보/첨부 보유·삭제, 악용 방지 기준을 정한다. 운영자가 실제로 답할 수 없는 시간이나 개인별 훈련 효과를 구독 혜택으로 약속하지 않는다. 이메일 경로라면 답변 상태 추적은 미지원임을 표시한다.

**예정 커밋·완료 판정.** `feat(support): preserve local inquiry drafts` → 선택 경로에 따라 `feat(support): open an explicit external contact channel` 또는 `feat(support): submit idempotent support requests`. 폼만 생긴 단계는 접수 완료 기능이 아니다. 지정 채널의 실제 수신/답변 확인, 실패·중복·동의 범위 검증과 운영 안내가 갖춰져야 해당 범위를 완료로 적는다. 이번에는 외부 문의를 보내지 않는다. 근거: [1인 구독·지원 운영안](2026-09-08-subscription-operations.md), [기존 국내 서비스 조사](../research/2026-09-07/expanded/korean-apps.md). 경쟁 서비스의 상담 범위를 우리 운영 약속으로 복사하지 않는다.

## 5. 단위 시작·종료 시 남길 문서와 증거

각 단위 시작 시 담당자는 현재 코드 기준·문제 재현 또는 빈 기능 경계·선택한 최초 범위·확정되지 않은 정책·영향 파일·이행 전 fixture를 기록한다. 이 문서의 제안을 채택했으면 **개발 판단**으로, 사용자가 직접 결정했으면 **사용자 확정**으로 출처와 날짜를 남긴다. 기존 문서를 읽은 사실만으로 인터뷰 답변을 생성하지 않는다.

종료 시에는 정상 흐름의 실제 코드, 실패/취소/경합 결과, 새 저장소로 복원한 필드, 스키마 읽기/쓰기 버전, 수행한 명령과 결과 로그·렌더, 미실행 실기 항목, 기능 커밋 ID를 적는다. ‘기반 구현’, ‘사용자 흐름 구현’, ‘실기 검증’, ‘운영 연결’, ‘공개 출시’를 한 체크박스로 합치지 않는다.

자동 검증은 기존 `flutter analyze`와 관련 `flutter test`를 사용하고, 파일 경합은 실제 임시 디렉터리·지연 writer·실패 주입으로 확인한다. UI는 기존 Console v2 토큰·KR/Mono·컴포넌트를 조립하고 작은 화면/큰 글자/키보드 상태를 headless로 렌더한다. 로드맵을 처음 작성한 문서 전용 작업에서는 테스트를 실행하지 않았고, 이후 결과는 [수행일·마감 보고서](2026-09-08-session-lifecycle-verification.md), [정밀 편집 당시 검증](2026-09-08-admin-precise-editor.md), [고급 처방 최신 검증](2026-09-08-advanced-prescriptions.md)에 나누어 남긴다. 초기 앱·웹 검증은 [각 당시 검증](2026-09-08-feature-verification.md), [웹 시안 검증](2026-09-08-interactive-landing-concepts.md)의 범위이며 미구현 후속 기능의 통과 수가 아니다.

## 6. 누락을 막기 위한 우선 확인점

1. **백업 범위와 원자성:** 운동 백업에 습관/설정이 포함된 것처럼 안내하지 않는다. 전체 앱 복원이라면 여러 파일·큐를 같은 세대로 바꿔야 하며 일부 성공을 전체 성공으로 표시하지 않는다.
2. **날짜 변경의 파생 영향:** 수행일·마감·일정 변경·기록 정정은 D5 근거 순서/undo·지난값 후보·타이머에 영향을 준다. 도메인 하나의 단위 테스트만으로 사용자 흐름 회귀를 대체하지 않는다.
3. **운영 준비와 실제 기능의 구별:** 관리자 내부 도구는 서버 권한이 아니고, FAQ/문의 폼은 실제 접수가 아니며, 구독 화면은 검증된 권한이 아니다. 오프라인·만료·장애에도 사용자 로컬 기록 접근을 지킨다.

로드맵 최초 작성은 9/7~9/8 기존 조사 문서의 공식 페이지를 참고했다. 이후 고급 처방 개발에서 확인한 Hevy·Liftosaur 공식 동작 자료는 [고급 처방 명세의 출처표](2026-09-08-advanced-prescriptions.md)에 구분해 남긴다. API 도입·계정 접근·결제·문의 전송은 수행하지 않았으며 출시 시점에 바뀔 수 있는 플랫폼 정책은 해당 연결 단위에서 공식 문서로 다시 확인한다.
