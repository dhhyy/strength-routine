# 2026-09-07 · 기록 의미·식별·일정·복원 기능 분석

대상: **IM03·IM06·IM09·IM12**. [개선안 15개](../2026-09-07-fitness-app-analysis.md)를 구현 전에 검토할 기능 계약으로 구체화한다. **조사·명세 문서만 작성했으며 앱 코드와 저장 파일은 변경하지 않았다.** 아래 상태명·필드명은 개념을 설명하기 위한 것으로 새 JSON 스키마나 API를 확정하지 않는다.

읽기 시작점: [기능 분석 정본·공통 기준](../2026-09-07-feature-specification.md).

- **사용자 확정:** 생성→기록→재실행 복원, 트레이너 프로그램 선택, 운동·세트 구성 보존, 중량·시작일·요일 개인화. [인터뷰 I01·I05·I06](../2026-09-07-work-log.md)

- **미결정:** 각 항목의 마지막에 남긴다. 수용 기준은 제안 정책을 채택할 경우의 검증 조건이며 구현 완료 증거가 아니다.

## IM03 · 기록 마감·실제 수행·제외 구별 · P0/M

**현재 코드 / 목적.** [상태 모델](../../lib/domain/training_program.dart)의 `isSessionComplete`는 필수 세트가 하나 이상이고 각각 `setActuals`에 있으면 참이다. `completed`와 `skipped`를 모두 포함한다. [오늘 카드](../../lib/training_screens.dart)는 이를 ‘운동 완료’로 표시하고, [운동 화면](../../lib/workout_screen.dart)은 완료/제외 집계와 일회성 안내를 제공한다. 목적은 **기록을 다 정리했다는 뜻과 실제 운동을 했다는 뜻을 분리**하는 것이다. 참고: [PROG04의 수행/누락 구분](../../research/2026-09-07/expanded/program-apps.md).

**정상 흐름 — 제안.**

1. 사용자는 각 세트를 실제 완료 또는 제외로 기록한다. 입력 중 초안은 어느 쪽에도 포함하지 않는다.
2. 필수 세트가 모두 처리되면 ‘필수 기록 충족’을 표시한다. 이를 사용자 마감으로 자동 전환하지 않는다.
3. ‘기록 마치기’에서 실제 완료·제외·남은 선택 세트·초안을 확인한다. 필요한 처리 후 명시적으로 마감한다.
4. 마감 후 ‘기록 마침 · 실제 수행 N세트’로 보여준다. 전부 제외면 N=0이다. 실제 운동 횟수는 마감 수와 별도 집계한다.
5. 마감 후 수정은 원기록과 분리된 수정 초안으로 시작한다. 취소하면 원기록·마감이 유지된다. 확인된 마감 기록의 수정 확정 시 해당 세션을 재개 상태로 바꾸고 재마감을 안내한다. 원래 미마감이거나 과거 마감 여부가 미상이면 그 이력을 보존하고 첫 명시 마감을 안내한다. 보관 계획 정정도 계획을 활성화하지 않고 같은 원칙을 적용한다.

**필수 데이터·상태 전이 — 논리 계약.**

| 개념 | 의미·전이 |
|---|---|
| 세트 처리 상태 | 미기록 / 작성 중 초안 / 실제 완료 / 제외. 실제 완료 중량 0은 유효한 기록이며 미입력과 다르다. |
| 파생 집계 | 필수 기록 충족, 실제 완료 세트 수, 제외 수, 미기록 수를 각각 계산한다. 선택 세트의 실제 수행도 실제량에는 포함한다. 필수 0개는 ‘필수 세트 없음’이며 현재 getter의 false를 마감 불가로 그대로 사용하지 않는다. |
| 세션 기록 상태 | 신규 미마감 → 명시적 마감 → 수정 확정으로 재개 → 다시 마감. v1의 과거 마감 미상은 별도 출처 상태로 남기고 첫 명시 마감 전까지 유지한다. 과거 마감·정정 사건의 순서와 대상 revision을 보존한다. |
| 마감 증거 | 사용자 마감 동작 ID·기록 시각·대상 세션/상태 revision. 마감 시각은 실제 운동 종료 시각을 대신하지 않는다. |
| 기존 안내 이력 | `completionNotified`는 안내 표시 이력이다. 마감 여부나 실제 수행 증거로 사용하지 않는다. |

**실패·취소·복구 / 타이머 계약.** 저장 실패 시 실제값·수정 초안을 유지하고 ‘마감 저장 중/실패’를 표시하며 확정 성공을 알리지 않는다. 같은 마감 동작의 재시도는 중복 마감 사건을 만들지 않는다. 마감 성공과 해당 세션 휴식 타이머의 비활성화를 같은 논리 저장 단위로 처리한다. OS 알림 취소는 저장된 타이머 상태와 대조하며 늦게 도착한 알림이 상태를 되살리지 못하게 한다. 수정·재개·완료 취소·재시도는 타이머 시작 사건이 아니다. **새 실제 수행의 완료 동작**만 IM08의 시작 후보다. 마감 취소나 수정 취소로 끝난 타이머를 재시작하지 않는다.

**GWT 수용 기준.**

| Given | When | Then |
|---|---|---|
| 모든 필수 세트가 제외 | 사용자가 기록을 마감 | ‘기록 마침·실제 수행 0세트’, 수행일/수행 횟수에 자동 산입하지 않음 |
| 필수 기록 충족, 마감 동작 없음 | 앱 종료 후 복원 | 충족 상태만 복원, 명시적 마감으로 바뀌지 않음 |
| 마감된 세션 | 수정 취소 / 수정 확정 | 취소는 원상 유지, 확정은 실제값 정정·재개·재마감 안내, 타이머 재시작 없음 |
| 마감 저장 실패 | 재시도 후 재실행 | 같은 동작 한 번만 확정, 세트/초안 손실 및 중복 완료 안내 없음 |
| v1에서 `isSessionComplete=true` | 이행 후 조회 | 필수 기록 충족만 재계산, 과거 명시적 마감 여부는 미상으로 유지 |
| 과거 마감 미상 또는 신규 미마감 기록 | 실제값 정정 확정 | 과거 마감·재개 사건을 만들지 않음. 기존 미상/미마감 이력을 유지하고 첫 명시 마감 안내 |
| 필수 0개·선택 세트만 있는 유효한 세션 | 선택 세트 수행 후 기록 마치기 | ‘필수 세트 없음’과 실제 수행 수를 표시하고 명시 마감 가능. getter의 false 때문에 차단하지 않음 |

**미결정 정책.** 필수 미기록을 남긴 조기 마감 허용 여부, 남은 선택 세트·초안 처리, 수행일 인정 기준, 재마감 안내 빈도는 미정이다. **제안 초기값은 필수 세트가 있으면 직접 완료/제외한 뒤 마감**이다. 필수 0개·선택만 있는 세션은 사용자 명시 마감을 허용하고 수행 0도 그대로 표시한다. 자동 일괄 제외·초안 삭제는 넣지 않는다. 위 수정 후 재개 방식은 IM13과 함께 결정할 정책이다.

## IM06 · 공통 종목 ID와 실제 수행 날짜 · P1/L

**현재 코드 / 목적.** [운동 모델](../../lib/domain/training_program.dart)의 `ProgramExercise.id`는 세션 내부 식별자이며 `mainLift`는 선택적 분류다. 계획의 운동·세트 ID는 계획/세션/운동/세트 경로에서 생성된다. `SetActual`에는 수행일·입력 시각·수정 시각이 없다. `calendarDate`는 연·월·일을 UTC 자정 값에 담는 **달력 날짜 표현**이다. 목적은 다른 프로그램의 같은 종목을 안전하게 비교하고 예정일과 실제 수행일을 혼동하지 않는 것이다. 참고: [PROG10의 실제 시각/계획 보존](../../research/2026-09-07/expanded/program-apps.md).

**정상 흐름 — 제안.**

1. 프로그램 작성 측은 운동 항목에 공통 종목 참조를 제공한다. 같은 명칭이어도 장비·변형이 다르면 별도 종목으로 구분한다.
2. 사용자는 과거 예정 세션을 열어도 기존 목표·세트를 보며 실제 수행한 날짜를 기록한다. 현재 수행 모드의 날짜 기본 제안은 사용자가 확인할 수 있게 한다.
3. 뒤늦은 입력·정정에서는 수행 날짜를 직접 지정한다. 날짜만 아는 경우 날짜만 보관하고 시각을 만들어내지 않는다.
4. 운동별 이력은 확인된 공통 종목·단위·비교 조건으로 연결한다. 예정일과 수행일을 각각 보여주고 날짜 미상 기록은 별도 표시한다.

**필수 데이터·상태 전이 — 논리 계약.**

| 개념 | 의미·불변 조건 |
|---|---|
| 기존 인스턴스 ID | 계획·세션·운동·세트 경로 ID를 그대로 유지한다. 새 종목 ID 도입이나 이름 변경으로 실제/초안 참조를 다시 만들지 않는다. |
| 공통 종목 참조 | 종목 ID, 변형/장비 정의, 사전 버전·매핑 근거. 이름·`mainLift`만으로 자동 병합하지 않는다. 미매핑도 유효한 상태다. |
| 예정 날짜 | 최초 확정 날짜와 변경된 유효 날짜는 ISO 달력 날짜다. 시간대 이동으로 날짜를 환산하지 않는다. |
| 수행 날짜 | 실제 완료 세트에 연결되는 달력 날짜와 출처: 수행 중 확인 / 사용자 소급 입력·정정 / 기존 데이터 미상. 세션의 수행 날짜 범위는 알려진 실제 세트에서 도출한다. |
| 시각·시간대 | 입력/수정 사건의 UTC 시각과 실제 수행 시각은 별개다. 알려진 경우에만 당시 시간대·오프셋과 실제 시각을 보존한다. 현재 기기 시간대로 과거 날짜를 다시 해석하지 않는다. |
| 미상 → 확인 | 사용자의 명시적 정정 또는 신뢰할 수 있는 원자료로만 전환한다. 정정 전 값과 근거를 남긴다. |

**실패·취소·복구.** 운동 사전 로드 실패나 미매핑 때문에 기록을 막지 않는다. 이름만 같은 기록은 비교에서 제외하고 이유를 보여준다. 날짜 수정 저장 실패 시 원래 값과 수정 초안을 유지한다. 신규 타임스탬프에는 주입 가능한 clock/시간대 문맥을 사용해 날짜 경계 테스트를 재현한다. 다른 지역에서 앱을 열어도 저장된 수행 달력 날짜와 예정 날짜는 바뀌지 않는다.

**v1 이행.** 기존 ID·프로그램·목표·실제값·초안을 보존하고 새 종목 참조와 수행 날짜는 미상으로 둔다. **예정일, 파일 수정 시각, 이행 시각, 최근 리프트 기록의 날짜를 실제 수행일로 복사하지 않는다.** UTC 자정으로 저장된 예정일을 실제 수행 시각으로 변환하지 않는다. 미상 기록도 삭제하지 않고 날짜가 필요한 빈도·월별 비교에서 별도로 집계한다.

**GWT 수용 기준.**

| Given | When | Then |
|---|---|---|
| 다른 프로그램의 동일 종목 참조 | 이력을 조회 | 각 기존 기록 ID를 유지하며 비교, 다른 장비/변형은 섞이지 않음 |
| 같은 이름, 공통 참조 미확인 | 지난 기록을 요청 | 자동 병합하지 않고 비교 불가/매핑 미상 안내 |
| 9/7 예정 운동을 9/9에 실제 수행 | 기록 후 시간대를 변경 | 예정 9/7·수행 9/9 유지, 실제 UTC 시각은 별도 의미로 보존 |
| 수행일 없는 v1 기록 | 이행·내보내기·재복원 | 실제 날짜 미상 유지, 예정일은 별도 필드, 원래 ID/실제값 일치 |
| 자정을 걸친 기록 또는 소급 입력 | 날짜를 확인·수정 | 입력 날짜와 수행 날짜를 혼동하지 않고 확인한 날짜만 반영 |

**미결정 정책.** 운동 사전 공급·매핑 검토 주체, 현재 수행 날짜의 기본값/확인 방식, 세트별·세션별 수행 날짜 UI, 여러 날에 걸친 한 세션의 표시·횟수 집계는 미정이다. 논리 모델은 실제 세트의 서로 다른 날짜를 하나의 예정일로 강제 합치지 않아야 한다.

## IM09 · 놓친 운동 수행·일정 재배치 · P1/L

**현재 코드 / 목적.** [계획 모델](../../lib/domain/training_program.dart)의 `rescheduleFuture`는 기존 날짜와 새 날짜가 모두 `asOf`보다 미래여야 한다. 생성자도 날짜가 시작일 이상·선택 요일·원래 세션 순서상 **엄격 증가**인지 검증한다. 날짜 중복과 순서 역전은 거부된다. [오늘/달력](../../lib/training_screens.dart)에서 놓친 세션과 과거 초안을 열 수 있지만 이동 UI는 없다. 목적은 원일정과 기록을 지키며 놓친 운동으로 돌아오는 것이다. 참고: [PROG05~07 일정·권한 구분](../../research/2026-09-07/expanded/program-apps.md).

**정상 흐름 — 제안.**

1. 놓친 세션에 ‘오늘 수행’과 ‘예정일 변경’을 구분한다. 오늘 수행은 세션 ID·예정일을 유지하고 IM06의 실제 날짜를 기록하는 경로다.
2. 일정 변경은 대상을 선택하고 원래 날짜→제안 날짜, 영향을 받는 뒤 세션, 충돌을 미리 보여준다. 기본적으로 다른 세션을 조용히 밀지 않는다.
3. 사용자가 변경 범위를 확정한 경우에만 전체 후보 일정을 검증하고 한 번에 적용한다. 날짜만 바뀌며 프로그램·운동·세트·확정 목표는 유지한다.
4. 다시 열면 최초 예정일·현재 예정일·실제 수행 날짜를 구분한다. 적용 취소/되돌리기도 같은 검증을 거친 새 일정 변경으로 처리한다.

**필수 데이터·상태 전이 / 모델 변경 범위.**

| 개념 | 계약과 현재 모델에 필요한 검토 |
|---|---|
| 불변 원본 | 최초 확정 일정·프로그램 버전·목표는 보존. 유효 일정과 변경 이력을 별도로 표현하는 방안을 검토한다. 객체를 직접 수정하지 않는다. |
| 변경 후보 | 계획 ID·기준 revision·대상 세션 ID/이전 날짜/새 날짜·범위·사용자 동작 ID. 생성→미리보기→검증→적용 또는 취소. |
| 현재 제약 유지 | 미래 일부 변경도 전체 날짜의 존재·선택 요일·시작일·엄격 순서를 재검증한다. 뒤 세션과 충돌하면 후보 전체를 적용하지 않는다. |
| 범위 확대 | 과거/오늘 이동, 선택 요일 밖 이동, 같은 날 여러 세션, 순서 변경은 현재 계약에서 거부된다. UI 연결만으로 풀지 말고 원본+유효 일정 모델과 정책을 먼저 정한다. |
| 상태 교체 | 같은 계획의 일정 개정은 새 프로그램 시작이 아니다. 현재 `withActivePlan`은 이전 계획을 보관하므로 같은 ID 교체용으로 사용하면 중복 ID 문제가 난다. 별도의 검증된 개정 동작이 필요하다. |

**실패·취소·복구.** 실제 기록이 있는 세션은 예정일 이동보다 수행 날짜 기록/정정으로 처리하는 방안을 우선 제안한다. 초안이 있는 세션을 허용 범위 안에서 이동해도 초안은 같은 ID에 남긴다. 미리보기 후 상태 revision이 바뀌면 다시 비교하게 하며 자동 덮어쓰기하지 않는다. 저장 실패 시 원래 적용 일정과 변경 후보를 구분해 유지하고 재시도한다. 세션·세트 재생성으로 충돌을 회피하지 않는다.

**GWT 수용 기준.**

| Given | When | Then |
|---|---|---|
| 과거 예정 세션에 초안 존재 | 오늘 수행으로 진입 | 같은 세션·세트 ID와 초안 복원, 예정일 보존·수행일 별도 기록 |
| 미래 세션 이동 후보가 다음 세션과 충돌 | 미리보기/적용 | 충돌 이유 표시, 부분 적용·자동 밀기 없음 |
| 허용된 미래 날짜 변경 | 저장·재실행 | 원본 일정/목표/실제/초안 보존, 유효 일정만 변경 |
| 후보 작성 뒤 다른 기록이 저장됨 | 일정 적용 | revision 재검증, 오래된 후보로 최신 기록을 덮지 않음 |
| 과거 세션의 오늘 이동 요청 | 현재 계약으로 검증 | 지원하지 않는 이동을 성공처럼 표시하지 않음, 오늘 수행 경로는 별도로 가능 |

**미결정 정책.** 단일 세션 이동과 이후 전체 이동, 원래 운동 순서 유지, 같은 날 여러 세션, 선택 요일 밖 예외, 이미 수행/마감한 세션 이동, 되돌리기 범위는 미정이다. 최초 구현 후보는 **놓친 세션을 원일정 그대로 오늘 수행 + 제약 안의 미래 일정 편집**이다. 원본을 지키면서 과거 날짜도 바꿀지 별도 결정한다.

## IM12 · 복원용 백업과 분석용 내보내기 · P1/L

**현재 코드 / 목적.** [저장소](../../lib/data/local_training_store.dart)는 한 인스턴스의 읽기/쓰기를 직렬화하고 임시 파일 쓰기→rename으로 `schemaVersion: 1` 상태를 저장한다. [컨트롤러](../../lib/app/training_controller.dart)는 메모리를 먼저 갱신하고 실패해도 입력을 유지하며 revision으로 최신 저장 결과를 표시한다. 외부 파일 가져오기·내보내기·배타적 복원 모드는 없다. 목적은 기기 이동용 **복원 가능 백업**과 분석용 CSV를 분리하는 것이다. 참고: [LOG02·05·10~11의 내보내기/복원 구별](../../research/2026-09-07/expanded/logging-apps.md).

**정상 흐름 — 제안.**

1. 내보내기는 현재 revision의 일관된 스냅샷을 확보한다. 저장 실패·작성 중 값의 포함 여부를 안내하고 포함 범위를 미리 보여준다. 백업은 프로그램 스냅샷·ID·실제·초안·노트·관련 상태를 복원할 수 있어야 한다.
2. 가져오기는 선택한 파일을 별도 후보로 읽고 크기·JSON 형태·지원 스키마·타입·단위·날짜·중복 ID·참조 무결성을 검사한다. 지원하는 이행도 복사본에서 먼저 실행한다.
3. 계획/기록/초안 수, 날짜 미상 수, 현재 데이터와 교체 범위를 보여준다. 초기 제안은 **전체 교체 복원**이며 자동 병합하지 않는다. 이 시점에는 현재 메모리/원본 파일을 바꾸지 않는다.
4. 사용자 적용 후 새 쓰기를 막는 배타 진입을 획득하고, 기존 writer queue를 소진한다. 남은 수정 초안·실패 저장을 해결한 일관된 현재 상태와 복원 후보를 재검증한다. 확인 이후 revision이 바뀌었으면 차이를 다시 보여준다.
5. 복구 가능한 기존 스냅샷을 확보한 뒤 후보를 임시 파일에 기록·검증하고 **한 번의 원자적 교체**로 커밋한다. 성공 후에만 메모리를 후보로 바꾸고 쓰기 진입을 다시 연다. 이전 큐의 작업·지연 콜백이 복원본을 덮지 않게 세대/revision 경계를 둔다.
6. 재실행 복원을 확인한다. 백업 파일 안의 타이머를 즉시 재생·알림 예약하지 않는다. IM08 계약으로 소속·만료·마감 상태를 대조한 뒤 사용자 재개 정책을 적용한다.

**필수 데이터·상태 전이 — 논리 계약.** 파일 종류/포맷 버전·생성 시각·데이터 범위·원본 revision, 지원 가능한 이행 경로, 검증 결과, 복원 동작 ID, 복구용 기존 스냅샷이 필요하다. `idle → 검사 → 미리보기 → 배타 적용 → 완료/실패`를 구분한다. CSV는 종목/세트 ID·예정일·수행일/미상·단위·실제값·제외 여부를 명시하고 분석 목적임을 표시한다. 생성 시각은 수행 날짜를 대신하지 않는다. 구체 포맷·저장 위치·체크섬 방식은 별도 설계한다.

**실패·취소·복구.** 파일 선택 취소·형식 오류·지원하지 않는 미래 스키마는 **현재 메모리/파일과 가져온 원본을 모두 보존**하고 원인을 알린다. 미래 파일을 v1로 줄여 쓰거나 초기화하지 않는다. 디스크 부족·권한·임시 파일/교체 실패는 기존 상태로 남고 후보를 재시도할 수 있어야 한다. 교체 전 프로세스 종료는 기존 파일, 교체 후 종료는 완전히 검증된 복원본이 읽혀야 한다. 실패 시 writer 잠금은 해제하되 지연된 과거 스냅샷을 무조건 재저장하지 않는다. 내보내기 공유를 취소했으면 완료로 안내하지 않는다.

**GWT 수용 기준.**

| Given | When | Then |
|---|---|---|
| 활성/보관 계획·실제·초안·미상 날짜를 담은 지원 백업 | 새 설치로 복원 | 기존 ID·목표·값·미상 여부가 일치, 온전한 스냅샷 복원 |
| 손상·미지원 미래 스키마·고아 참조 파일 | 가져오기 | 이유 표시, 현재 상태/파일 및 가져온 원본 불변 |
| 이전 자동 저장이 진행 중 | 복원 적용 | 큐 소진·새 쓰기 차단 후 후보 한 번 커밋, 오래된 저장이 복원본을 덮지 않음 |
| 미리보기 뒤 새 입력 또는 미저장 오류 | 적용 시도 | 충돌/미저장 상태를 해결하기 전 교체하지 않음, 사용자 입력 유지 |
| 디스크 오류 또는 커밋 전후 강제 종료 | 재실행 | 이전 상태 또는 완전한 복원본 중 하나, 반쪽 데이터·무음 초기화 없음 |
| 수행일 미상·kg/lb·제외가 혼재 | CSV 내보내기 | 단위/날짜 의미 명시, 미상은 미상, 목표·초안을 실제로 집계하지 않음 |

**미결정 정책.** 전체 교체와 병합 지원 범위, 내보낼 개인정보/초안 범위, 백업 암호화·보관 위치, 복구본 유지 기간, CSV 열/호환 대상, 복원한 진행 세션·타이머의 재개 방식은 미정이다. 자동 클라우드 동기화와 외부 앱 CSV 가져오기는 이번 기능의 전제가 아니다.

## 공통 선행 조건과 검증 순서

1. IM03의 마감 의미와 IM06의 종목/날짜 계약을 먼저 합의한다. 마감·정정·타이머 세부 연결은 [운동 기능 명세](2026-09-07-workout.md)와 같은 계약을 사용한다.
2. 이행은 v1 원본을 복사한 고정 fixture로 검증한다. 새 필드의 미상 상태·기존 ID·원일정·실제·초안을 보존하고 이행을 반복해도 데이터가 달라지지 않아야 한다.
3. 날짜 경계·윤일·시간대 변경·지연 입력·기록 정정·일정 충돌을 주입 가능한 시계와 고정 날짜로 검증한다. 예정 civil date와 UTC instant를 혼용하지 않는다.
4. 저장 경쟁·복원 중단·실패 재시도를 실제 임시 파일로 검증한 뒤 네이티브 파일 선택/공유·앱 종료 후 복원을 확인한다. 기존 파일 저장 테스트를 외부 백업 복원 검증으로 대체하지 않는다.

이 문서는 상태와 데이터의 논리 경계를 정의한 개발 제안이다. 새 스키마 번호, 마이그레이션 실행, 데이터 덮어쓰기, 실제 기능 구현을 승인하거나 수행한 기록이 아니다.
