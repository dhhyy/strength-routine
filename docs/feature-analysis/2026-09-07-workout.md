# 9/7 기능 분석 · 운동 입력·휴식·요약·보관 기록 정정

작성일: 2026-09-07 (Asia/Seoul). 범위: [개선 백로그](../2026-09-07-fitness-app-analysis.md)의 IM07·08·10·13. **개발을 준비하는 설계 제안이며, 사용자 확정 요구·구현 완료·운동 효과 검증이 아니다.** 앱 코드·저장 파일·스키마를 변경하지 않았다.

읽기 시작점: [기능 분석 정본·공통 기준](../2026-09-07-feature-specification.md).

기존 결정인 트레이너 운동·세트 구성 보존, 목표/초안/실제 분리, 기기 저장·재실행 복원을 전제로 한다. 아래 논리 필드명은 구현 확정 이름이 아니며, [IM03·06·09·12 중앙 데이터 계약](2026-09-07-data-reliability.md)과 함께 확정한다. 현재 상태는 9/7 소스 직접 대조 결과다. 경쟁 앱은 [기존 공식 자료 조사](../../research/2026-09-07/expanded/logging-apps.md)를 참고했으며 이번에는 추가 웹 검색·앱 설치·화면 조작을 하지 않았다.

**공통 저장 한계:** 저장 실패 중에는 메모리 입력을 보존하지만, 실패한 쓰기 자체가 강제 종료 뒤 복원되지는 않는다. 재실행 복원의 보장은 마지막으로 영구 저장에 성공한 초안·확정값까지다. 최신 미저장값까지 복구했다고 표시하지 않으며, 실패한 정정은 이전 확정값/마감 상태를 손상하지 않아야 한다.

## IM07 · 지난 실제값 가져오기·증감·저장 후 다음 세트

- **목적:** 같은 값을 다시 입력하거나 목록에서 다음 세트를 찾는 동작을 줄이되, 가져온 값과 이번에 수행한 기록을 구분한다.
- **현재 차이:** [SetEditor](../../lib/workout_screen.dart)는 초안→현재 실제값 순으로 복원하며 신규 입력은 비어 있다. kg/lb 전환은 숫자 유지 방식이다. 과거 세트 조회·증감·다음 세트 이동은 없고, 저장 성공 시 시트가 닫힌다.
- **정상 흐름 1:** 편집 진입 → 현재 목표·작성 중 입력을 먼저 표시 → 비교 가능한 지난 실제 세트의 수행일·중량·단위를 별도로 확인한다.
- **정상 흐름 2:** 사용자가 ‘지난 중량·반복 사용’을 누른다 → 덮어쓸 필드와 출처를 확인한다 → 중량·단위·반복만 초안에 적용 → 이번 수행 후 ‘저장하고 다음 세트’를 누른다.
- **정상 흐름 3:** 유효성 검사·기기 저장 성공 → 트레이너 순서에서 뒤쪽의 첫 미기록 세트로 이동한다. 뒤쪽이 없으면 남은 앞쪽 세트를 안내하거나 목록으로 돌아가며, 다른 세트를 자동 제외하지 않는다.
- **필수 데이터 제안:** 대상 계획/세션/세트 ID, 공통 종목 참조와 변형·장비·부하 의미, 지난 기록 ID/리비전/수행일 출처, 원단위 실제값, 현재 초안과 필드별 변경 여부를 사용한다.
- **선택 데이터 제안:** 지난 RIR·메모는 출처가 붙은 읽기 전용 참고값이다. 이번 RIR·메모로 복사하지 않는다. 현재 세트에 사용자가 작성한 RIR·메모는 복사·증감 때 그대로 보존한다.
- **지난값 선택 논리:** 같은 프로그램 세션 유형·종목·대응 세트 순번을 우선하되, 확인된 실제 수행일이 현재 수행일보다 앞선 완료 기록만 후보로 삼는다. 수행일이 미상이거나 여러 후보의 순서가 불명확하면 자동 ‘최근’ 선정을 하지 않는다.
- **비교 경계:** 이름만 같은 운동·다른 변형·다른 장비·서로 다른 부하 의미를 병합하지 않는다. 세트 구성이 달라 순번 대응이 안 되면 사용자가 출처를 선택하게 한다. 시작 설정의 `RecentLiftRecord`는 실제 세트 이력과 별도다.
- **초안 보호:** 기존 중량·단위·반복 중 하나라도 작성·수정돼 있으면 조용히 덮어쓰지 않고 현재값/가져올 값을 확인한 뒤 선택 적용한다. 취소하면 원문 초안이 그대로 남는다.
- **반복 복사:** 같은 출처·같은 값의 재요청은 변화 없는 동작으로 처리한다. 복사 후 사용자가 고친 값에는 다시 덮어쓰기 확인을 요구한다. 복사 이력·필드 변경 표시는 재실행으로 사라져 보호가 풀리지 않게 한다.
- **단위 논리:** 최초 제안은 원중량과 원단위를 함께 복사하는 방식이다. 입력 단위 변경은 현재처럼 숫자를 유지한다. 환산은 별도 명시 동작으로 분리하며, 제공한다면 내부 kg/lb 환산 후 표시만 반올림하고 원기록은 바꾸지 않는다.
- **증감 논리:** 장비/운동별 입력 간격은 값과 단위를 함께 갖고 유한 양수여야 한다. 계획의 `incrementKg`를 lb 입력 간격으로 그대로 쓰지 않는다. 간격 미지정·단위 불일치·불완전 숫자에서는 증감을 비활성화한다.
- **0과 숫자:** 중량 `0`은 유효한 실제값이며 빈값이 아니다. 감소 결과가 음수면 입력을 바꾸지 않고 안내한다. 반복은 양의 정수, RIR은 선택값이되 입력된 `0`은 보존하며 현재 검증 범위를 임의 강화하지 않는다.
- **저장 논리:** 복사·증감은 원문 초안만 저장한다. ‘저장하고 다음’은 실제 완료 저장의 최신 성공 응답 뒤 한 번만 이동한다. 다음 세트의 기존 초안은 복원하며 지난값으로 미리 덮지 않는다.
- **빈 상태:** 비교 가능한 이력이 없으면 ‘지난 기록 없음’과 수동 입력을 제공한다. 다음 미기록 세트가 없으면 목록/요약으로 연결하며 새 세트를 생성하지 않는다.
- **로딩 상태:** 지난값 조회 중에도 현재 초안 입력은 가능하다. 늦게 도착한 조회 응답은 사용자가 입력한 내용을 바꾸지 않는다. 완료 저장 중에는 중복 제출·대상 이동을 막는다.
- **실패 상태:** 조회 실패는 비교 영역에서만 재시도한다. 초안·실제 저장 실패는 현재 입력·단위·선택 세트를 유지하고 재시도하며, 다음 이동·완료 성공을 표시하지 않는다.
- **취소·이탈:** 복사 확인 취소는 변화 없음. 편집 닫기는 초안 저장 후 이탈하며 실패하면 머무른다. 프로세스 종료 후 저장된 초안/출처를 복원한다. 완료 전 초안 폐기는 별도 명시 동작으로 남긴다.
- **선행:** IM06 공통 종목/실제 수행일·단위 의미, 운동별 장비 간격 정책. 데이터가 없으면 원단위 수동 입력만 허용하며 추측한 이력이나 간격을 만들지 않는다.
- **영향 파일 제안:** [workout_screen.dart](../../lib/workout_screen.dart), [training_program.dart](../../lib/domain/training_program.dart), [training_controller.dart](../../lib/app/training_controller.dart), [local_training_store.dart](../../lib/data/local_training_store.dart). 비교·환산은 화면 밖 순수 로직으로 둔다.
- **GWT 1:** Given `0 kg`, 반복 양수, RIR `0`, 과거 메모가 있는 지난 세트와 현재 RIR/메모 초안 → When 중량·반복을 가져오고 다시 누름 → Then 중량 `0`은 보존되고 현재 RIR/메모는 유지되며 실제 기록은 생성되지 않는다.
- **GWT 2:** Given 가져온 값 이후 직접 수정한 lb 초안과 kg 간격 → When 다시 가져오기를 취소하거나 증감을 시도 → Then 수정 초안은 그대로이며 단위 불일치 증감은 실행되지 않는다. 명시적 환산을 선택한 경우에만 단위 계산을 적용한다.
- **GWT 3:** Given 다음 세트에 기존 초안이 있고 현재 완료 저장이 실패 → When 재시도 성공/중복 응답 발생 → Then 성공 전 이동하지 않고 성공 후 한 번만 다음 세트 초안을 복원하며 원래 목표·세트 순서는 같다.
- **미결정 정책:** 기본 이력 범위를 같은 프로그램으로 제한할지, 같은 날 이전 수행을 어떻게 정렬할지, 반복 구조가 다른 세트의 후보 선택 방식, 장비별 간격 제공 주체·표시 정밀도·환산 제공 여부를 정해야 한다.
- **근거:** [Hevy 이전값과 루틴값 구분](https://help.hevyapp.com/hc/en-us/articles/34105442929943-Previous-Workout-Values-Vs-Routine-Values-How-to-Adjust-in-Settings), [FitNotes 입력/증감](https://www.fitnotesapp.com/workout_tracking/), [FitNotes 다음 세트 설정](https://www.fitnotesapp.com/settings/). 초안 보호·복사 범위는 우리 앱의 설계 제안이다.

## IM08 · 실제 세트 완료에 연결된 휴식 타이머

- **목적:** 운동 기록 흐름 안에서 남은 휴식을 확인하고, 앱 전환·재실행에도 같은 휴식을 이어간다. 휴식 시간을 앱이 임의 처방하지 않는다.
- **현재 차이:** [ProgramSet](../../lib/domain/training_program.dart)에 휴식·세트 유형이 없고, [TrainingAppState](../../lib/domain/training_program.dart)에 타이머/완료 작업 식별자가 없다. [SetEditor._commit](../../lib/workout_screen.dart)는 신규 완료·수정·제외·되돌리기를 같은 저장 경로로 처리한다.
- **정상 흐름 1:** 프로그램에 명시된 휴식 또는 사용자가 지정한 시간을 확인 → 이번 실제 수행 세트를 완료 → 기록과 휴식 상태를 같은 저장 작업으로 확정한다.
- **정상 흐름 2:** 저장된 타이머의 남은 시간을 표시 → 사용자는 시간 조절·건너뛰기 가능 → 다른 앱으로 이동해도 복귀 시 같은 타이머를 복원한다.
- **필수 데이터 제안:** `timerId`, 계획/세션/세트 ID, 신규 수행 완료 `operationId`, 설정 시간/출처, 시작·만료 UTC 시각, 상태, 마지막 관측 시각과 리비전을 저장한다. 실행 중 단조 시계 앵커는 별도 런타임 데이터다.
- **선택 데이터 제안:** 프로그램 휴식, 사용자 덮어쓴 휴식, OS 알림 ID·예약 상태·허용 상태를 별도 보유한다. 워밍업/일반 세트별 시간은 IM14가 세트 유형을 지원한 이후 적용한다.
- **시간 유효성:** 시간 미지정은 타이머 미사용이다. `0`은 명시적 휴식 없음으로 처리하고 타이머/즉시 알림을 생성하지 않는다. 음수·비정수·비정상 수치는 거부하며 기본 초를 임의 생성하지 않는다.
- **시작 조건:** ‘이번 수행 신규 완료’ 명령만 시작 후보가 된다. 단순 상태가 `completed`로 바뀌었다는 이유로 시작하지 않는다. 제외·초안 저장·지난값 복사·기록 정정·되돌리기·재개·재시도에는 시작 이벤트가 없다.
- **중복 방지:** 한 신규 완료의 `operationId`를 첫 제출부터 재시도까지 재사용한다. 실제값과 타이머 시작 식별자를 원자적으로 저장하고, 같은 작업의 저장 재시도·콜백 재전달·복원은 시작 시각을 갱신하지 않는다.
- **완료 취소:** 되돌리는 세트에 연결된 진행 타이머가 있으면 그 타이머를 중지한다. 다른 세트 타이머는 유지한다. 되돌리기를 취소하거나 정정 기록을 복구해도 자동으로 새 휴식은 시작하지 않는다.
- **시간 조절:** 현재 타이머 리비전에 변경량을 한 번 적용하고 만료 시각을 저장한다. 건너뛰기는 해당 타이머를 종료한다. 남은 시간이 `0` 이하이면 종료 상태로 제한하고 음수 카운트다운을 표시하지 않는다.
- **시계 논리:** 화면의 매초 감소 횟수를 저장하지 않는다. 실행 중에는 단조 시계로 경과를 계산하고, 프로세스 재실행은 저장한 만료 시각과 현재 UTC로 복원한다. 시간대 변경은 UTC 만료를 바꾸지 않는다.
- **시계 변경/드리프트:** 런타임의 UTC 경과와 단조 시계 경과 차이가 허용 오차를 넘거나 재실행 시 현재 시각이 마지막 관측보다 과거면 ‘기기 시간이 변경됨’을 표시한다. 확인 가능한 남은 시간으로 재설정/종료 선택을 받고 정확한 복원을 주장하지 않는다.
- **감지 한계:** 종료 중 수동 시계 변경은 모두 구별할 수 없다. 만료 이후 재실행은 `0`/휴식 종료로 복원하고 새 소리·새 휴식을 자동 발행하지 않는다. 시계 검증이 불가능한 상황의 알림 신뢰 범위는 명시한다.
- **알림 논리:** 영구 저장된 `timerId`로 예약/취소를 멱등 처리한다. 알림 예약 실패·권한 거부는 기록 저장 실패와 구분하고 앱 내 타이머는 사용 가능하다. 백그라운드 콜백 실행에 기록 보존을 의존하지 않는다.
- **마감 연결:** IM03의 세션 마감 확정과 연결된 타이머 종료를 같은 상태 저장으로 처리한다. 실패하면 ‘마감 완료’ 또는 ‘알림 취소 완료’라고 표시하지 않으며, 재시도는 원래 마감 작업을 이어간다.
- **빈 상태:** 시간이 없으면 ‘휴식 시간 설정’ 또는 사용 안 함을 제공한다. 진행 타이머가 없을 때 가상 숫자를 표시하지 않는다.
- **로딩 상태:** 앱 복원 중 타이머를 임의 재시작하지 않는다. 저장 중에는 해당 작업 진행을 표시하고 동일 조절/건너뛰기 중복 제출을 막는다.
- **실패 상태:** 실제 완료 저장 실패는 입력과 동일 타이머 초안을 보존하고 재시도한다. 재시도 성공까지의 경과를 포함해 원래 만료로 복원한다. 저장 실패만으로 알림을 먼저 예약하지 않는다.
- **취소·이탈:** 설정 취소는 기존 시간 유지, 화면 이탈은 저장된 타이머 유지, 건너뛰기는 명시 종료다. 알림 허용 요청을 취소해도 기록 화면으로 돌아온다.
- **선행:** 휴식 제공 주체·IM03 마감 명령·완료 작업 식별자 계약, 주입 가능한 시계와 OS 알림 어댑터. 잠금화면/워치 입력 자체는 IM15 후속이다.
- **영향 파일 제안:** [training_program.dart](../../lib/domain/training_program.dart), [training_controller.dart](../../lib/app/training_controller.dart), [local_training_store.dart](../../lib/data/local_training_store.dart), [workout_screen.dart](../../lib/workout_screen.dart); 타이머 순수 로직/플랫폼 어댑터와 스키마 이행 검증이 추가로 필요하다.
- **GWT 1:** Given 휴식이 지정된 신규 완료의 저장 실패 → When 동일 작업을 재시도하고 성공 응답을 중복 전달 → Then 실제 기록과 타이머는 한 번만 저장되고 첫 시작·만료 시각을 유지한다. 과거 기록 수정/undo는 시작 이벤트가 없다.
- **GWT 2:** Given 저장된 진행 타이머 → When 앱 전환·재실행·시간대 변경 또는 탐지 가능한 시계 역행 → Then 정상 경과는 동일 만료로 복원되고 역행은 확인 상태가 되며, 만료 후 새 휴식이나 알림을 만들지 않는다.
- **GWT 3:** Given 알림 거부 또는 명시적 `0`초 → When 실제 세트를 완료 → Then 기록 저장은 가능하고, 거부 시 앱 내 타이머만 동작하며 `0`초는 타이머 없음이다. 마감 저장 실패 시 확정 종료로 오인시키지 않는다.
- **미결정 정책:** 동시에 타이머 하나만 허용하고 새 완료가 이전 타이머를 대체할지, 마지막 세트에도 시작할지, 사용자/프로그램 시간 우선순위, 조절 간격, 허용 시계 오차, 소리/진동 기본값·OS 지원 범위를 정해야 한다.
- **근거:** [Strong 휴식 타이머](https://help.strongapp.io/article/231-rest-timer), [FitNotes 타이머 시작 조건](https://www.fitnotesapp.com/workout_tools/). 작업 식별·저장 원자성·시계 이상 처리 방식은 우리 앱의 제안이다.

## IM10 · 운동별 종료 요약·지난 수행·다음 일정

- **목적:** 기록을 마친 뒤 무엇을 실제로 수행했는지 확인하고, 비교 가능한 지난 기록과 다음 일정을 이해한다. 마감과 실제 운동 수행을 같은 수치로 취급하지 않는다.
- **현재 차이:** [WorkoutScreen](../../lib/workout_screen.dart)은 완료/제외/전체 수와 필수 세트 기록 후 일회 안내를 제공한다. 운동별 비교·다음 일정 요약은 없다. [isSessionComplete](../../lib/domain/training_program.dart)는 필수 세트에 제외만 있어도 참이다.
- **정상 흐름 1:** IM03의 명시적 ‘기록 마감’ 성공 → 해당 세션의 저장된 최신 기록으로 요약 → 기록 탭에서도 같은 요약을 다시 연다. 모든 필수 세트가 채워졌다는 것만으로 마감했다고 추정하지 않는다.
- **정상 흐름 2:** 수행일/예정일·실제 완료/제외/미기록 수 확인 → 운동별 실제 세트·반복·중량과 선택 비교 확인 → 다음 예정 운동을 미리 보거나 오늘 화면으로 돌아간다.
- **필수 데이터 제안:** 계획/세션 ID와 당시 프로그램 스냅샷, 명시 마감 상태/리비전, 완료 실제값·단위·반복, IM06 수행일과 출처·공통 종목/장비/부하 의미를 사용한다.
- **선택 데이터 제안:** 실제 RIR·메모, 알려진 시작/종료 시각, 비교 대상 ID/리비전, 다음 일정이 있다. 시각이 없는 옛 기록에 운동 시간을 추정 생성하지 않는다.
- **집계 논리:** `completed`만 실제 수행 세트/반복에 산입한다. `skipped`는 제외 수, 실제값 없는 세트는 미기록 수이며 그중 초안 수를 별도 표시할 수 있다. 목표·초안은 실적에 더하지 않는다.
- **수행 0과 마감:** 전부 제외하거나 수행 없이 명시 마감하면 ‘기록 마침 · 수행 0세트’로 표시한다. 마감 횟수를 운동 수행 횟수로 사용하지 않는다. 부분 수행 마감은 실제 수와 남은 미기록을 함께 보인다.
- **중량 0:** 유효한 `completed(weight: 0, repetitions > 0)`는 수행 세트·반복 집계에 포함한다. 중량 미입력과 구별하며 0을 이유로 제거하지 않는다. 기록된 외부중량×반복량의 기여는 0이지만 운동 효과가 0이라는 뜻은 아니다.
- **지표 명칭:** 기본은 실제 완료 세트·총 반복·각 세트 실제 중량이다. 선택적 합계는 ‘외부중량×반복량’처럼 계산 의미를 표시한다. D1의 부위별 주간 hard set 볼륨과 동일한 ‘볼륨’으로 표시하지 않는다.
- **단위 논리:** 같은 부하 의미일 때만 kg/lb를 공통 내부 단위로 환산해 비교/합산하고 표시 단계에서 반올림한다. 입력 원단위·원값은 보존한다. 보조중량·체중·머신 설정처럼 의미가 다르거나 미상인 항목은 합산하지 않는다.
- **비교 논리:** 같은 종목·변형·장비·부하 의미와 같은 반복 조건의 이전 실제 기록을 비교한다. 비교 날짜·조건을 함께 표기하고 조건이 달라지면 수치 증감 대신 ‘비교 조건 다름’을 표시한다.
- **날짜 논리:** 예정일과 실제 수행일을 각각 보여준다. 실제 날짜 미상은 그대로 미상이며 예정일/저장일을 수행일로 대입해 ‘지난 운동’ 순서를 만들지 않는다. 동일 날짜 내 순서가 불분명하면 자동 우열 비교를 하지 않는다.
- **0 기준 비교:** 지난값이 0이면 퍼센트 증가율을 계산하지 않고 이번 값과 절대 차이만 표시한다. 첫 기록·대응 세트 없음은 비교 없음이며 PR·증가율을 임의 생성하지 않는다.
- **RIR·해석:** 실제 RIR 없는 기록을 목표 RIR로 대체해 hard set으로 분류하지 않는다. 감소한 중량·반복을 자동 실패로 표현하지 않으며 디로딩/다른 처방의 맥락을 유지한다. e1RM 등 미확정 공식은 제외한다.
- **갱신 논리:** 요약은 실제값에서 계산하고, 캐시가 있다면 입력 기록/리비전·지표 버전에 연결한다. IM13 정정·되돌리기 확정 후 재계산하며 과거 완료 알림을 재발행하지 않는다.
- **다음 일정:** 현재 활성 계획의 다음 예정 세션과 날짜를 보여주고 읽기 전용 미리보기로 연결한다. 보관 세션 요약에서는 현재 계획의 일정임을 구분한다. 일정 변경·자동 세션 시작은 하지 않는다.
- **빈 상태:** 세트 없는 잘못된 구성은 오류 안내, 수행 0은 유효한 0 상태, 비교/다음 일정 없음은 각각 별도 안내다. 기록 자체를 읽지 못한 상태를 수행 0으로 대체하지 않는다.
- **로딩 상태:** 저장·복원 중 확정 요약 대신 진행 상태를 표시한다. 비교 계산이 늦어도 이미 확인된 실제 기록은 볼 수 있고, 다른 세션의 뒤늦은 응답을 섞지 않는다.
- **실패 상태:** 마감 저장 실패는 입력 화면에 남아 재시도하며 마감 요약 성공을 표시하지 않는다. 비교 조회 실패는 실제 세션 요약을 유지한 채 해당 영역만 재시도한다.
- **취소·이탈:** 마감 확인 취소는 현재 기록/초안 유지, 요약 닫기는 저장값 변경 없음이다. 재실행 후 저장된 마감 요약을 다시 볼 수 있다. 정정 중 초안은 기존 확정 요약 집계에 넣지 않는다.
- **선행·영향 파일:** IM03 마감/수행 구분, IM06 비교·날짜 계약, IM13 정정 무효화. [workout_screen.dart](../../lib/workout_screen.dart), [training_screens.dart](../../lib/training_screens.dart), [training_program.dart](../../lib/domain/training_program.dart), [training_controller.dart](../../lib/app/training_controller.dart); 집계 순수 함수와 저장 이행 검증이 필요하다.
- **GWT 1:** Given 전부 제외 후 마감한 세션과 `0 kg × 5회` 완료 한 세트 세션 → When 각각 요약 → Then 전자는 수행 0/마감 상태, 후자는 수행 1세트/5회이며 목표·초안은 합산되지 않는다.
- **GWT 2:** Given 같은 부하의 kg/lb 실제 기록, 지난 중량 0, 실제 날짜 미상 기록 → When 비교 → Then 동등 단위는 환산 비교하고 0분모 증가율은 없으며 날짜 미상 기록에 가짜 ‘최근’ 순서를 부여하지 않는다.
- **GWT 3:** Given 마감 요약과 연결된 이전 기록 → When 실제 기록 정정 확정 또는 비교 조회 실패 → Then 정정 뒤 최신 실제값으로 재계산하고 재마감 전 상태를 반영하며, 조회 실패에도 확인된 수행값은 보존된다.
- **미결정 정책:** 기본 비교 지표/대응 조건, 같은 날 복수 수행 정렬, 부분 수행 마감 허용 범위, 요약 첫 노출 방식, 외부중량 합산 지원 종목을 정해야 한다. 날짜/부하가 불명확한 기존 데이터는 보수적으로 미분류한다.
- **근거:** [Strong Focus Metric](https://help.strongapp.io/article/226-focus-metric), [FitNotes 진행 비교](https://www.fitnotesapp.com/progress_tracking/). 요약·지표 자체 효과는 실측하지 않았으며 위 집계 규칙은 앱 데이터에 맞춘 제안이다.

## IM13 · 보관한 프로그램의 실제 기록 정정

- **목적:** 프로그램을 바꾼 뒤 발견한 입력 오류를 바로잡으면서 당시 트레이너 계획·목표와 수행 이력을 보존한다.
- **현재 차이:** [SavedRecordsScreen](../../lib/training_screens.dart)은 보관 세션과 미래 세션 모두 `readOnly`로 연다. [withSetActual/withSetDraft](../../lib/domain/training_program.dart)도 활성 계획의 세트만 허용한다. UI 조건만 해제해서는 정정이 작동하지 않는다.
- **정상 흐름 1:** 보관 기록의 실제 세트 조회 → 별도 ‘기록 정정’ 진입 → 기존 확정값과 현재 수정 초안 표시 → 필드 수정 → 변경 내용 확인 후 저장한다.
- **정상 흐름 2:** 저장 확정 → 정정 이력/시각 보존 → IM03 계약에 따라 확인된 마감만 재개·재마감으로 안내 → IM10 요약/비교를 다시 계산한다. 과거 마감 미상/미마감은 기존 이력을 보존하고 첫 명시 마감을 안내한다. 보관 계획은 활성화하지 않는다.
- **권한 제안:** 미래 계획은 계속 읽기 전용이다. 보관 계획은 기존 실제 기록의 정정만 별도 허용하며, 운동·세트 추가/삭제·순서·목표·프로그램 버전·일정은 편집하지 않는다. 보관된 미기록 세트를 새 수행으로 추가하는 것은 별도 정책이다.
- **필수 데이터 제안:** 보관 계획/세션/세트 ID, 원실제값, 정정 초안, 대상 `baseRevision`, 정정 `operationId`, 확정 리비전·수정 UTC 시각·수정 전후 값의 최소 이력을 저장한다. 실제 수행일을 정정하면 그 날짜와 출처도 함께 보존한다. 원본 계획 스냅샷은 변경하지 않는다.
- **선택 데이터 제안:** 변경 이유와 이전 리비전 복원을 제공하는 undo UI다. 메모 수정과 실제 수행일 정정은 새 운동 발생으로 취급하지 않는다. 이력 보관 범위는 별도 정책이다.
- **초안 분리:** 보관 정정 초안은 새 수행 초안과 구분해 저장하고, 조회/통계는 정정 초안으로 확정값을 대체하지 않는다. 재실행 시 원기록·작성 중 수정·저장 상태를 함께 복원한다.
- **저장 경계:** 기존 `TrainingController.update`는 실패 때도 메모리 상태를 먼저 바꾼다. 정정은 확정 기록과 보류 중 변경을 구분하는 명령/상태 계약을 추가하고, 실제값·이력·마감 재개를 하나의 저장 단위로 검증한다.
- **필드 검증:** 실제 중량은 유한 0 이상, 반복은 양의 정수, 선택 RIR은 유한 0 이상이다. `0`/빈값을 구분하고 원단위를 보존한다. 단위만 변경할 때 숫자 유지임을 표시하며 환산은 명시 동작으로만 제공한다.
- **상태 정정:** 제안 범위는 기존 완료값 정정과 완료↔제외의 명시적 변경이다. 완료→제외는 실제 중량/반복/RIR 제거 영향을 확인하고 이전 리비전에 보존한다. 제외→완료는 유효한 실제값을 새로 입력해야 한다.
- **재개/마감:** 편집 진입·초안 저장은 기존 상태를 유지한다. 정정 확정 시 확인된 마감만 재개하고 재마감을 제안한다. 미상/미마감 기록에는 과거 마감·재개 사건을 만들지 않는다. 기록 누락 상태로 되돌리기 허용 여부는 별도 정책이며 자동으로 마감 조건을 맞추지 않는다.
- **취소 논리:** ‘정정 취소’는 해당 정정 초안을 폐기하고 원확정값·마감 상태를 유지한다. 재개 후 원값으로 되돌리는 undo는 별도의 정정 리비전이며 이력을 지우지 않고 새 수행으로 만들지 않는다.
- **경합 논리:** 저장 시 현재 리비전이 `baseRevision`과 다르면 자동 덮어쓰기하지 않고 최신값/작성 초안 비교를 제공한다. 중복 제출·재시도는 동일 `operationId`로 한 번만 반영한다.
- **파생 영향:** 수정 확정 시 수행 수·비교·내보내기 대상은 새 리비전을 사용한다. 이미 다른 세트에 사용자가 복사한 초안/실제값은 소급 변경하지 않고 출처 리비전을 보존한다.
- **휴식 영향:** 정정·정정 취소·undo·재마감은 새 휴식을 시작하지 않는다. 진행 중인 다른 세션 타이머는 영향받지 않는다. 바로잡은 세트에 연결된 타이머가 남아 있으면 IM08의 중지 조건만 적용한다.
- **빈 상태:** 실제 기록 없는 보관 세트는 계획 조회와 ‘정정할 기록 없음’을 제공한다. 보관 초안이 있다면 작성 중 정보로만 표시하며 완료값을 만들어 내지 않는다.
- **로딩 상태:** 원기록·리비전 로드 완료 전 편집을 비활성화한다. 저장 중 같은 정정의 중복 제출을 막고 기존 확정값/저장 중 변경의 차이를 확인할 수 있게 한다.
- **실패 상태:** 읽기 실패는 원파일 유지·재시도, 쓰기 실패는 정정 초안·원확정값 유지·재시도다. 실패 상태의 값을 확정 집계에 반영하거나 성공 문구로 표시하지 않는다.
- **취소·이탈:** 취소는 초안 폐기 확인 후 원기록으로 돌아간다. 단순 닫기/뒤로가기는 수정 초안 저장 후 이탈하며 실패하면 머무른다. 앱 종료 후에는 마지막 저장 성공한 정정 초안을 복원하며 저장에 실패한 최신 입력의 복구를 보장하지 않는다.
- **선행:** IM03 명시 마감/재개, IM06 수행일·리비전/종목 계약, 저장 파일 이행. 기록 정정 권한을 미래 계획이나 트레이너 원본 편집 권한과 분리해야 한다.
- **영향 파일 제안:** [training_screens.dart](../../lib/training_screens.dart), [workout_screen.dart](../../lib/workout_screen.dart), [training_program.dart](../../lib/domain/training_program.dart), [training_controller.dart](../../lib/app/training_controller.dart), [local_training_store.dart](../../lib/data/local_training_store.dart). 기존 활성 계획 제한을 전역 해제하지 말고 정정 명령으로 검증한다.
- **GWT 1:** Given 보관 계획의 완료 기록 → When 중량/단위를 정정하고 저장 → Then 실제값·수정 이력만 바뀌고 원계획/목표/세트 ID·활성 계획은 같다. 확인된 마감은 재마감 대기, 미상/미마감은 과거 상태를 보존하며 새 휴식은 없다.
- **GWT 2:** Given 저장에 성공한 정정 초안과 기존 마감 기록 → When 취소하거나 정정 확정 저장 실패 후 재실행·재시도 → Then 취소는 원값/마감 유지, 실패 후 원확정값과 마지막 저장 초안은 복원되고 재시도 성공은 리비전을 한 번만 추가한다.
- **GWT 3:** Given 편집 중 대상 리비전이 바뀌었거나 미래/미기록 보관 세트 → When 정정 저장 요청 → Then 경합은 초안 보존 후 검토를 요구하고 읽기 전용 대상은 거부한다. 완료↔제외/undo 허용 경로도 새 운동·휴식 이벤트는 만들지 않는다.
- **미결정 정책:** 완료↔제외·기록 전 되돌리기의 허용 범위, 정정 후 재마감 방식, 실제 날짜 정정 범위, 변경 이유 필수 여부·이력 보존 기간·undo 노출, 보관 미기록 세트의 추후 입력을 정해야 한다. 현재 읽기 전용을 이미 변경한 것으로 해석하지 않는다.
- **근거:** [Strong 과거 운동 수정](https://help.strongapp.io/article/249-how-do-i-edit-a-past-workout). 리비전·마감 재개·원본 보존·충돌 처리는 우리 앱의 설계 제안이다.

## 문서 검증과 구현 전 확인

- 각 항목은 현재 코드 차이, 정상 흐름, 데이터/논리, 빈·로딩·실패·취소·이탈, 선행/영향 파일, Given–When–Then 3개, 미결정 정책을 포함한다.
