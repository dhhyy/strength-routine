## 0. 이 문서의 목적

1. 사용자가 제시한 **4가지 자동 조절 로직**을 분석·검토하고, 결정론적 엔진의 규칙으로 명세한다.
2. 참고 엔진(Strength Architect)의 모델을 해부하여, 4가지 로직이 어떤 **공통 원리** 위에 있는지 정렬한다.
3. "계속 늘어나는 디테일"을 감당할 **엔진 아키텍처(규칙 레지스트리)**를 제안한다.
4. 진행 전 **확정이 필요한 결정 항목**을 한곳에 모은다.

> 이 문서는 아직 값·수치를 확정하지 않는다. `제안 기본값`으로 표시된 것은 전부 함께 정할 대상이며, 임의로 만든 수치를 사실처럼 쓰지 않는다.

## 1. 참고 엔진 해부 — Strength Architect

랜딩 페이지에서 읽어낸 모델(참고용 요약, 이 제품의 프레이밍일 뿐 정답은 아님):

**핵심 철학** — *"Stimulus decides how much. Cost decides when to stop."*

세 가지 화폐:

| 화폐 | 이름 | 뜻 | 역할 |
|---|---|---|---|
| 효익(Benefit) | **Effective Sets** | 자극에 실제로 기여한 세트. 무겁고 깔끔한 세트, 가볍고 깊은 세트가 같은 크레딧을 얻을 수 있음. 각성에서 먼 쉬운 세트는 크레딧 거의 없음 | 세션 슬롯·개인 볼륨 목표의 크기를 정함 |
| 전역 비용 | **Neural Load** | 무겁고 고출력 작업의 '빠른 청구서'. 최대치 근처에서 급증. **신경계는 공유되므로 리프트 간에 따라다님** | 회복 상한(ceiling) |
| 국소 비용 | **Metabolic Load** | 실패 근처 깊은 세트의 부위별 청구서. 실패 근처에서 곡선이 가팔라지고 잔여 피로가 그 부위에 남음 | 부위별 피로 예산(budget) |

**Recruitment Router (Fast-Twitch Threshold)** — 부하가 고역치 섬유를 스스로 동원할 수 있는지에 따라 두 갈래로 처방을 라우팅:
- **Load road (역치 위)**: 무게가 이미 필요한 섬유를 동원 → 세트를 깔끔하게 유지, 힘 품질(force quality)이 떨어지는 지점에서 중단.
- **Fatigue road (역치 아래)**: 무게만으로는 못 미침 → 피로가 섬유를 끌어오도록 세트를 더 깊게, 단 부위별 대사 예산 안에서.

**Set Architecture** — 국면(phase)이 자극 목표·강도 밴드·비용 예산을 고정하면, **결정론적 가중 선택**으로 구조를 고름(Wave Loading, Strength Cluster, Sawtooth = load road / Tapered, Drop Set = fatigue road / Interleave = mixed). 같은 노출 반복을 피함.

**과학 예시** — 80% 1RM에서 최대 힘은 ~3반복까지 95% 이상 유지, 이후 인산 축적으로 하락 → 그래서 3×5가 아니라 **5×3**(힘 품질 지점에서 세트를 끊고 반복을 늘리는 대신 세트를 추가). "peak force drop-off model, VBT 연구 기반 보정"이라고 표현.

**Continuous Regulation** — 생성은 시작점일 뿐:
1. **Readiness gates today**: 수면·근육통·기분·HRV·최근 노력이 오늘의 볼륨·강도·RPE 상한·가능한 세트 구조를 바꿈.
2. **Performance updates strength**: 완료 세트가 '살아있는 working max'를 유지 → 퍼센트가 '지금의 나'를 따라감.
3. **Volume landmarks are learned**: 부위별 목표를 인구 평균표가 아니라 **실제 흡수한 effective work**에서 재계산.

### 관찰 (검토 결과)

- 이 엔진은 `01-requirements.md`(RIR·블록 템플릿·우선순위 기반의 단순 모델)보다 **한 단계 정교**하다.
- **당신의 4개 로직은 모두 위 화폐들의 표현이다** → 흩어진 if문이 아니라 하나의 일관된 모델로 묶을 수 있다.
- **좋은 소식**: 4개 로직은 전부 앱이 이미 수집하는 데이터(`중량/반복/RIR`)만으로 구현 가능하다. HRV·수면 같은 readiness 입력은 `01` 문서상 MVP 범위 밖 → **후속 확장**으로 두면 정합성이 맞는다.
- **결정 필요**: 참고 엔진의 정교함(모터유닛·이중 비용·recruitment router)을 **어디까지 채택**할 것인가. → §6, §8 참고.

## 2. 대전제 (01에서 계승 + 엔진에 맞게)

- **결정론**: 같은 입력 → 같은 출력. UI와 분리된 **순수 함수**.
- **규칙·계산식** 기반 (생성형 AI 아님).
- 모든 자동 조정에는 **(a) 한 줄 이유 (b) 되돌리기/수동 수정**이 따른다.
- **의료 표현 금지**: 진단·부상 예방 보장·재활 처방으로 표현하지 않는다. "질 좋은 훈련·회복" 프레이밍만.
- **재현성**: 엔진 버전 · 템플릿 버전 · 입력 스냅샷을 저장해 언제든 재현 가능.

## 3. 공용 어휘 정의 (엔진의 전제 — 먼저 합의 필요)

엔진이 결정론적이려면 용어부터 한 가지 뜻으로 못 박아야 한다.

| 용어 | 이 문서에서의 뜻(제안) | 결정 필요 |
|---|---|---|
| **볼륨(Volume)** | 부위별 **주간 세트 수** | '총 세트'인지, RIR이 낮은 **hard set**만인지, 참고엔진식 **effective set**인지 |
| **강도(Intensity)** | working max 대비 % | RIR로 역산할지, %만 쓸지 |
| **Working Max (e1RM)** | 완료 기록으로 갱신되는 '살아있는' 최대 추정 | 갱신 공식·조건 |
| **Effective Set** | 자극에 유의미하게 기여한 세트 | 개념 채택 여부 / 판정 기준 |
| **Neural Load / Metabolic Load** | 전역·국소 피로 지표 | 채택 수준(간단 지표 vs 참고엔진식 모델) |
| **국면(Phase)** | `축적 / 강도(피킹) / 디로딩` | 명칭·개수 |
| **부위(Muscle group)** | 볼륨 상한을 매기는 단위 | 분류 체계 + 각 운동의 부위 기여 매핑 |

## 4. 로직별 분석 (핵심)

형식: **[원문] → [의도] → [배후 원리 & 참고엔진 매핑] → [결정론적 규칙 초안] → [결정 필요] → [엣지 케이스]**

### 로직 1 — 축적 ≤ 3주 → 자동 디로딩 또는 미니 피킹

- **[원문]** 볼륨 축적 시기 3주 이상 안 되게 → 그다음 주 자동 디로딩, 혹은 미니 피킹(볼륨 줄이고 강도 증가 추천).
- **[의도]** 무한 축적을 막고, 3주 뒤엔 강제로 피로를 풀거나(디로딩) 국면을 전환(피킹)한다.
- **[원리 & 매핑]** 축적될수록 **Neural Load 상한**에 근접 → 적응이 피로에 가려짐. 디로딩 = 예산 리셋, 미니 피킹 = fatigue road → load road 전환(볼륨↓·강도↑).
- **[규칙 초안]**
  - 신호: `accumulationWeeks` (현재 블록 내 연속 축적 주차)
  - 조건: `accumulationWeeks >= MAX_ACCUM` (제안 기본값 **3**)
  - 액션: 다음 주차 `phase = DELOAD | MINI_PEAK`
  - 선택 규칙(결정 필요): 예) 목표=근비대 → `DELOAD`, 목표=스트렝스/파워빌딩 & 잔여 블록 충분 → `MINI_PEAK`
  - `DELOAD` 정의(제안, 조정 가능): 세트 수 ~50%↓, 강도(%) 유지 또는 소폭↓
  - `MINI_PEAK` 정의(제안): effective set 목표↓, 강도 밴드↑, load road 구조 위주
  - 이유 예: "3주 연속 볼륨을 쌓았어요. 쌓인 피로를 풀기 위해 이번 주는 디로딩입니다."
- **[결정 필요]** MAX_ACCUM(3 고정? 목표·개인별?), 디로딩↔미니피킹 자동 선택 기준, 각 국면의 정량값.
- **[정합성 경고]** `01` 문서의 기본 4주 블록은 `볼륨 2주 → 강도 1주 → 디로딩 1주`(축적 2주)다. 신규 규칙(≤3주)과 **숫자가 다르다**. → 신규 규칙을 '상한'으로 두고 프리셋은 그 안의 한 인스턴스로 볼지 확정 필요.
- **[엣지]** 블록이 3주보다 짧을 때, 블록 경계와 디로딩이 겹칠 때.

### 로직 2 — 스쿼트/데드 같은 날 OK, 볼륨은 하나만

- **[원문]** 스쿼트·데드 같은 날 해도 되지만 둘 다 볼륨은 넣지 않게. 스쿼트가 메인 볼륨이면 데드 볼륨 자동↓, 혹은 반대.
- **[의도]** 동일 세션 배치는 허용하되, 두 종목 모두 고볼륨은 금지. 하나가 메인이면 다른 하나는 저볼륨.
- **[원리 & 매핑]** 스쿼트+데드는 **공유 회복 자원**(척추기립근·후면사슬 = 국소 Metabolic Load 공유, 고중량 = 전역 Neural Load 공유). 한 세션에서 둘 다 고볼륨 → 예산 초과.
- **[규칙 초안]**
  - 정의: 한 세션 내 리프트의 `role ∈ {MAIN_VOLUME, TECH_MAINTAIN}`
  - 조건: 같은 세션에 스쿼트·데드 공존 AND 둘 다 `MAIN_VOLUME`
  - 액션: 우선순위(온보딩 1~3순위) 낮은 쪽을 `TECH_MAINTAIN`(저볼륨·소수 고강도 세트)로 강등
  - 이유 예: "오늘은 스쿼트가 메인이라 데드리프트는 가볍게 기술 유지로 둘게요."
- **[매핑 확인]** `01` 문서 "스쿼트+데드는 같은 **블록**에서 둘 다 최대 발전 볼륨 금지"와 정합. 다만 문서는 **블록** 층위, 신규는 **세션(같은 날)** 층위 → 둘 다 규칙으로 공존 가능.
- **[결정 필요]** "볼륨 줄이기"의 정량(데드 세트 상한·%), 벤치+OHP도 동일 규칙 적용?(문서엔 있음), 하체1+상체1 조합의 상한 차등.
- **[엣지]** 사용자가 수동으로 둘 다 볼륨을 넣으려 할 때 → `01` 원칙대로 **경고 후 허용**(편집 자체는 막지 않음).

### 로직 3 — RIR 누적 과부하 → 하향 추천 + 이유

- **[원문]** 사용자가 기록하며 자꾸 무리(RIR 1~2 계속 누적) → 앱이 무게를 줄이라고 추천, 방향성을 설명하면서.
- **[의도]** 실제 RIR이 목표보다 지속적으로 낮으면(=계획보다 무겁게) 감량을 **제안**하고 이유를 설명한다.
- **[원리 & 매핑]** 목표보다 낮은 RIR 지속 = 상대 강도가 계획보다 높음 = **working max 추정이 과대** 또는 피로 과축적. 참고엔진의 *"Performance updates strength(살아있는 working max)"* + *"Readiness gates"*에 해당.
- **[규칙 초안]**
  - 신호: 최근 `N` 세션(제안 기본값 **3**)의 대상 리프트 `목표RIR − 실제RIR` 추세
  - 조건: `실제RIR ≤ 목표RIR − k` 가 `m`회 연속 (제안 `k=1`, `m=3`)
  - 액션(방향 확인 필요, 아래 셋 중):
    1. **Working max 재보정**(권장): working max를 소폭↓ → 이후 모든 % 자동 하향 (가장 근본적)
    2. 다음 세션 목표 중량만 −1~2 증량틱↓
    3. 볼륨↓ (RIR 누적은 볼륨 처방이 더 흔함)
  - 이유 예: "최근 3세션 RIR가 목표보다 낮았어요(계획보다 무겁게 하고 있어요). 질 좋은 볼륨을 위해 기준 중량을 조금 낮출게요." (+되돌리기)
- **[결정 필요]** 신호 창(세션 수 vs 세트 수), `k·m` 임계값, 감량 폭, **감량 대상(무게 vs 볼륨 vs working max)**, 메인/보조 차등.
- **[엣지]** 하루 컨디션 저하(문서의 "오늘 가볍게")와 **추세**를 구분해야 함. 의료 표현 경계 유지.

### 로직 4 — 주간 토탈 볼륨 상한 (오버트레이닝 방지)

- **[원문]** 일주일 토탈(메인+보조) 볼륨이 너무 높지 않게, 사용자가 오버 훈련 안 하게.
- **[의도]** 부위별 주간 볼륨에 상한을 두고, 초과 시 보조운동을 줄이거나 대체한다.
- **[원리 & 매핑]** 참고엔진의 **Volume landmarks(부위별 학습된 목표)** + **Metabolic Load 예산**. 메인 리프트도 특정 부위 볼륨에 기여하므로, 보조는 남은 예산 안에서만.
- **[규칙 초안]**
  - 정의: 부위별 주간 세트 카운트 = Σ(메인 리프트의 부위 기여 + 보조운동 세트)
  - 데이터: `부위별 주간 상한 테이블` + `운동→부위 기여 매핑`
  - 조건: `부위 주간세트 > 상한`
  - 액션: 낮은 우선순위 보조부터 세트↓ 또는 대체 제안 (`01`: "메인 회복 부담↑ → 보조 수·세트↓ 또는 대체안")
  - 이유 예: "이번 주 등 볼륨이 회복 범위를 넘어서, 바벨 로우 2세트를 줄였어요."
- **[결정 필요]**
  - 볼륨 카운팅 단위(총 세트 / hard set / effective set)
  - **부위 분류 체계 + 운동별 기여 매핑** (데이터셋 필요)
  - **상한값의 출처**: 일반 가이드라인을 출발점으로 → 운영자(트레이너) 검토·조정 → 장기적으로 참고엔진처럼 개인 데이터 학습. *(수치는 임의 생성하지 않고 함께 확정)*
- **[엣지]** 사용자가 보조를 많이 추가할 때 → `01`: 사용자 추가 보조는 완료 조건 제외, 경고만.

## 5. 아키텍처 제안 — "규칙 엔진"으로 지어야 하는 이유

당신이 "계속 추가되어야 한다"고 했다. 그렇다면 이 로직들을 **하드코딩된 if-else 덩어리**로 쌓으면 안 된다 — UI에서 겪은 "하나 고치면 전체가 터짐"을 **엔진에서 똑같이** 겪게 된다.

**제안: 규칙 레지스트리 + 파이프라인**

```
각 로직 = 독립 규칙(Rule) {
  id, version,            // 재현성/버전관리
  priority,               // 충돌 시 우선순위
  signals(state) -> {}    // 필요한 입력 신호 수집
  guard(signals) -> bool  // 발동 조건
  action(ctx) -> Change   // 제안/변경 (자동적용 or 사용자 승인)
  reason(ctx) -> string   // 한 줄 이유 (필수)
}

엔진(state) =
  신호 수집 → 규칙 평가(priority·충돌 해소)
  → 제안 생성 → (자동적용 | 사용자 승인)
  → 스냅샷 저장(입력·엔진버전·결과)   // 결정론 + 재현성
```

- **충돌 해소 정책 필요**: 예) *안전·회복 > 발전*. 로직3의 감량 추천이 다른 규칙의 증량과 부딪히면 감량 우선.
- **"디테일 추가" = 규칙 하나 추가** → 기존 규칙은 건드리지 않음(격리). 이게 당신이 원한 "계속 늘어남"을 안전하게 만드는 핵심.
- `01`의 요구(결정론·버전 저장·테스트 가능)와 정확히 정합.

> **UI에서의 '디자인 시스템'과 완전히 같은 처방이다**: 단일 진실 공급원 + 격리된 조립 단위. 병(단일 덩어리·격리 없음)도, 약(격리된 조립 + SSOT)도 UI와 엔진이 동일하다.

## 6. 검토에서 발견한 이슈 요약

1. **정합성**: `01`의 축적 2주(4주 블록 프리셋) ↔ 신규 로직1의 축적 ≤3주 — 숫자 상충. 상한 vs 프리셋 관계 확정 필요.

5. **readiness 입력**: HRV·수면 등은 `01`상 MVP 밖. 로직1~4는 `중량/반복/RIR`만으로 충분 → MVP 실현 가능.

## 7. 플랫폼 변경 메모 (웹앱 → Flutter)

- `01`은 "모바일 우선 웹앱", 비기능 요구도 "모바일 Safari/Chrome" 기준. **이번에 Flutter 네이티브 앱으로 변경.**
- **엔진 영향**: 거의 없음 — 오히려 유리. 계산 엔진을 **Dart 순수 함수 패키지**로 두면 UI와 완전히 분리되고 테스트가 쉬움(`01`의 순수 함수·결정론 요구와 정합).
- **UI 파운데이션 영향**: 웹(CSS)이 아니라 **Flutter 기준**으로 다시 잡는다. 다행히 Flutter는 디자인 시스템에 유리 — `ThemeData`/`ThemeExtension` = 디자인 토큰, 모든 것이 위젯 = 컴포넌트 조립. (다음 단계에서 다룸)
- `01` 문서의 "웹앱/Safari/Chrome" 문구는 추후 개정 대상으로 표시.
