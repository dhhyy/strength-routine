# 9/7 Claude 인수인계 · 여기서 재개

> 작성일: 2026-09-07 (Asia/Seoul)
> 대상: `apps/strength_routine` · Flutter 네이티브 사용자 앱
> 목적: 대화 이력이 없는 Claude가 확정 사항과 실제 작업 상태를 파악하고 이어서 작업하기 위한 문서

**최신 개발 기준:** [9/7 기능 개발과 커밋](2026-09-07-development.md)의 F01~05. 검색·습관은 실제 데이터 기능이며, 다음 세트·상태 집계·보관 초안도 보완했다. **최신 검증 결과는 [자체 검증 보고서](2026-09-07-verification.md)를 따른다.** 직접 빌드 전환 여부·D5 정량·첫 프로그램은 여전히 미결정이다.

**최신 사용자 지시:** “시뮬레이터는 띄우지 말고, 자체적으로 검증하고 문서로 상세하게 업데이트해줘.” 정적 분석·자동 테스트·코드 대조를 기본으로 한다. 이전 시뮬레이터 요청보다 이 지시가 우선하며 사용자 재요청 전까지 실행·조작·장애 해결 재시도를 자동 재개하지 않는다.

## 먼저 알아야 할 결론

**사용자는 트레이너가 만든 완성된 프로그램을 선택한다. 앱은 운동·세트 구성을 유지하고 중량·시작일·운동요일만 개인화한다.**

첫 마일스톤은 **프로그램 선택·시작 → 운동 기록 → 앱 재실행 후 복원**이다. 9/7 후속 작업에서 프로그램 계약·시작 화면·실제 세트 입력·로컬 저장을 연결했다. **실제 배포 카탈로그는 아직 비어 있다.** 공개 후보 조사만 승인됐고 특정 프로그램 선정·배포는 미확정이다. 트레이너 등록 도구는 사용자가 별도로 나중에 개발한다.

이번 날짜 경계 수정 전 기준은 정적 분석 문제 없음·전체 **65개 테스트 통과**다. [V01 습관 탭·V02 프로그램 시작일 선택기](2026-09-07-verification.md)의 재현과 최종 결과는 자체 검증 보고서에서 확인한다. 기존 375×812 위젯 렌더는 네이티브 조작이 아니다. 이전 실행의 `NSMachErrorDomain -308`과 전용 기기 인식 실패 이후 마지막 재시도는 Xcode 빌드(124.0초)까지 성공했지만, 요청 변경 전 앱 화면을 확인하지 못했다. 네이티브 입력·프로세스 종료 후 화면 복원은 미검증이며 현재 보류다. 초기 12개·39개 테스트 및 Mac 잠금은 아래 이전 이력으로만 읽는다.

새 기록 모델은 스쿼트·벤치프레스·데드리프트·오버헤드프레스 4종을 수용한다. 유효한 중량/반복/RIR 및 주입한 기준일에 따른 미래 날짜 여부를 검사하며, 날짜는 입력된 연·월·일을 UTC 자정으로 보관한다. e1RM·working max 계산은 없다.

**현재는 JSON 변환뿐 아니라 실제 파일 저장소까지 구현했다.** 다만 배포 카탈로그가 비어 있어 일반 실행에서는 빈 상태가 정상이다. 전체 흐름은 QA 전용 프로그램을 주입하여 검증하며, QA 데이터가 출시 콘텐츠에 포함됐다고 해석하지 않는다.

중량 처방은 `manual` / `fixedKg` / `percentOfBaseline` 세 종류다. 비율 처방은 사용자가 명시적으로 입력한 프로그램 기준 중량에 적용하며 최근 반복 기록으로 e1RM을 자동 산출하지 않는다. 일정·계산한 목표 중량은 시작 시 저장하고 복원 때 현재 날짜나 수정된 원본 프로그램으로 다시 계산하지 않는다.

## 후속 조사 · 14개 운동 앱 비교

사용자가 운동 앱을 더 조사하고 그 자료에 근거한 개선 분석을 요청했다. [9/7 종합 분석](2026-09-07-fitness-app-analysis.md)에 14개 앱·공식 본문 40개, [현재 코드 대조](../research/2026-09-07/expanded/current-app-audit.md)의 APP01~15, 개선 백로그 IM01~15와 수용 기준을 정리했다. 개별 출처는 [목록](../research/2026-09-07/expanded/sources.md)을 따른다.

조사 당시 제안 순서는 실제 프로그램 연결·상태 정확성/네이티브 검증 → 운동 ID/수행일 계약 → 기록 편의 → 일정·요약·백업이었다. **개선안 전체가 사용자 확정 요구인 것은 아니다.** 조사 단계에서는 코드·저장 데이터·스키마를 바꾸거나 테스트를 실행하지 않았고 당시 검증 기준은 39개였다. 이후 개발 요청에 따라 F01~05를 구현했으며 현재 상태는 위 코드 표와 [자체 검증 보고서](2026-09-07-verification.md)를 따른다. 현재 사용자 지시에 따라 네이티브 실행은 보류한다.

## 후속 요청 · 개선 기능 상세 분석

사용자의 “그리고 문서들을 남기고, 그 기능들을 분석해” 요청에 따라 [기능 분석 정본](2026-09-07-feature-specification.md)과 [프로그램·시작·검색](feature-analysis/2026-09-07-programs.md), [운동 중 기록·요약·정정](feature-analysis/2026-09-07-workout.md), [상태·날짜·일정·복원](feature-analysis/2026-09-07-data-reliability.md)을 추가했다. IM01~15 각각 현재 구현과 차이, 정상 흐름, 논리 데이터, 실패·취소·재실행, 영향 파일과 선행 조건, 수용 기준, 미결정 정책을 기록했다.

개발 전에 특히 다음 경계를 확인한다.

- `isSessionComplete`의 필수 기록 충족, 실제 완료 세트 수, `completionNotified`, 사용자 명시 마감은 서로 다른 의미다. 기존 파일에서 마감 의도를 추정하지 않는다.
- 예정일과 실제 수행일을 분리하고 옛 기록의 실제 날짜는 미상으로 남긴다. 공통 종목 ID를 추가해도 기존 계획·세션·세트 ID를 보존한다.
- 지난 값은 새 초안에만 가져온다. 새 수행 완료의 저장 성공만 타이머 시작 후보이며 정정·취소·재시도·복원은 새 완료 사건이 아니다.
- 설정 초안 취소로 이미 저장한 최근 리프트 기록을 지우지 않는다. 전체 백업 복원은 일반 저장과 달리 기존 쓰기를 정리하고 후보 전체를 검증한 뒤 교체한다.
- 선정 콘텐츠에 필요한 IM14 최소 확장은 IM01보다 먼저 할 수 있다. 모든 편의 기능을 IM06 완료까지 멈출 필요는 없으며 현재 세션 내 다음 세트 이동·집계 문구는 먼저 가능하다.

상세 문서의 필드명·전이·수용 기준은 **개발 제안**이다. 이번 문서 작성으로 코드·저장 스키마를 변경하거나 기능 테스트를 실행하지 않았다. 이후 실제 구현 결과와 검증은 해당 IM 및 날짜별 작업 기록에 별도로 남긴다.

## 아직 답이 없는 항목

1. **직접 빌드 vs 트레이너 프로그램 선택:** 후속 개발 요청의 직접 빌드 순서가 기존 선택 방식을 대체하는지 질문했으며 미응답이다. 답변 전에는 기존 구성 보존 결정을 유지하고, 새 목표/기간/리프트 우선순위 생성기를 확정하지 않는다.
2. **첫 공개 후보 선정:** I08의 조사 방식은 답변 완료. [공개 후보 비교](../research/2026-09-07/program-candidates.md)의 [Stronglifts 5×5](https://stronglifts.com/stronglifts-5x5/workout-program/), [GZCLP](https://swoleateveryheight.blogspot.com/2016/02/gzcl-applications-adaptations.html), [5/3/1 for Beginners](https://www.jimwendler.com/blogs/jimwendler-com/5-3-1-for-beginners) 중 어떤 버전·기간을 검토할지 또는 기간형 후보를 추가 조사할지 정한다. 앱 수록/재배포 권한은 세 후보 모두 미확인이다.
3. **실제 프로그램 처방 계약:** 현재 고정 kg·수동·명시적 기준 대비 %를 지원하도록 기술 계약을 구현했다. 특정 후보의 시작 중량·TM·e1RM 공식이 사용자 확정됐다는 뜻은 아니다.
4. **부족한 기록·운동별 처방:** 현재 시작 화면은 프로그램에 필요한 메인 리프트 기록과 비율 처방의 기준 중량을 요청한다. 보조 운동은 `manual`로 목표 중량을 비워 둘 수 있다. 실제 수록 프로그램에 이 계약이 충분한지는 선정 후 검토한다.
5. **I02 — 목표 분류:** 스트렝스·근비대·파워빌딩 3종은 기존 요구사항. 이번 인터뷰는 미응답이며, 프로그램의 분류 항목으로 다룰지도 검토한다.
6. **엔진 D3~D7, 특히 D5:** 신호창·임계·감량 대상/폭을 포함한 수치·공식은 미확정이다. D3~D6의 운동·세트/블록 자동 변경은 I06과 적용 범위를 재조정해야 한다. 훈련 후 자동 조절은 첫 시작 흐름과 구분해 후속 인터뷰한다.

기존 D1(hard set)·D2(Lv1/순수 함수)·D8(충돌 우선순위)은 과거 확정 기록이지만, 이것만으로 트레이너 프로그램을 자동으로 재구성해도 된다는 뜻은 아니다.

## 재개할 작업

1. [자체 검증 보고서](2026-09-07-verification.md)부터 읽고 `flutter analyze`와 `flutter test --concurrency=2 --reporter expanded`로 변경 범위를 확인한다. V01/V02와 저장·복원 한계를 구별해 기록한다. 시뮬레이터 실행은 사용자 재요청 전까지 보류하며 자동 재개하지 않는다.
2. 직접 빌드 전환 여부에 대한 답변과 **첫 수록 후보·구체 버전·기간**을 반영한다. 기존 선택 방식을 임의로 폐기하거나 원작을 임의로 4주 패키지화하지 않는다.
3. 해당 콘텐츠의 수록 조건과 처방 형식을 확인한 뒤 카탈로그에 연결한다. 초기 계약은 **매주 동일 세션 수·유한 기간·고정 반복**이며 AMRAP, 진급 단계, 무한 주기는 미지원이다.
4. 시작 전 최종 결과 확인 화면까지 구현됐다. 날짜별 운동·세트·목표 중량을 검토한 뒤 확정 저장하는 흐름을 QA한다. **시작 후 일정 변경 UI**는 미구현이다. 미래 일정 변경의 도메인 메서드는 있어도 사용자 UI 완료로 보지 않는다.
5. 후속 설정, 실제 수행일·공통 운동 식별을 전제로 한 기록 추세, D5 조절, 코치 Q&A·트레이너 도구·계정·클라우드 동기화·구독은 후속 작업이다. 검색·습관을 다시 미구현으로 다루지 않는다. 운동 설명 사전·미디어 가이드는 현재 검색과 별개다.
