# Strength 인터랙티브 랜딩 — 정의·접근성·Three.js 근거

확인일: 2026-09-08. 공식 본문 5개를 웹에서 열어 확인했다. 이 문서는 연구 결과와 구현 제안을 구분한다. 라이브러리 설치·브라우저 렌더·성능 측정·앱/랜딩 코드 변경·배포는 수행하지 않았다.

## 이번 시안의 작업 정의

**사용자 입력 → 명시적인 상태 변화 → 바로 식별할 수 있는 결과 → 다시 변경하거나 초기화**를 한 단위로 설계한다. 이는 아래 R01의 trigger/feedback 개념을 Strength의 시안 평가에 맞게 확장한 **제품 작업 정의**다. 여러 단계를 포함하는 전체 랜딩 체험을 하나의 microinteraction이라고 부르는 뜻은 아니다.

예를 들어 프로그램 버튼 선택 시 선택 표시, 설명·주간 횟수, 대응하는 3D 장면이 함께 바뀌어야 한다. 배경 자동 회전이나 커서에 따른 광택만 있다면 시각적 반응은 있지만, 이번 시안의 핵심 체험을 설명하는 입력·결과 관계는 약하다.

다섯 시안을 구분할 때 팔레트뿐 아니라 **무엇을 조작하고 무엇을 이해하게 되는지**를 달리한다. 아래는 시각 스타일과 별개인 동작 후보이며 확정 사양이 아니다.

| 동작 후보 | 입력 | 상태 변화·즉시 피드백 | 드래그 대안 |
|---|---|---|---|
| 프로그램 둘러보기 | 프로그램 선택 | 선택 프로그램·빈도·설명이 바뀌고 해당 3D 그룹 강조 | 이름이 있는 선택 버튼 |
| 주간 일정 보기 | 운동 요일 선택 | 요일 배치와 선택 개수가 동시에 갱신 | 요일 토글 버튼 |
| 세트 기록 체험 | 체험용 세트 완료/되돌리기 | 완료 개수와 기록 요약·3D 진행 표시 갱신 | 실제 button 요소 |
| 주차 비교 | 주차 선택 | 표시 중인 주차·세트 구성과 장면 상태 갱신 | 이전/다음 버튼·직접 주차 선택 |
| 장면 탐색 | 회전·초점 변경 | 시점과 현재 선택 항목 설명이 같이 바뀜 | 방향·초기 시점 버튼 |

주차 비교에서 미래 성과나 체중·근력 향상을 계산한 것처럼 표시하지 않는다. 기존 프로그램 구성과 합성 체험 상태를 구분하고, 랜딩 체험 조작을 실제 앱에 운동 기록을 저장하는 기능으로 표현하지 않는다.

## 핵심 출처 5개

### R01 · 인터랙션의 입력과 피드백

- 공식 자료: [NN/g — Microinteractions in User Experience](https://www.nngroup.com/articles/microinteractions/?lm=drag-drop&pt=article)
- 작성자·게시일: Alita Kendrick, 2018-10-21.
- **본문 확인:** 사용자 동작 또는 시스템 상태 변경이 trigger가 되고, 맥락에 맞는 작은 UI 변화로 feedback을 전달하는 쌍으로 설명한다. 진행 상태, 대기, 오류 방지와 되돌리기를 예시로 든다.
- **설계 적용:** 조작 옆에 선택 값·진행 수치·상태 문구를 유지하고 결과를 3D 장면과 연결한다. 클릭 피드백을 장면의 먼 위치에만 숨기지 않는다.
- **주의:** 이는 휴리스틱·전문가 설명이다. 특정 시안의 전환율 상승이나 사용성 검증을 완료했다는 근거로 사용하지 않는다.

### R02 · 모션 감소

- 공식 자료: [W3C WAI — Understanding SC 2.3.3: Animation from Interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- 본문 갱신일: 2025-09-16. **Level AAA** 해설이며 해설 페이지 자체는 규범 본문을 설명하는 자료다.
- **본문 확인:** 상호작용으로 발생하는 비필수 모션은 끌 수 있어야 한다. 불필요한 모션 제거, 끄기 컨트롤, OS/브라우저의 감소된 모션 선호를 해결 방법으로 안내한다. `prefers-reduced-motion` 사례와 CSS·JavaScript 관련 기법을 연결한다.
- **설계 적용:** 모션 감소에서는 카메라 이동·패럴랙스·연속 흔들림·물리적 튕김을 정지 상태 전환으로 바꾸되, 프로그램 선택과 기록 수치 피드백은 유지한다. CSS만 바꾸고 Three.js 렌더 동작은 계속 두지 않도록 동일 선호를 JS 상태에도 연결한다.
- **주의:** 단순히 움직임을 느리게 하는 것을 “끄기”와 동일시하지 않는다. 자동 재생은 이 문서가 별도로 구분하는 2.2.2 검토 대상이다. 이번 제안에서는 비필수 상시 자동 재생을 피한다. 이 항목 하나로 WCAG 전체 준수를 선언하지 않는다.

### R03 · 드래그 대체 조작

- 공식 자료: [W3C WAI — Understanding SC 2.5.7: Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)
- 본문 갱신일: 2026-08-10. **Level AA**.
- **본문 확인:** 필수적인 경우 등을 제외하면 드래그 기반 기능에 드래그 없는 단일 포인터 대안을 제공한다. 키보드 대안만으로 이 기준을 만족한다고 볼 수 없으며, 클릭·탭 대안과 키보드 접근은 따로 평가한다.
- **설계 적용:** 궤도·캐러셀·일정 이동에는 방향 버튼, 직접 선택, 숫자 입력 등 같은 결과에 도달하는 조작을 제공한다. 슬라이더는 드래그 외 트랙 클릭·키보드 조작이 되는지 실제 확인한다.
- **주의:** “모바일에서는 스와이프 가능”을 대체 수단으로 계산하지 않는다. 브라우저 기본 스크롤과 사이트가 가로채 구현한 스크롤을 같은 것으로 보지 않는다.

### R04 · Three.js 설치와 모듈 구성

- 공식 자료: [Three.js Manual — Installation](https://threejs.org/manual/en/installation.html)
- 버전별 고정 문서가 아닌 현재 공식 매뉴얼. 이번 조사에서는 최신 npm 버전 번호를 선정하거나 설치하지 않았다.
- **본문 확인:** npm과 빌드 도구가 일반적인 권장 경로이며 CDN/import map 경로도 설명한다. HTML 파일 직접 열기 대신 로컬 HTTP 서버를 사용한다. core와 addons는 별도 import가 필요하며 같은 Three.js 버전·같은 CDN 출처를 유지하도록 안내한다. CDN 장애가 사이트 실행에 영향을 줄 수 있다고 설명한다.
- **설계 적용:** 다섯 시안은 하나의 고정 버전과 공통 import 경로를 공유한다. 기존 정적 서버를 유지할 경우 해당 방식에 맞게 모듈 경로를 구성하고, 외부 CDN을 쓰면 오프라인 지원이라고 표현하지 않는다.
- **주의:** 문서의 예시 버전 문자열을 최신 버전으로 간주하지 않는다. 이 조사 자체는 빌드 도구 추가나 배포를 지시하지 않는다.

### R05 · 렌더러와 성능 점검

- 공식 자료: [Three.js Docs — WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)
- 현재 공식 API 문서. 실제 사용할 고정 버전의 API와 한 번 더 대조해야 한다.
- **본문 확인:** WebGL2를 사용하며 r163부터 WebGL1을 지원하지 않는다. 애니메이션 루프는 `setAnimationLoop()`를 권한다. `setPixelRatio()`, `setSize()`, `setDrawingBufferSize()`로 버퍼 크기를 제어한다. `renderer.info`는 draw calls·도형·메모리 관련 통계, `dispose()`는 렌더러가 할당한 GPU 리소스 해제를 제공한다. `powerPreference`는 GPU 구성에 대한 힌트다.
- **설계 적용:** WebGL 초기화 실패 시에도 HTML 설명·버튼·체험 상태는 동작하게 한다. 보이는 시안에만 렌더 자원을 배정하고, 정지·비활성 상태의 불필요한 프레임 갱신을 줄인다. 시안 전환 반복 후 통계가 계속 증가하는지 확인한다.
- **수식에서의 추론:** 같은 CSS 크기에서 pixel ratio 3은 ratio 1보다 버퍼 픽셀 수가 9배다. 이는 FPS가 반드시 9배 나빠진다는 뜻은 아니다. DPR 상한과 그림자·후처리 수준은 실제 측정으로 결정한다.
- **주의:** `high-performance` 설정을 성능 보장으로 설명하지 않는다. 렌더러 정리만으로 장면의 모든 자원이 해제된다고 가정하지 말고 실제 리소스 수명을 검증한다.

## 구현 검수용 최소 기준 — 이번 제품 제안

1. 각 시안에 결과를 바꾸는 명시적 조작과 초기화 동작을 둔다. 성공 조건은 “움직였다”가 아니라 선택 값·설명·진행 상태가 맞게 바뀌었다는 것이다.
2. 빈 선택은 안내, 초기화 실패는 체험 상태 유지와 재시도, WebGL 실패는 2D 결과로 이어진다. 장면 로딩이 HTML 버튼과 본문을 가리지 않도록 한다.
3. 터치·마우스·키보드로 같은 핵심 결과에 도달한다. 드래그 없이 클릭/탭만으로도 완료한다.
4. 모션 감소를 켜도 정보·상태 변화가 남는다. 비필수 연속 움직임은 멈추며, 전환 도중 설정을 바꾼 경우도 확인한다.
5. 좁은 화면과 높은 DPR, WebGL 생성 실패, 시안 연속 전환, 백그라운드 복귀를 확인한다. 프레임 시간·렌더 통계는 실제 실행값을 기록하며 미측정 성능 수치를 작성하지 않는다.

실행 검증은 구현 담당 작업에서 별도로 수행해야 한다. 현재 문서의 “본문 확인”은 공식 텍스트 확인이고, “설계 적용·검수 기준”은 Strength용 제안이다.
